# sub_82B1C210

Ninety-nine lifted lines, four of them frame. One direct callee (`sub_828E29C0`), no imports,
no vector work. 25,894 calls a boot session -- the busiest function in this batch by an order
of magnitude.

What it does. `r3` is a record whose first two words are `sub_828E29C0`'s handle pair
(a holder pointer at `+0`, a token at `+4`); this function never touches them, it only hands
the record over. `+8` is a byte flag, `+9` is a count N, and `+12` starts a variable region:

* flag zero -> the value block starts at `+12` and nothing is clamped.
* flag non-zero -> N pairs of `(min, max)` int32 occupy `+12 .. +12+8N`, and the value block
  starts right after them, at `r5 = (r3 + 12) + 8N`.

The value block is `{header word at +0, N words at +4}`. The loop clamps value `i` into
`[min_i, max_i]` with a signed compare and stores it back in place; the header word at `+0` is
never written, only tested. If it is non-zero, the whole block's value array (`r5 + 4`) is
broadcast to every listener via `sub_828E29C0`. The result is a literal 0 regardless.

Reading it as "clamp a set of parameter values into range, then notify subscribers" fits every
field, which is exactly the kind of story `CLAUDE.md` warns about; what is actually *verified*
is the arithmetic and the store set. What the header word at `r5+0` means -- a count, an event
id, a dirty flag -- was not determined.

Stores: exactly one outside the frame, `stwu r10,4(r8)` -- `{r5 + 4 + 4*i, 4}` for
`i` in `0..N-1`. Two details preserved: the count at `+9` is re-read on every iteration (so
the trip count is not fixed at entry), and the value is loaded from the very address the store
writes, three loads deep (`min`, `value`, `max`, in that order).

The `rotlwi r10,r9,3` is a rotate, not a shift. It is safe as a multiply by 8 only because
`r9` came from an `lbz` (0..255, nothing can wrap out of bit 31); the native body keeps
`__builtin_rotateleft32` so the reasoning does not have to be re-derived. The following
`add r5,r10,r11` is 64-bit on zero-extended operands, so `block` is kept as a `uint64_t` and
cast only at the memory accesses.

Gate verdict: **gate 1**, at depth 1, `sub_828E29C0`. That callee walks a subscriber list and
`bctrl`s each node's function pointer at `+8` with the payload in `r3` and the node's user
data in `r4`. The targets are stored pointers, unbounded in practice, and a listener is free
to do anything -- so a replay would fire every listener a second time. The call is guarded by
the header word, so a Windows() predicate could in principle admit only the calls where
`*(r5) == 0`; that would leave the clamp loop comparable, which is the one part worth
comparing, so this function is the best re-screen candidate in the batch if the guard is ever
found to be frequently zero. It is labelled gate 1 rather than split because nothing measured
says how often the header is zero.

Write set that would have been declared if it were comparable (the header-zero path, where
`sub_828E29C0` never runs): with `N = REX_LOAD_U8(r3 + 9)` and
`block = r3 + 12 + (enabled ? 8*N : 0)`, a single span `{block + 4, 4*N}` -- contiguous,
because the loop steps 4 bytes at a time with no gaps. Reads: `{r3 + 8, 2}` for the flag and
count, `{r3 + 12, 8*N}` for the range table, `{block, 4}` for the header. One span for the
writes, three for the reads, well inside budget. The only entry-state hazard is that `+9`
is re-read inside the loop: if the range table or the value block ever overlapped `r3+9` the
trip count would change mid-call, and since `block >= r3+12` it cannot. So on that path this
is enumerable and the gate is genuinely only gate 1.

Result mask: r3, the literal 0.

## Split and armed, 2026-09-12

Converted from gate-1 to a path split, which this note already named as the best re-screen
candidate in the batch. STATUS is `pending (partial: ...)`.

- **Predicate:** `(int32_t)REX_LOAD_U32(block) == 0`, where `block = r3 + 12 + (u8[r3+8] ? 8*N : 0)`
  and `N = u8[r3+9]`, all from entry bytes. Sound because the function *never writes* the header
  word at `block+0` — it only tests it — so no store can move the value between the entry read and
  the branch.
- **Comparable write set:** one span, `{block + 4, 4*N}`. The loop steps four bytes with no gaps, so
  it is contiguous, and `N` is an `lbz` so the span is at most 1,020 bytes. Reads: `{r3+8, 2}`,
  `{r3+12, 8*N}` and `{block, 4}`.
- **The count reload.** `+9` is re-read every iteration, so the trip count is not fixed at entry in
  general. It is fixed here because every store lands at `block+4` or above and `block >= r3+12`,
  so nothing inside the call can reach `+9`. A concurrent writer growing the count mid-call is the
  one residual hazard; it would put a native store outside the window, so if this port ever shows a
  memory divergence on a *later* word than the loop should reach, that is the thing to suspect.
- **Expected fraction:** unmeasured. 25,894 calls a boot, and nothing here says how often the header
  is non-zero — which was the stated reason this was labelled gate-1 rather than split. The skip
  counter now answers it directly, which is the point of arming it.
- **Stays unchecked:** the broadcast — `sub_828E29C0(r3, block+4)` and the listener walk behind it.
