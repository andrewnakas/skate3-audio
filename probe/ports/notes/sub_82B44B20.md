# sub_82B44B20

Leaf float-array multiply-accumulate: `dst[i] += src[i] * scale` for `i` in `[0, count)`. 321
lifted lines, 33 vector instructions, ~2.1M calls per boot session on `RwAudioCore Dac` -- the
hotter of this pair. No callees, no imports, no indirect calls, no timebase, no locks -- gate 1
passes trivially.

**STATUS: verified.** Session `s19` (probe/harness/out/s19.log, 2026-09-12 03:19-03:21):
`runs=2080943 diverged: registers=0 memory=0 skipped=0 overflow=0`. `skipped=0` means
`Windows()` answered on all two million calls; `overflow=0` means the window stayed in budget.

This is `sub_82B3BED8`'s accumulating twin: the same entry predicate, the same two paths, the same
window. The difference is `vmaddfp`/`fmadds` against the destination in place of a plain multiply,
which makes the destination a *read*-modify-write and puts eight extra `lvx128` in the inner loop.

Arguments: `r3` destination floats, `r4` source floats, `r6` the float count, `f1` the scale.
Nothing in `docs/rw_audio_structs.h` names either buffer, so no offset constants.

Two paths, chosen on entry state alone:

- **vector**, taken when `((r3|r4) & 0x7F) == 0` and `(r6 & 0x3F) == 0`. 32 floats per iteration:
  eight `lvx128` of the source, eight of the destination interleaved with eight `vmaddfp`, then
  eight `stvx128` in the lifted order (+32, **+0**, +16, +48, +64, +80, +96, +112). Every load of
  a block happens before every store of it, which is what makes an overlapping src/dst behave as
  the original does. The lifted cursors `r10`/`r11` run 32 bytes ahead of the block they address
  (`r9 = r11 - 32` is re-derived each iteration); the port keeps block bases instead, so its
  offsets are the lifted *effective addresses*, not the lifted displacements.
- **scalar** (`loc_82B44C44`): `count/4` groups of four `fmadds` plus a one-float
  `lfs`/`lfsu`/`stfsu` tail.

## What the game actually passes

From the census's first-four dumps: `r6 = 0x100` (256 floats, a 1 KB window) every time, `r3` and
`r4` always 128-byte aligned, `f1 = 1.0`, so **the vector path is the one that runs**. One call
site, `lr = 0x82B319F0`.

## Stores

| where | address | size |
|---|---|---|
| `stvx128` x8 | `d + {0,16,32,48,64,80,96,112}`, d = dst + 128k | 16 each |
| `stfs` x4 | `d + {0,4,8,12}`, d = dst + 16k | 4 each |
| `stfsu` | `dp + 4`, walking to `dst_end` | 4 each |

No `dcbzl` here (unlike `sub_82B3BED8`) -- it accumulates, so it cannot zero the line first. The
`__savegprlr_29` spill of r29-r31 plus lr is the function's own frame: not reproduced, not
windowed. `__restgprlr_29` restores r29-r31 on both returns, so no preserved register changes.
Every clobbered vector register is v0-v13, all volatile, so the result mask is `kReturnNone` and
the memory window is the whole comparison.

## Window

`[r3, r3 + count*4)` on both paths. The fast path's end pointer is `rlwinm r10,r6,2,0,27` here,
where `sub_82B3BED8` uses `srawi` then `rlwinm` -- same value for a positive multiple of 64, but
it is computed each way as the original does rather than shared. Reads: `[r4, r4 + count*4)`, and
`[r3, r3 + count*4)` as well, declared because the accumulator is read before it is written and a
replayed vector needs its prior contents.

`Windows()` returns **false** on one predictable class: the vector path with a span that is zero
or not a multiple of 128 -- `count == 0`, a negative count, or `count*4` overflowing 32 bits. The
lifted loop compares `(r10 - 32) != r30` with a 128-byte stride, so none of those terminate; the
original **hangs**, and the native body reproduces the hang rather than guarding it. Also false if
`dst + len` would wrap the address space. The scalar path returns immediately on a zero or
negative count (`cmplw r11,r9 ; bge`), declared as a zero-length write set. None of these fired in
s19 (`skipped=0`).

## Limits of the green

- **The scalar path is unexercised.** Every logged entry point is 128-byte aligned with
  `count = 256`, so the 2.08M clean comparisons are almost certainly all vector path. The scalar
  path is verified only by a bounds/addressing cross-check: a Python model of the lifted register
  machine against a model of this port over 111 cases -- six alignment combinations, 18 counts
  including 1/3/7/17/63/65/127, and three overlapping src/dst layouts -- agreeing on both the
  written bytes and the written address set. That checks addresses, loop counts and store order,
  not float rounding.
- The scale broadcast is `simde_mm_set1_ps(float(f1))` rather than four `stfs` to `-48(r1)`
  followed by `lvx128 v0,r0,r9`. Those agree only if the guest r1 is 16-byte aligned, because
  `lvx128` masks the low four address bits. Measured on the real entries: `r1 = 0x707BFB20`, low
  four bits clear -- observed, not just argued from the ABI.
- `vmaddfp` is `simde_mm_fmadd_ps` (single rounding) and `fmadds` is `double(float(std::fma(...)))`;
  neither is ever written `a * b + c`. The scale is the **first** operand of every `vmaddfp` and
  the source the first of every `fmadds`, exactly as lifted, per `vmx128-exactness.md` rule 4:
  with two NaN operands the winning slot is part of the semantics.
- If a caller ever placed the destination buffer inside this callee's own red zone, the
  `__savegprlr_29` spill would land inside the declared window and the native body (which does not
  spill) would differ. Not plausible; recorded because it would present as a memory diff with no
  arithmetic explanation.
