# sub_82B399D0

Leaf VMX128 kernel, 901 lifted lines, 98 vector instructions, **141,594 calls** in the session
that verified it (182,370 in the reference boot) on `RwAudioCore Dac`. No callees, no imports, no
indirect calls, no timebase, no locks — gate 1 passes trivially. The only caller is
`sub_82B39FA0`, whose port already names the arguments; this note uses the same names.

**Role.** One filter stage over `count` singles, three things at once:

    mixed[k] = addend[k] - f2 * source[k + 1]          vector, four groups at a time
    mixed[k] = mixed[k] - f1 * mixed[k - 1]            scalar, sequential, in place
    copy[k] += f4 * (f3 * source[k] + source[k + 1])   vector, the accumulate bus

`f5` is the recursion's `y[-1]` and the returned `f1` is `mixed[count-1]`, which
`sub_82B39FA0` latches back into its gain block `+ 32` as the next call's state. `source` is read
at both `k` and `k+1`, so it holds `count+1` singles and every read of it is an unaligned window:
the census shows `r10` ending in 0x388/0x3C0/0x3C8, and the kernel handles that by rebuilding a
32-byte table of byte indices 0x00..0x1F in .data (`0x830D1524`, from `lis -31987` + 5412) and
indexing it by `source & 0xC` into two `vperm128` controls — the compiler's inline `lvsl`.

Arguments: `r3` count (0x100 in every logged call), `r9` addend, `r10` source, `f1` pole, `f2`
feed, `f3`/`f4` the bus coefficients, `f5` the entry state, plus three outgoing stack slots of the
caller's frame — `84(r1)` mixed (descriptor + 16), `92(r1)` copy (descriptor + 20), `100(r1)` a
flag. `r4`-`r8` are passed and never read. Nothing here is named in `docs/rw_audio_structs.h`.

Shape: one block of 16 singles is prepared, then `ceil(blocks/4)` iterations each filter the
previous block and prepare the next (software-pipelined one block behind), then a tail block.
`blocks = count/4 - 4`, truncating toward zero (`srawi`+`addze`), so with `count = 256` that is
60 blocks, 15 iterations, and exactly 256 singles written.

## Stores

| where | address | size |
|---|---|---|
| `stw` x8 | `0x830D1524 + {0,4,..,28}` | 4 each |
| `dcbzl` | `(copy & ~127) + 128i`, `i < ceil(count*4/128)` | 128 each, flag == 0 only |
| `stvx128` x4 | `(mixed & ~0xF) + {0,16,32,48}` | 16 each, first block |
| `stfs` x16 | `mixed + 64i + 4k`, `i < iters` | 4 each |
| `stvx128` x4 | `(mixed & ~0xF) + 64(i+1) + 16g` | 16 each |
| `stvx128` x4 | `(copy & ~0xF) + 64i + 16g` | 16 each |
| `stfs`/`stfsx` x16 | `mixed + 16*blocks + 4k` | 4 each, tail |
| `stvx128` x4 | `(copy & ~0xF) + 16*blocks + 16g` | 16 each, tail |

Plus 3 `stfd`, 12 `stfs` and 8 `stw` to `-116..-176(r1)`: this function's own frame (no `stwu`;
`__savegprlr_22` puts the register saves at `-8..-88`). Not windowed, per the brief, and not
reproduced — the three splats and the two `vperm128` controls are built as registers, which is
exact because `stw`/`stfs` write big-endian and `lvx128` reverses all sixteen bytes, so the word
stored lowest lands in host lane 3 (`sub_82B3C098`'s verified precedent). It also assumes the
guest `r1` is 16-byte aligned, which the lifted `lvx128` masking relies on too: measured
`r1 = 0x707BF800` on all four census entries.

## Window

Three spans, all from entry state: the 32-byte table at its fixed address, one span over `mixed`
and one over `copy`. Both buffer spans take the union of the shapes above, which is why they are
computed rather than written down: `dcbzl` starts at the **128-byte floor** of `copy`, the `stfs`
runs are unmasked while every `stvx128` is masked to 16, and the tail block sits at
`16*blocks`, which for `count < 16` is *below* the buffer. With the 16-byte-aligned buffers and
`count = 256` the census logs, both collapse to exactly 1024 bytes: 2080 bytes in total against
the 32 KB budget. Reads declared: the table, the three argument slots, both buffers (both are
read before they are written) and `64*(iters+1)` bytes of `addend`, plus 16 more of `source` for
the one-past window.

`Windows()` returns **false** on two predictable classes, both from entry state: `count < 16`,
where `mixed + 16*blocks` walks off the bottom of the map, and a `count*4` so large that the
`dcbzl` establish would wrap the address space. Neither fired — `skipped=0` over 141,462 calls.

## Gates

All four pass. Gate 1: leaf. Gate 2: enumerable — the 56 gate-2 suspects in the census are the
loop cursors and inter-buffer deltas the body builds (`r5 = mixed - source - 16` and the like),
not independent bases; every one resolves to a fixed offset from an entry pointer times an index
derived from `r3`. Gate 3: no `mftb`. Gate 4: the result is memory plus `f1`.

**STATUS `verified`: zero divergence over 141,462 comparisons** in session s23
(`probe/harness/out/s23.log`, 2026-09-12 03:58–04:00):
`runs=141462 diverged: registers=0 memory=0 skipped=0 overflow=0`.

Result mask `kReturnF1`. The caller reads nothing else — `port_82B39FA0` shows `stfs f1,32(r31)`
as the only use of the return — and `r3` is left as scratch (`count/4 - 1`), so it is deliberately
not compared. The free extra signal is that **seven preserved VRs are clobbered without being
saved**: v25–v31 are in the range the harness compares unconditionally and this kernel has no
`__savevmx_*`, so the last block's `mix[0]`, `sum[3]`, `mix[3]`, `mix[2]`, the `addend` line and
the two `+4` windows are all compared on every call. v29 is the exception: it is untouched when
the loop never runs, so the port writes it only when `iters != 0`.

## Unsure

- **Rule 4 of `docs/vmx128-exactness.md`** applies to 32 `vmaddfp`/`vnmsubfp` sites and 32
  `fnmsubs`. Operand order is copied from the lifted lines (the splat is always the first operand
  of a `vnmsubfp`, the window always the first of a `vmaddfp`), which is the best that can be done
  from source. A divergence that appears on only some calls should be checked for a NaN in
  `addend`/`source` first.
- **Two hoists.** The 16 `lfs` of each scalar block are loaded up front, where the original
  interleaves the last five with the first two stores; and in the tail block all 16 precede all
  16 stores. Both are exact because no single in either run is read after it is written and the
  addresses involved cannot alias — checked store by store, not assumed. Everything else keeps
  the lifted order, including the `stfs` of the second single before the first, the
  `+112/+64/+96/+80` store order into `mixed`, and the reload of the recursion state from memory
  (`lfsu`) rather than carrying it in a register.
- **The `dcbt` loops are elided.** The `flag != 0` path (`loc_82B39A2C`) is four `dcbt` and a
  counted loop of four more, and the `dcbzl` loop carries three more: prefetch hints with no
  state. The `dcbzl` itself is reproduced as a 128-byte `memset`.
- `count` is 256 on every logged entry and `blocks` is therefore a multiple of 4, which makes the
  loop and the tail block tile `mixed` exactly. If `blocks` were ever not a multiple of 4 the
  loop would overshoot and the tail would re-filter bytes the loop already wrote — the original
  does the same, and the window covers the union either way, but no such call has been observed.
