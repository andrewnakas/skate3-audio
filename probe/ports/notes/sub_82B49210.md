# sub_82B49210

Twenty-seven lifted lines, twenty-three of them frame. Body: `lwz r3,4(r3)`,
`bl 0x82b49280`, `li r3,8`. Structurally identical to `sub_82B33210` and `sub_82B49238` --
same three instructions, same `+4` indirection, same constant 8 -- over a different callee, so
the three are almost certainly slots of one dispatch table, with 8 as its shared return
convention (status or record size; not pinned down).

Arguments: r3 = a record whose second word (`+4`) is the object. r4 is not set up, unlike its
sibling `sub_82B49238`, so `sub_82B49280` is a one-argument call.

Stores: none outside its own frame.

What the callee does, for context: `sub_82B49280` reads a used count at `owner+280` and a
capacity at `owner+282` (owner = `object+16`); when the array is full it asks the allocator
held at `owner+36` for a larger block through its vtable (`lwz r9,4(r10)` then `bctrl`), copies
the old contents with `sub_82EDF460`, releases the old block through a second vtable slot
(`lwz r8,12(r9)` then `bctrl`), publishes the new pointer at `owner+108` and the new capacity
at `owner+282`; then it walks the array comparing the priority byte at `+73` of each entry
against the new one's and inserts in order. So: grow-and-priority-insert into a handle list.

Gate verdict: **gate 1**, at depth 1, `sub_82B49280`. Both `bctrl` calls go through the
allocator's vtable, and one of them frees the previous block. Replaying the native body on
rewound memory would allocate a second block and free the same pointer twice -- the canonical
non-replayable effect. `docs/shadow-harness.md` names these two indirect calls as the reason
transitive screening exists. The calls are conditional on the array being full, so on a
non-full call the callee only walks and inserts; but the walk's stores are still not enumerable
(see below), and the port's status has to describe the function, not the lucky path.

Write set that would have been declared if it were comparable: not enumerable, which makes this
gate 2 as well one level down. With `object = REX_LOAD_U32(r3 + 4)` and
`owner = REX_LOAD_U32(object + 16)` the entry-state-visible part is `{owner + 108, 4}`,
`{owner + 282, 2}`, `{object + 71, 1}`, `{object + 76, 4}`, `{object + 28, 8}` (the two words
at +28 and +32). The rest are stores through pointers the call itself produces: `{r9 + r30, 4}`
(the `stwx` into the freshly allocated array at the insertion index), `{r6 + 4, 4}`,
`{r11 + 272, 4}`, `{r11 + 280, 2}`, `{r9 + 4, 4}` and `{r10 + 16, 4}`, whose bases are all
reloaded after the allocation. Result mask: r3, the literal 8.

Reached only indirectly -- no `bl 0x82b49210` in the generated corpus -- at 2,210 calls per
boot.
