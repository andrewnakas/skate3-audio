# sub_82B32480

- Role: `void f(record*)` — retire finished entries of the **20-slot, 16-byte ring embedded at
  `record+100`**, read cursor `u8[record+475]`. While `u8[entry+13] == 2` (exactly 2): clear that
  state byte; if `u32[entry+0]` (the buffer) is nonzero, subtract `u32[buffer+4]` from
  `u32[u32[record+96] + u8[entry+14]*80 + 24]`, then — only when `u32[entry+4]` is nonzero **and**
  `u8[record+477]` is zero — call `sub_82EC1378(u32[entry+4], u32[entry+0])`, and null
  `u32[entry+0]`; then advance the cursor, wrapping to 0 at 20. 119 lifted lines, one direct
  callee, no own indirect call, no timebase, no lock of its own. **205,361 boot calls** on
  `RwAudioCore Dac` (tier D) — the hottest function in this batch.
- Argument: r3 = the record. No other entry register is read. Note the `subfe r8,r9,r9` at
  `loc_82B3250C` reads **r9 uninitialised** on the path where the entry's buffer was null (and on
  the first iteration, where r9 is the caller's volatile); `~r9 + r9` is all ones whatever r9
  holds, so the result cannot depend on it. That is why the compiler was free to emit it, and the
  port reproduces the *meaning* (`next == 20 ? 0 : next`) rather than the register dependence.
- This is the same record as `port_82B32870` and `sub_82B32328`: `+477` is the flag
  `sub_82B32328` raises (`stb r8,477(r3)`, r8 = 1) for the duration of its flush and clears at the
  end, and `+475` is one of the bytes it zeroes. So `+477` set means "we are tearing down, do not
  hand buffers back to the owner" — the accounting still happens, only the release call is
  skipped. Two independent functions agree on both bytes.
- Stores (3 per iteration at most, plus this call's own frame):
  - `stb r29,13(r31)` — `u8[entry+13] = 0`, 1 byte, every iteration
  - `stw r5,24(r11)` — `u32[budget slot + 24] -= u32[buffer+4]`, 4 bytes, only when the buffer is
    nonzero; a 64-bit subtract truncated at the store, allowed to go negative
  - `stw r29,0(r31)` — `u32[entry+0] = 0`, 4 bytes, only when the buffer was nonzero
  - `stb r7,475(r30)` — the new read cursor, 1 byte, every iteration
  - the `stwu` back chain is this call's own frame; never windowed.
  `u8[record+475]` is **reloaded** at the bottom of every iteration rather than carried in a
  register, so the release call is free to have moved it; reproduced as a reload. `u32[entry+0]`
  is likewise reloaded for the call's r4 instead of reusing r8.
- Result: **none** honestly — no `li r3,...` on any path, so r3 is `record` until a release runs
  and `sub_82EC1378`'s result afterwards. The macro line carries `kReturnR3` because a
  gate-labelled port with a false `Windows()` and `kReturnNone` trips lint check 5; the mask is
  never read for a gate label. A comparable version would declare `kReturnNone`.
- Gate 1 **fails** at depth 1: `sub_82EC1378` reaches
  **RtlEnterCriticalSection / RtlLeaveCriticalSection** (census `reason: import:...`, `depth: 1`),
  from the `bl 0x82ec1378` at 0x82B32504. A lock cannot be replayed on rewound memory, and the
  closure below it is 176 functions wide (the whole heap), so this is not a near miss. The call is
  conditional — `owner != 0 && u8[record+477] == 0` — and both inputs are readable before the
  call, but the *number* of iterations is not (each iteration's entry state is only known after
  the previous one's release ran), so a partial `Windows()` cannot be predicated on it either.
- The write set I WOULD have declared: per iteration `spec.write(entry + 13, 1)`,
  `spec.write(entry + 0, 4)`, `spec.write(record + 475, 1)` and
  `spec.write(u32[record+96] + class*80 + 24, 4)` — that is at most 4 spans per iteration and the
  ring is 20 slots, so a full drain is 80 spans against a 32-span cap: it would also have to
  return false on **budget** (gate 2's second clause) for any drain longer than eight entries,
  even without the lock. Reads `{record+96, 4}`, `{record+475, 1}`, `{record+477, 1}`,
  `{entry, 16}` per iteration, `{buffer+4, 4}`.
- Unsure: the meaning of the 80-byte budget records at `u32[record+96]` and of `u8[entry+14]` as
  their index — the stride math (`class*5*16`) is certain, the naming is not. `u32[slot+24]`
  going *down* by the buffer's byte count reads like an outstanding-bytes counter, but only this
  one function was read. `sub_82EC1378` is characterised only by its census entry (heap, takes a
  lock); its body is not in this tree, so "release the buffer" is inference from the call shape
  `(owner, buffer)`.
