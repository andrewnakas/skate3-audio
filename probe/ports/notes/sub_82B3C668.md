# sub_82B3C668

Leaf, 292 lines, no callees, no imports, no timebase, no locks. 2,012 calls per boot session on
`RwAudioCore Dac`. One caller only (`skate3_recomp.67.cpp:56150`, inside sub_82B34BD0's TU
neighbour): `mr r3,r29 ; addi r4,r31,64 ; lbz r5,42(r31) ; bl`, and immediately after the call it
stores 0 to `r31+98` (the flag that gated the call) and reloads everything else from r31. No caller
reads r3, f1 or any volatile register: mask `kReturnNone`. r3/r4/r5 are never written by the body,
so they match anyway.

Arguments: r3 = row-owner object, r4 = array of `count` singles ("deltas"), r5 = count (a u8 at the
call site, `r31+42`, so 0..255; the port handles any r5). Object fields, nothing in
`docs/rw_audio_structs.h` names them: `rw_ptr` row base at +4, `u16` row pitch in SINGLES at +14.
The same two fields drive the memset loop just above the call site, which clears 1024 bytes per row
(`li r5,1024 ; bl sub_82EE5E80`), so at the live call site pitch is 1024 bytes and the rows are
disjoint 1 KB channel buffers.

Behaviour, per iteration i of count: `row = u32[+4] + ((u16[+14] * i) << 2)`, then for k = 0..15
`row[k] = fmadds(delta[i], tap[k], row[k])`, then `delta[i] = 0.0f`. So only the first 64 bytes of
each row are touched. The taps are sixteen consecutive pool singles at `0x822F8A04` (= kPool 0x822F8600
+ 1028; f30 is +1028 ascending to f0 at +1088) and the fill is the 0.0f cell at `0x82165A10`; both are
hoisted out of the loop by the original, as here. Values are not assumed — the body loads them.

Stores, in order, 17 per iteration: `row+0,4,...,60` (16x stfs, 4 bytes each) then `4(r10)`
(stfsu, 4 bytes, the delta just consumed). Reloads kept: +14 and +4 every iteration, and the delta
before every one of the sixteen fmadds. Two harmless reorderings: the original loads `row[k+1]`
before storing `row[k]` for k = 12..15, and loads the delta before the accumulator at k = 0 and
after it at k >= 1 — in every case both are pure loads at provably distinct addresses with no
intervening store, so the k-loop's fixed order is the same computation.

Window: the delta array is one span `{r4, 4*count}`. The rows are one span per row when the byte
pitch exceeds 64 (the live case), so it is enumerable only while `count + 1 <= 32`; when the pitch is
0 or <= 64 the rows coincide/abut and one merged span covers them, capped by the 32 KB budget
(`count <= ~481`). Returns false, per path, on: `count + 1 > 32` spans, > 32 KB, an address that
wraps 2^32, index math that wrapped (the monotone union guard), and — the real gate-2 risk — a write
span that covers object+4..7 or object+14..15, since both are re-read inside the loop and would then
change mid-call. Reads: those two fields, the 64-byte tap table, the 0.0f cell.

Gates: 1 pass (leaf), 2 pass **conditionally** — the census flagged all 17 stores `gate2_suspect`
because every store base is loop-derived, but the bases derive only from two entry-readable fields
plus the loop index; the checks above are what make that honest, and the span cap is the live
constraint. 3 pass (no timebase). 4 pass (17 stores per iteration).

Unsure: (a) the expected `count` at run time — it is `u8[r31+42]`, presumably the channel count, and
if it ever exceeds 31 with a 1 KB pitch the port skips rather than compares, which will show up as
`PortSkip "not enumerable"` in the census rather than as coverage; (b) the meaning of the 16 taps is
unread — "a ramp/curve applied to the head of each row" is a reading of the arithmetic, not
established, so the role line stays descriptive.
