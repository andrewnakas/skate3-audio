# sub_82B22228

- Role: `void f(obj*)` — a per-tick top-up check. Three steps: (1) clamp `f32[obj+72]` **up** to
  `f32[obj+52]`; (2) compare `f32[obj+68]` against the global float at **0x822F87CC** and, when
  they differ, copy the global into `+68` and clear `u32[obj+64]`; (3) compute
  `round(f32[obj+72] * f32[obj+68])` — half away from zero, then `fctiwz` — and if
  `s32[obj+112]` is **less** than that, call `sub_82B3D668(obj + 100)`. 115 lifted lines, one
  direct callee, no own indirect call, no imports, no timebase, no lock. **184,376 boot calls** on
  `RwAudioCore Dac` (tier D) — one of the hottest scalar functions in the corpus.
- Argument: r3 = the object. No other entry register is read.
- Constants, all computed as `((lis_imm & 0xFFFF) << 16) + offset`:
  - `0x822F87CC` = `lis r11,-32208` (0x82300000) + `addi -31232` (0x822F8600) + 460. The
    `lis`/`addi` split says data, not a literal pool, so this is a mutable global — which is why
    the code re-checks it every tick instead of folding it. **Its value was not read**: there is
    no decrypted image on this tree, so whether it is a sample rate, a frame rate or something
    else is unknown.
  - `0x82165A10` (the zero cell) and `0x8209975C` (0.5, the rounding bias) are the *same two*
    cells `port_82B217F0` reached by the same `lis`/`lfs` pairs — an independent corroboration of
    both addresses.
- Stores (3 to the object, 2 to this call's own frame):
  - `stfs f0,72(r3)` — `f32[obj+72] = f32[obj+52]`, 4 bytes, only when `+72 < +52`
  - `stfs f0,68(r3)` — `f32[obj+68] = [0x822F87CC]`, 4 bytes, only when they differ
  - `stw r11,64(r3)` — `u32[obj+64] = 0`, 4 bytes, same condition as the line above
  - `stfd f13,80(r1)` (twice, one per rounding path) and the `stwu` back chain are this call's
    own frame; never windowed. The doubleword spill and the `lwz r4,84(r1)` that reads its low
    word back are reproduced verbatim — that pair *is* how the int reaches a GPR.
  `+68` and `+72` are both reloaded at `loc_82B2226C` after the two conditional stores, so
  neither load may be hoisted above them.
- Float exactness: `fmuls`/`fadds`/`fsubs` are single-precision round trips (`double(float(...))`);
  `fcmpu` + `bge` means a NaN span stores nothing, and `fcmpu` + `beq` means a NaN on either side
  of the rate check takes the refresh path. `disableFlushModeUnconditional()` sits at four points
  — before the first `lfs`, at `loc_82B22248`, at `loc_82B2226C`, and inside the `fsubs` arm
  (which is a branch target); the `fadds` arm has none, because it falls through.
- Result: **none** honestly — there is no `li r3,...` on any path, so r3 is `obj` when the call is
  skipped and `sub_82B3D668`'s return value when it is not. The macro line carries `kReturnR3`
  because a gate-labelled port with a false `Windows()` and `kReturnNone` trips lint check 5; the
  mask is never read, since the macro does not arm the shadow branch for a gate label. A
  comparable version would declare `kReturnNone` plus the write set above.
- Gate 1 **fails** at depth 1: `sub_82B3D668` reaches the core allocator through two `bctrl`s —
  `u32[u32[u32[0x8307762C] + 36] + 0]` (its `lwz r11,30252(r20)` is the cell `port_82B3C930`
  names `kCoreOwnerPtr`) slot **+4** (allocate) at 0x82B3D6F8 and slot **+12**
  (free) at 0x82B3D838, the same `owner+36 -> vtable` chain `port_82B3C930` and `port_82B32870`
  hit. Allocation cannot be replayed on rewound memory. The call is conditional, so a partial
  `Windows()` returning true only when `s32[obj+112] >= needed` would be *possible* — every input
  to that predicate is readable before the call — but it would compare only the no-op path, so it
  was not written. That is the honest reason this one stays gate 1 rather than being split.
- The write set I WOULD have declared: `spec.write(obj + 64, 12)` (the `+64`/`+68`/`+72` triple,
  all three conditional but contiguous and cheap to over-declare), and on the call path the whole
  of `sub_82B3D668`'s write set, which includes allocator-internal memory and is the blocker;
  reads `{obj+52, 4}`, `{obj+64, 12}`, `{obj+112, 4}`, `{0x822F87CC, 4}`, `{0x82165A10, 4}`,
  `{0x8209975C, 4}`.
- Unsure: what the three floats mean. `+52` as a floor for `+72` and a `+72 * +68` product
  compared against an integer count reads like *seconds × rate = samples wanted*, and `+64` looks
  like an accumulator reset when the rate changes, but nothing outside this function supports that
  and `0x822F87CC` was never read. `+100` is a subobject, not a pointer field — the call site is
  `addi r3,r3,100`.
