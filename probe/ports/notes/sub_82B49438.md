# sub_82B49438

- Role: **remove** this object from its owner's handle array — the exact counterpart of
  `sub_82B49280`'s grow-and-priority-insert. `u32 f(object*)`: linear-search the array for the
  entry whose first word is the object, decrement the owner's halfword count, and `memmove` the
  tail down over the hole. Returns 1 when it removed something, 0 when the object was not there.
  90 lifted lines, one direct callee, no imports, no indirect call, no lock, no timebase.
  3,094 boot calls on `RwAudioCore Dac`.
- Arguments: r3 = the object. Structures are `sub_82B49280`'s, same names: `owner =
  u32[object+16]` (reloaded before nearly every access), `owner+108` the entry array, `owner+280`
  u16 count, an entry 8 bytes `{u32 object, u32 payload}`. The slot is **not** cleared; only the
  count shrinks and the tail slides.
- Flow. `count = u16[owner+280]`, tested with a **signed** `cmpwi` on the zero-extended halfword,
  so only zero skips the search. The search walks `u32[array + 8k]` for `k` in `[0, count)`; a miss
  falls through to `li r3,0` with no store. On a hit at index `k`:
  `offset = rlwinm(k,3,0,28)`; `used = u16[owner+280]` (reloaded); `sth (used + 0x10000) - 1` back
  — the `addis`/`addi` pair is just `used-1` once the halfword store drops the carry; then
  `owner` is reloaded a **third** time, `array = u32[owner+108]`, `remaining = u16[owner+280]`
  (the value just stored), `tail = remaining - k` as a **64-bit** `subf`, and
  `sub_82F4DC60(array+offset, array+offset+8, rlwinm(tail,3,0,28))`. Returns 1.
- Stores: `u16[owner+280]` (2 B) and the memmove's `[array + 8k, array + 8k + 8*(count-1-k))`.
  The `stw r12,-8(r1)` is this call's own LR spill; the `stwu r1,-96(r1)` **is** reproduced,
  because `sub_82F4DC60`'s forward case tail-calls the memcpy leaf `sub_82F52B30`, which spills r3
  at `-8` off the caller's r1 — without the frame move that spill lands on this function's own.
- `sub_82F4DC60` through `GuestCall`. Read through: it returns immediately when `dst == src`,
  branches to `sub_82F52B30` (memcpy) when `dst < src`, and otherwise copies backwards byte and
  word at a time. Every store is `stb`/`stw`/`stwu` inside `[dst, dst+n)`. Here `dst < src` always
  (`src = dst+8`), so the memcpy branch is the one taken. Neither routine allocates, locks,
  signals or calls indirectly; the closure leaves the audio corpus only into those two CRT leaves.
- Window rationale: two spans, both from entry state. The count, the array base and every entry
  word are read before the single store, and the search reads nothing the call has written, so the
  index — and therefore the memmove's destination and length — is entry state. The new count used
  for the length is the halfword this call itself stores, i.e. `(count-1) & 0xFFFF`. Returns false
  when the object or the owner is null, when the array is null with a non-zero count, when the
  count exceeds 1024 (a bound that keeps the search loop visibly finite and the read span under
  8 KB), when the halfword at `owner+280` would overlap the `object+16` pointer that is reloaded
  after it, and when the memmove span would wrap 2^32. Worst case: 2 spans, 8 KB.
- Result mask `kReturnR3`: both returns are literals and `sub_82B49280`'s note records that the
  callers of its sibling do read the result.
- Unsure: nothing was checked about whether the `owner+272` high-water mark that `sub_82B49280`
  maintains is ever walked back down — this function does not touch it, which is reproduced, not
  judged. The signed `cmpwi` on a zero-extended u16 can never be negative, so the `ble` and a
  `beq` would behave identically here; the port keeps the signed form anyway.
- Gate verdict: none fire — the callee is a pure copy leaf, the write set is enumerable from entry
  state, no timebase, r3 observable. STATUS pending: written, never compared.
