# sub_82B50100

Non-leaf, 214 lifted lines, 4,250 boot calls, `RwAudioCore Dac`. Census gate-1 verdict: pass,
closure of 2 (`82B4F5F8`, `82B50270`), no imports, no indirect call, no lock, no timebase. Both
callees are already ported and **verified**: `recomp/src/audio_ports/sub_82B4F5F8.inc` (one unsigned
varint, one `stw` at its r4) and `recomp/src/audio_ports/sub_82B50270.inc` (advance a bit cursor,
`stw` at its r4 and, on the page wrap, at its r3). A change to either of those window sets requires
a change here.

Arguments: r3 = the cursor record to fill in, r4 = a substream index, r5 = the stream descriptor,
r6 = the chunk. Sole call site `skate3_recomp.68.cpp:55318`, which does `add r28,r3,r28` on the
result — r3 is the chunk's byte length and the caller uses it to step to the next chunk. Mask
`kReturnR3`.

Layouts, all plain offsets (nothing in `docs/rw_audio_structs.h` names them):

- cursor (r3): `+4` the 2048-byte packet the target frame starts in, `+8` bytes from that packet to
  the end of the chunk minus 4, `+20` the bit offset inside the packet (or `-1`).
- descriptor (r5): `+4` seek-table base (0 = no table), `+8` the sample position, `+20` a flag byte.
- chunk (r6): `+0` the packed length field — `r25 = u32[r6] >> 2` is the byte length and is the
  return value, so the **two low bits are the per-stream flag `CLAUDE.md` lists as unexplained**;
  `+4` the first packet.

Behaviour. `frames = (u32[r5+8] + (u8[r5+20] ? 0 : 384)) / 512`, a signed divide truncating toward
zero (`srawi 9` + `addze`). The four bytes at `r6+4..7` are stored into the frame cell at `r1+80`
and read back as one big-endian word; `(word >>a 11) & 0x7FFF` is the initial bit position, poisoned
to `-1` at or past 16352 (the page's bit count). With a seek table, `r30 = table + u32[table + 4*r4]`
starts a varint reader: `sub_82B4F5F8` yields the frame count of each packet, and the walk advances
the packet pointer by 2048 and accumulates counts until `frames < counted + consumed`; the settled
packet's own four header bytes then give the bit position the same way. Finally
`sub_82B50270(&cell88, &cell80)` runs once per frame still ahead of the target, and the three cursor
words are published.

Stores outside the frame: exactly `u32[r3+4]`, `u32[r3+20]`, `u32[r3+8]`, in that order (4 bytes
each). Everything else this function writes is `r1+80..83` and `r1+88`, and both callees write only
through those two pointers.

The `stwu r1,-160(r1)` **is** reproduced (most ports skip their own frame): the +80 and +88 cells
are handed to the callees as pointers, so they must be real guest memory, and `sub_82B50270` spills
r28-r31 below whatever r1 holds when it is entered. r25-r31 are never touched, so `__savegprlr_25`
has nothing to reproduce and `__restgprlr_25`'s exit values are the entry values by construction.
Both cells are fully initialised before they are read, so the replay never sees the original run's
leftovers in them.

Window: two spans, 12 bytes, both at fixed offsets from the entry r3. The walk's trip count is not
bounded from entry state and does not need to be — it cannot move a written byte. Returns false only
when r3, r5 or r6 is null, where the original would store or load through the image base.

64-bit care taken, per the session's rules: `add r30,r10,r11` (seek-table entry + table base),
`add r30,r3,r30` (the varint length), `add r31,r11,r31` and `add r10,r11,r31` are all 64-bit on
zero-extended words and are kept as `uint64_t`; the compares against them are `cmpw`, i.e. signed on
the low 32 bits, and are written that way. `subf r11,r29,r27` and `addi r9,r11,-4` are 64-bit but
only their low 32 bits are stored. `addi r11,r11,384` is applied to the low 32 bits, so a carry out
of bit 31 is discarded before the divide, as the original's later `.s32` accesses do.

Gates: 1 pass (both callees verified, neither allocates, locks or calls indirectly), 2 pass (a fixed
three-word write set), 3 pass, 4 pass (r3 is read by the only call site). STATUS pending: written,
never compared.

Unsure of: nothing in the body. The read set is deliberately a **summary** — the varint walk
consumes one to five bytes per packet with no bound available before the call, so `Windows()`
records 256 bytes from the reader's start and at most 32 KB of the chunk. Reads are never compared,
so this only weakens an offline replay, never the comparison. The `+20` flag byte's meaning (why a
clear flag adds 384 samples before the divide) was not traced.
