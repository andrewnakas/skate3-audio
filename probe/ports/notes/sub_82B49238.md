# sub_82B49238

Twenty-nine lifted lines, twenty-four of them frame. Body: `li r4,0`, `lwz r3,4(r3)`,
`bl 0x82b48f28`, `li r3,8`. The third member of the family with `sub_82B33210` and
`sub_82B49210`: same `+4` indirection, same constant 8, one extra instruction because this
callee takes a flag.

Arguments: r3 = a record whose second word (`+4`) is the object; r4 = the literal 0. In
`sub_82B48F28` that flag is tested as `clrlwi r11,r28,24` (its low byte) and, when zero, the
whole unlink-and-splice half of the function runs; a non-zero flag skips straight to the tail.
So this table entry always takes the long path.

The lifted order is `li r4,0` before `lwz r3,4(r3)`; the port loads first and lets `GuestCall`
set both argument registers, which is equivalent -- neither instruction touches memory and the
load's base is the entry r3.

Stores: none outside its own frame.

What the callee does, for context: `sub_82B48F28` walks the child pointer array at `object+80`
for the count at `object+68`, calling two vtable slots per non-null child (`lwz r10,0(r11)` then
`bctrl`, and `lwz r8,12(r9)` then `bctrl` -- the same acquire/release slot pair
`sub_82B49280` uses); then, with the flag clear, it unlinks the node embedded at `object+28`
from whichever of the owner's two list heads (`owner+20` or `owner+28`, owner = `object+16`)
the type byte at `object+71` selects, splices the neighbours' `next`/`prev`, calls
`sub_82B49438`, and on its result takes a further branch. So: release the children and remove
the object from its owner's list.

Gate verdict: **gate 1**, at depth 1, `sub_82B48F28`, three `bctrl` calls. Two of them are the
per-child release pair, so replaying the body on rewound memory would release every child a
second time. Nothing about the flag or the entry state avoids them -- they are inside the
`object+68`-bounded loop, which runs whenever the object has children.

Write set that would have been declared if it were comparable: not enumerable, so gate 2 one
level down as well. Every one of `sub_82B48F28`'s nine non-frame stores has a derived base --
`{r9 + 16, 4}`, `{r9 + 20, 4}`, `{r9 + 24, 4}`, `{r9 + 28, 4}`, `{r9 + 32, 4}` (the owner's
list heads, with r9 = `REX_LOAD_U32(object + 16)`, that one being recoverable from entry state)
and `{r10 + 0, 4}` / `{r10 + 4, 4}` twice over, where r10 is the neighbour node reached through
the embedded links at `object+28` and `object+32`. Those two are one indirection past entry
state, and the loop over the children is the part that cannot be closed at all: the vtable
calls write whatever each child's implementation writes. Result mask: r3, the literal 8.
