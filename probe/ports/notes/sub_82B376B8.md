# sub_82B376B8

Non-leaf, 171 lines, 23 calls in the boot session (29 in the newer census), `RwAudioCore Dac`.
**Passes all four gates; STATUS pending.** The window set is only enumerable because both callees
are already verified ports whose `Windows()` could be mirrored -- see below.

Args: r3 = the meter object, r4 = a descriptor. Returns 1 in r3 on every path, so `kReturnR3`.
The object is the **same one** `sub_82B373C8` and `sub_82B370E8` take, and every field name in the
port file is copied from `sub_82B373C8.inc` / `sub_82B370E8.inc` for the same cell: `+42`
channels (which `sub_82B370E8` reads as its layout byte), `+240/272/304/336` the four per-channel
meter arrays, `+376` ring length in blocks, `+384`/`+386` the u16 byte offsets of the level and
peak rings, `+388` the ring cursor. New here: `+368` the rate the rings were last built for,
`+372` the history length, `+380` the tick interval, `+390` the tick counter.

Body:

1. `lhz +390` vs `lwz +380`, **signed** on the zero-extended u16: below it, `+390 += 1`, return 1,
   nothing else. That is the common case -- the meters run once per interval.
2. Otherwise compare the cached rate `+368` against `[r4+40]+12`. `fcmpu`/`beq`, so a NaN rate is
   "not equal" and rebuilds every tick.
3. On a change: `+368 = [r4+40]+12`; `+376 = fctiwz(rate * P[2156] * [+372] + 0.5)` (low word of
   the spill), forced to 1 when not positive; the ring byte count is
   `((fctidz([+372] * P[444] + 0.5) * [+42]) << 2) & ~3`, falling back to `([+42] << 2) & ~3` when
   that is zero; `memset(obj + [+384], 0, n)`, `memset(obj + [+386], 0, n)`, `+388 = 0`.
4. Always: `+390 = 1`, then `sub_82B373C8(obj, [r4+28])` and `sub_82B370E8(...)`, then `r3 = 1`.

Constants, computed not eyeballed: `lis r11,-32208 ; addi r11,r11,-31232` =
`((-32208 & 0xFFFF) << 16) - 31232` = **0x822F8600**, the pool `sub_82B2FE00.inc` names `kPool`;
the two words read off it are pool+2156 = **0x822F8E6C** and pool+444 = **0x822F87BC**.
`lis r9,-32246 ; lfs -26788(r9)` = `0x820A0000 - 0x68A4` = **0x8209975C**, which four other ports
read out of the validated image dump as **0.5f** -- so both `fmadds` are round-half-up before a
truncating convert. The two pool words are not in the dump notes; reading pool+2156 as Hz -> blocks
per second and pool+444 as a worst-case blocks per second (so the allocation covers any rate) fits
the arithmetic, but it is a reading, not a finding.

Callees, all through `GuestCall`: `sub_82EE5E80` (the XDK memset, twice), `sub_82B373C8`
(**verified port**) and `sub_82B370E8` (**verified port**). Gate 1 passes -- census verdict pass,
the only closure member outside the audio set is the memset. No timebase (gate 3), r3 = 1 is read
by the caller (gate 4).

**`sub_82B370E8` is called with no register setup at all**: `bl 0x82b373c8` is immediately followed
by `bl 0x82b370e8`, and that callee takes the object in r3. The original is relying on
`sub_82B373C8` leaving r3 alone, which is whole-program register allocation and not the ABI (that
function carries the object in r3 throughout, and neither it nor its port ever writes r3). The body
reproduces it as `GuestCall` with zero arguments, which writes no argument register -- the same
machine state as the bare `bl`.

**Windows -- mirrored from two callees.** Own stores: `{+390,2}`, `{+368,4}`, `{+376,4}`,
`{+388,2}` and the two ring clears. The ring clears are the interesting ones and they *are*
enumerable: their length comes from `+372` and `+42`, both read before any store that could reach
them, so `RingBytes()` is shared verbatim between `Native` and `Windows`. Folded in from the
callees:

- `sub_82B373C8.inc`: its four per-channel arrays, declared as one 128-byte span 240..368 at the
  full eight-channel extent (the bytes past the channel count are written by neither run and
  compare equal; this spends bytes to save spans), its cursor write, and its two ring slots per
  channel at `((frames * channel + cursor) << 2) & ~3`. **Those addresses depend on `+376` and
  `+388`, which this call has just published**, so the builder predicts both: the computed frames
  (or 1) and cursor 0 on the resize path, the entry values otherwise. Its eight-channel limit is
  inherited -- past that it overruns its own red zone, so `Windows()` returns false, exactly as its
  own port does.
- `sub_82B370E8.inc`: 48..240 declared as one span whenever its layout byte (this object's `+42`)
  is 1, 2, 4 or 6-and-above; layouts 0, 3 and 5 write nothing.

Worst case is 25 spans at eight channels, 17 at four, inside the 32-span budget.

Two refusals, both checked rather than assumed. `+386` is read **between** the two memsets, and all
five header fields are re-read by the callees afterwards, so if a ring clear covers any of them the
addresses stop deriving from entry state: `ClearsControlFields()` returns false there, and the same
guard is applied to `sub_82B373C8`'s per-channel slots (its own port does this too). A null object,
descriptor or format pointer returns false -- the original would load through it.

Fidelity: `stwu r1,-128(r1)` is reproduced because `sub_82B373C8` works out of the red zone below
r1 (r1-320 .. r1-160) and needs it where the original put it; the `stfd f8,80(r1)` / `lwz 84(r1)`
convert spills are inside that frame and are done in registers instead, the round trip being
bit-preserving. `mullw` is the 64-bit product of the sign-extended low words and `rlwinm r,r,2,0,29`
takes the **low** word shifted left two, so the intermediates stay 64-bit and the cast is at the
store. `rotlwi r10,r11,0` is `mr`.

Unsure: `+380` read as an interval and `+390` as its counter is inferred from the increment-and-
return shape only; the counter is reset to 1 rather than 0, so the effective period is
`interval + 1` ticks, which looks like an off-by-one in the original and is reproduced as such.
