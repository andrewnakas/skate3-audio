# sub_82B2F590

Non-leaf, 332 lifted lines, 30,397 calls per boot on `RwAudioCore Dac`. Census gate-1 pass, closure
of 4; the one member outside the audio corpus is `82B2FF88`, which is a leaf with no import, lock or
allocation (checked by reading it: it writes `+1060..+1083` and the byte `+1089` on r3 and uses
`r1-16` as scratch). Both callers (`sub_82B2F9E4`, `sub_82B2FDF4`) do `li r3,1` immediately after the
call, so the mask is `kReturnNone`.

Argument: r3 = a filter/envelope object, ~1104 bytes. Fields used, all plain offsets: `+52`, `+60`,
`+68` three parameters; `+56` a word poisoned with `0x7FF7FFF1` (a NaN) on the rate path; `+348..+363`
their published copies (`+348` copies `+1100`, `+352` copies `+52`, `+356` copies `+60`, `+360`
copies `+68`); `+364` f32[6] ramp; `+388` s32[6] points; `+436` f32[6] bands; `+460` f32[6] weights;
`+1060..+1083` sub_82B2FF88's block; `+1088` u8 flag; `+1089` u8 voice count; `+1092` s32 state;
`+1096` the table pointer sub_82B2FEA8 sweeps; `+1100` f32 blend; `+140 + 60i` per-voice records;
`+1068 + 4i` a word array.

Nothing runs unless `+1092` reads exactly 1. Then one of four paths, and all four tests read memory
that no callee writes (the highest object byte sub_82B2F2C8 touches is `+1056`; sub_82B2FE00 and
sub_82B2FEA8 stay inside `+364..+411`):

- `+60 != +356`: copy `+60` into the frame at r1+80, sub_82B2FE00 clamps it there and fills `+364`,
  the clamped value goes back to `+60`, `+56` is set to the NaN, then sub_82B2FEA8 (`+364` → `+388`)
  and sub_82B2F2C8 (`+364` → `+436`), and r29 is set to 1 -- the only path that arms the record loop.
- else `+1100 != +348`: sub_82B2FEA8 and sub_82B2F2C8 as above, then `+1088` is zeroed, which forces
  sub_82B2FF88 below.
- else `+68 != +360`: sub_82B2F2C8 only.
- else: nothing but the tail.

Tail, on all four: the six weights `w[k] = (1 - band[k]) * (1 - floor/param52)` where `param52` is
`+52` floored up to the rodata single at `0x822F8A5C` (same pool sub_82B2F2C8 reads at +1120 and
sub_82B298E0 at +480) and `floor/param52` is a single-precision divide; all seven loads precede all
six stores. Then `+1088`: zero calls sub_82B2FF88, non-zero and r29 == 1 and `+1089` non-zero runs the
record loop (per record: read `+24`/`+28` and one word from `+1068+4i`, write `+40` = 0, `+36`, `+44`,
`+56`, and a zero byte at `+60` -- which is the NEXT record's first byte; the bound `+1089` is
re-read every iteration). Then the state word goes to 2 -- stored between two of the tail's loads,
where the lifted body puts it -- and all four parameters are published.

`stwu r1,-128(r1)` **is** reproduced: sub_82B2FE00 is handed r1+80 and clamps it in place, and
sub_82B2F2C8 (r1-80) and sub_82B2FF88 (r1-16) both use the red zone below the live r1.

Windows: declared per path, not as one union, mirroring the callees' own ported Windows()
(`sub_82B2FE00.inc`, `sub_82B2FEA8.inc`, `sub_82B2F2C8.inc` -- if any of those widens, this must
widen too): `+56..+63`, `+364`, `+388`, sub_82B2F2C8's `+436` plus its six 25-byte record publishes
and six envelope words when `+68 != +360`, the `+1088` byte, the weights, the state word, the four
copies, and either `[+1060, +1090)` for sub_82B2FF88 or one merged span over the record loop. That
callee's write set is declared as one 30-byte span, four unwritten bytes included; `+1088` sits inside
it and is read before the call, never after.

The record loop's span is `[+176, 140 + 60*(n-1) + 61)` in one piece rather than n pieces of 25: at
stride 60 and up to 255 records that is at most 15 KB and one span, where 255 spans could not fit the
budget. Note at n >= 16 the loop really does write `+1096` and `+1100` -- record 15's `+56` store and
its `stbu` -- and the tail then publishes the corrupted `+1100`. That is reproduced, not fixed.

Returns false when r3 is null, when sub_82B2FEA8 would run with a null table pointer (mirroring its
own Windows()), or when a record store could land on `+1089`, the loop's own re-read bound. The five
store offsets are 36/40/44/56/60 from 140 + 60i and no residue can reach 1089, but the check is a
loop rather than a paragraph. sub_82B2F2C8's own three false exits cannot fire from this caller: they
test its r4 (always `+436` here) against `+68`, `+360`, `+388..+411` and the records' first two words,
all disjoint from `[436, 460)` by construction.

Gates: 1 pass, 2 pass except the guards above, 3 pass (no timebase), 4 pass (all output is stores).
STATUS: **verified** -- the .inc header carries the status and the call count the harness session recorded; this note was written before that session ran.

Unsure of:
- Field names: `+52/+60/+68` are named by offset on purpose. `+60` is a rate (sub_82B2FE00 clamps it),
  `+68` is what sub_82B2F2C8 calls its current level, `+1100` is the value both of the mapping callees
  take in f1. `+52` is only ever floored and inverted into the weights.
- `0x7FF7FFF1` is a NaN by construction (exponent all ones, mantissa non-zero). Nothing in this
  function reads `+56` back, so why the NaN is written is unexplained -- most likely to force some
  later `fcmpu` to be unequal.
- On the `+68 != +360` path the original does not reload f1 before sub_82B2F2C8; it carries the
  `+1100` single loaded for the previous compare. The port sets it explicitly to that same double.
- Callee rodata and sub_82B2FEA8's 1652-entry table are NOT recorded in this port's read set; their
  own hooks record them. A vector from this function alone will not replay without the image.
