# sub_82B50380

Leaf, 1,284 lifted lines, 217 vector instructions, no callees and no imports. 163,060 calls in the
boot session, all on `RwAudioCore Dac`. **Gate 2: the write set is not enumerable from entry
state** — measured, not inferred (`probe/harness/out/p17_windows.log`, `docs/PLAN.md`). The body is
written and exact; it is the reference for the Rust port and for the three smaller kernels that
share its idioms.

## What it does

16-bit PCM out of a wrapping ring into float32, one decode block per call. Two runs per call: the
`first` elements from `src + (offset & ~1)`, then the `wrap` elements from `src` itself — the ring
wrap, split by the caller. Each run has a vector loop plus a scalar remainder.

Args (all read straight off the lifted entry; nothing in `docs/rw_audio_structs.h` names these
buffers, so there are no offset constants):

| reg | meaning |
|---|---|
| r3 | `dst` — channel 0 floats out (`mr r11,r3`) |
| r4 | `dst_second` — channel 1 floats out, stereo only (`stw r4,-128(r1)` ; `mr r7,r4`) |
| r5 | `src` — the 16-bit ring's base |
| r6 | byte offset into the ring where this block starts |
| r7 | channel count: 1 takes the mono path, anything else takes `loc_82B505D8` |
| r8 | samples (mono) / frames (stereo) from the offset to the ring's end |
| r9 | ...and the count that wrapped back to the base |

Void: nothing in the caller reads a result (see the mask section).

Entry state as logged (24 consecutive samples at boot, plus calls 50,000 and 100,000): `r7 = 1`
every time (mono), `r8 = 0x87`, `r9 = 0` except the one wrap call with `r8 = 0x7E, r9 = 0x09`, and
`r6` stepping by `0x10E = 2*0x87` until it wraps at `0x1800`. So the ring is 3,072 samples and one
call converts one 135-sample block. **Neither the stereo path nor a non-zero `wrap` on a vector
path has ever been observed running** — the only `wrap` seen is 9, which takes the scalar tail.

Scale for every scalar sample: `lfs f0,-17516(r8)` after `lis r8,-32206`, i.e.
`((0x8232) << 16) - 17516 = 0x8231BB94`. Almost certainly 1/32768 — it is the scalar twin of the
`vcsxwfp128 <-,15` the vector paths use — but the body loads it rather than assuming it.

## Stores

Everything below is `stvlx128`/`stvrx128` pairs unless said otherwise. A pair
(`stvlx` at `ea`, `stvrx` at `ea+16`) writes exactly `[ea, ea+16)`.

- `{sp+36, 4}` and `{sp+68, 4}`: `stw r5,36(r1)` / `stw r9,68(r1)`. **The caller's frame**, not
  this function's — there is no `stwu`, so positive offsets off r1 are the outgoing-parameter save
  area. The stereo path reloads `src` and `wrap` out of them after clobbering both registers.
  Reproduced, because a window builder would have to declare them.
- mono: `[dst, dst + 4*first)` then `[.., + 4*wrap)` contiguously — 64 bytes per vector iteration
  (16 samples), 4 bytes per scalar remainder sample (`stfs` / `stfsu`).
- stereo: `[dst, dst + 4*(first+wrap))` for channel 0 and the same length at `dst_second` for
  channel 1 — 128 bytes per vector iteration per channel (32 frames), 4 bytes per remainder frame.
- `dcbz`, both paths, only when `(dst & 0x7F) == 0` and the total reaches the threshold (32 samples
  mono, 16 frames stereo). RexGlue models `dcbz` as a **32-byte** `memset` of the line containing
  the address; Xenon's `dcbz` establishes 128. The lifted model is what executes, so it is what is
  reproduced. Consequence worth recording: mono zeroes at `dst + 128k` for `k < n/32`, ending at
  `4n - 96`, inside the converted extent; **stereo** steps the same 128 bytes for `k < n/16` and so
  ends at `dst + 8n - 96`, well past channel 0's own `4n` bytes. A window builder has to cover that
  overshoot, not just the converted extent. (With the hardware's 128-byte line the mono establish
  covers exactly `4n` and the stereo one exactly `8n` — which would be both channels if they were
  adjacent. They are not in any logged call: `dst = 0x4B399B80` while `r4 = 0x707BF9C0`.)
- `{sp-80, 16}`: the `vperm128` control the stereo path builds and reads back with one `lvx128`.
  This function's own frame, excluded by the brief, and kept because the four words are **not**
  identical — unlike the splat round trips elided in `sub_82B44B20`/`sub_82B399D0`, the load's lane
  reversal is not a no-op here, so hand-assembling the constant from the immediates would be the
  one place a silent error could hide. In guest byte order:
  `00 01 04 05 08 09 0C 0D 02 03 06 07 0A 0B 0E 0F` — the even halfwords of the group gathered
  into one half and the odd ones into the other, i.e. the stereo de-interleave.

## Which registers the body reassigns, and where — why gate 2

This is the record so a later reader does not have to re-derive it. Every store is based on r11,
r10 or r7 and indexed by one of r3, r4, r5, r6, r7, r8, r9, r27, r28, r29, r30, r31. **Not one of
them holds its entry value at the store.**

Addresses below are the `loc_` labels that appear in the lifted body; the bare numbers are absolute
lifted line numbers in `skate3_recomp.68.cpp`, which is what the census's `assigned_at` field
reports, so every row is checkable without re-deriving anything.

| reg | at entry | reassigned at | value at the store |
|---|---|---|---|
| r11 | stale caller scratch: `0x49600060` in the 24 consecutive boot samples, `0x496017E4` at call 50,000, `0x496014D4` at call 100,000 — it drifts, which is itself the point | `mr r11,r3` in the prologue; `addi r11,r11,64`/`,128` per iteration (`assigned_at` 56175, 56275, 56857) | `dst`, then `+64` (mono) or `+128` (stereo) per iteration |
| r10 | stack scratch, `0x707BF900` | `add r10,r10,r5` in the prologue; `mr r10,r5` at loc_82B50524 and loc_82B5097C; `lwz r10,-128(r1)` mid-block (`assigned_at` 56708) and `lwz r10,-120(r1)` at the bottom of it | `src + (offset & ~1)`, then `src`; on the stereo path a value reloaded from slots the body itself wrote |

So the entry-state evaluation of the census's own expressions is nonsense: `ea = r11 + r3` becomes
`0x49600060 + 0x4B399B80 = 0x94999BE0`, outside guest range, and `r5 = 0xE2E3F000` *is* a pointer
at entry (the ring, in the 4 KB physical-mapped range) but is the constant 32 or 48 by the time a
store names it. That is the measurement; the earlier pass that judged this function portable read
the **form** of those `ea` expressions rather than their operands, one of the three inference
mistakes `docs/PLAN.md` records. **No prediction is attempted here to rescue it**, and the verdict
is not "hard", it is "measured false": `Windows()` returns false unconditionally and the original
runs. Windowing it would need per-store instrumentation inside the lifted body, not a hook that
reads entry registers.

Gates 1 and 3 are pass (leaf, no imports, no indirect calls, no `mftb`). Gate 4 would be pass if
gate 2 were.

## Result mask

Honest mask: **`kReturnNone`** — the function is void. `kReturnR3` is declared instead only
because lint check 5 rejects a false `Windows()` paired with `kReturnNone` (it would compare
nothing at all), and it is harmless because a gate label is never shadowed or promoted. r3 is left
correct anyway: 64 on the mono path (`li r3,64`, loc_82B50444), 112 on the stereo path, and on the
stereo wrap remainder the **last right-channel sample sign-extended** (`extsh r3,r8` in
loc_82B50B28). No caller reads it.

v0 and v32–v63 are the only vector registers written, all of them volatile, so no preserved VR is
clobbered — unlike `sub_824531C8`/`sub_82B399D0` this body needs no `keepNN` bookkeeping. r25–r31
are clobbered and restored by `__restgprlr_25`, so the body leaves them untouched.

## What is elided, and the assumption each elision makes

- **Four counted `dcbt` loops** (loc_82B503D4, loc_82B50404, loc_82B50608, loc_82B50638). `dcbt`
  lifts to nothing; each loop's only other effect is on r3/r4/r6/r7/r31 and `ctr`, and every one of
  those is written again before it is next read (`li r7,0` / `li r7,16`, `li r3,112`). r31 is
  restored by the epilogue.
- **The own-frame spills at `-88` .. `-128(r1)`**, kept in locals: two loop-carried cursors
  (`-120` the read cursor, `-128` the channel-1 cursor), two remainder counts (`-80`, `-124`) and
  seven spilled `li` immediates (16/16/32/32/32/32/48 at `-116`/`-112`/`-108`/`-104`/`-100`/`-96`/
  `-88`). **The assumption:** no store in the body lands in this function's own frame, i.e. the
  caller does not hand us a destination inside our own red zone. That holds in every logged call
  (`dst = 0x4B399B80`, `dst_second = r1 + 0x110`, `r1 = 0x707BF8B0`) but it is an assumption, not a
  proof, and the shadow harness would catch it if it were wrong — which is exactly what the gate
  label costs us here. This is the same elision the verified `sub_82B44B20` and `sub_82B399D0`
  ports make for their own frames, with the same kind of note.
- The `std`/`lfd` round trip through `-80`/`-88(r1)` in every scalar tail, which is only a GPR→FPR
  move of the sign-extended halfword before `fcfid`. `double(int64_t)` is exact for a 16-bit input.
- Note that because the `-80` remainder spill is elided while the four control words are kept, the
  guest frame at `-80(r1)` is left holding `0x00010405` where the original leaves the remainder.
  Own frame, read by nobody after the reload, never compared.

## Exactness details

- `stvlx128`/`stvrx128` are reproduced as the two byte loops with their **opposite** lane orders:
  `stvlx` takes `u8[15]` downwards from `ea`, `stvrx` takes `u8[0]` upwards written backwards from
  `ea-1`. `docs/PLAN.md` names this as the hazard specific to this kernel, and it is real: for a
  16-byte aligned `ea` the pair is indistinguishable from one aligned store, so **only an unaligned
  destination could ever tell a wrong translation apart, and nothing available can check that** —
  the harness cannot manufacture entry states, `dst` is 128-byte aligned in every logged call, and
  the gate keeps the shadow compare off this function anyway. Treat both loops as unverified.
- The same for `lvlx128`/`lvrx128`: `lvrx` on an already-aligned `ea` reads nothing and yields
  zero, which is the lifted ternary and the case that actually runs. The mono first run and the
  stereo first run use the unaligned pairs; both wrap runs use plain `lvx128`, which masks the low
  four address bits — so the wrap runs assume a 16-byte aligned `src`, as the original does.
- `vcsxwfp128 <-,15` is a multiply by `2^-15` (`0x38000000`) and stays a **separate** multiply;
  there is no FMA anywhere in this kernel (no `vmaddfp`, no `vnmsubfp`, no `fmadd`), so the
  single-rounding rule has nothing to bite on here. The scalar path's `fcfid`/`frsp`/`fmuls` stay
  three steps.
- `ctx.fpscr.enableFlushModeUnconditional()` is emitted once per vector-loop iteration, at the
  first `vcsxwfp128`; `disableFlushModeUnconditional()` at each `lfs`/`lfd`. Both are at the lifted
  points. Inside a loop the `vor128`/`vperm128`/`vupkhsb128`/`vupklsb128` ops are hoisted across
  the toggle relative to the lifted schedule — safe because all four are integer SSE ops and read
  no rounding state, and the conversions themselves are all on the enabled side either way.
- Every vector load and store keeps the `VectorMaskL`/`VectorMaskR` lane reversal.
- `add r10,r10,r5` (the read cursor) is a 64-bit add on zero-extended words and can carry into bit
  32; every use of r10 reads `.u32`, so a 32-bit cursor is faithful.
- `rlwinm rX,rY,1,0,30` after `srawi` is a masked shift: the rotate's wrapped bit 31 lands in bit 0
  and the mask clears it.
- Every `bdnz` is a `do/while (--n != 0)` on a `uint32_t`, which reproduces `mtctr`'s 64-bit copy
  and `bdnz`'s 32-bit test exactly, including a negative count looping ~2^32 times — the four
  vector loops are guarded by a signed `>=` that makes the count at least one, the four scalar
  tails are guarded only by `!= 0`, so a negative `first`/`wrap` hangs in the original too and is
  not guarded here.
- Store order is the lifted order throughout, and in both stereo loops **all** channel-0 stores
  precede **all** channel-1 stores. The second stereo remainder (loc_82B50B28) stores channel 1
  **before** channel 0, the opposite of loc_82B5092C; both are preserved.

## Unsure

- The vector paths' `vupkhsb128`/`vupklsb128` are commented `...sb` in the lifted stream but
  RexGlue lowers them as 16→32 signed widenings, which is what `vcsxwfp128 <-,15` then needs. The
  lowering is copied verbatim rather than reasoned about, so a wrong mnemonic label costs nothing
  here.
- The value at `0x8231BB94` is loaded, never assumed. If it is ever dumped, confirming it is
  `0x38000000` would also confirm the scalar and vector paths agree, which the shadow compare
  cannot do while this function is gated.
- The stereo path has no observed input at all. If it matters later, the `.mpf`/music path is the
  likely producer of a two-channel block; the mono calls logged here all come from one XMA decode
  buffer in the physical-mapped range (`0xE2E3F000`, `0xE2F81800`, `0xE2F57800`).
