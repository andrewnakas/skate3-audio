# sub_82B454B8

- Role: leaf, void, `f(obj* r3, record* r4, float* gains r6, f1)`. Distance-weighted 2D panning:
  writes the gains of the four selected speakers, and of speaker 1 / 5 / 6 when the channel count
  calls for them. 77,736 calls per boot on `RwAudioCore Dac`, 409 lifted lines, no callees.
- Callers: `sub_82B45440` (f1 = its own f2) and `sub_82B460A0` (loops r6 += 32, r4 += 16, f1 = f29).
  Both reload r3/r4/r6/f1 from callee-saved registers immediately after the call, so no volatile
  register is read: mask `kReturnNone`, and the gain stores carry the comparison.
- Object (r3), nothing in `docs/rw_audio_structs.h` names it: `+56 s32 count` (compared with 4, 6
  and 8) and `+172/+176/+180/+184 s32` speaker indices -- the same fields `sub_82B45B60` reads.
  The indices are used two ways: `8*index` to read an (x,y) pair out of the object, and `4*index`
  to address the gain array. INFERENCE: a 7-entry speaker position table at `object + 8*k`, which
  is why `+8/+12` (speaker 1), `+40/+44` (5) and `+48/+52` (6) are read and why their gains land
  at `gains+4`, `+20`, `+24`. Consistent with `count` sitting at `+56 == 8*7`, but unverified.
- Record (r4): the 12 bytes `sub_82B453D8` writes -- `+0/+4` a position clamped to the unit disc,
  `+8` its squared length clamped to 1.0. `1.0` is the degenerate case.
- Constants (image dump): 1.0f 0x8231A844, 0.0f 0x82165A10, 0.5f 0x8209975C, 0.0005f 0x821A0318.
- Maths: `weight_k = 1 - 0.5*|speaker_k - source|` (fsqrts then fnmsubs) for the four selected
  speakers, plus 5 and 6 when count == 8; `front = 0.5*(x+1)` and `back = 1 - front`, each snapped
  to 0.0 within 0.0005; the front pair is normalised by `sqrt(front / sum of squares)` over two
  weights (count == 4) or three, the third being `weight(speaker 1) * f1`; the back pair by
  `sqrt(back / sum of squares)` over weights 5, 6, 184, 180. Every stored gain is then scaled by
  `sqrt(1 - lensq^2)`, `lensq` reloaded from r4+8.
- Stores, in order. Path A (`r4+8 == 1.0f`): five `stw` of zero to `gains+0,+4,+8,+12,+16`, then
  `count` is reloaded and if it is 8, `stfs 0.0f` to `gains+20,+24`. Path B: `stfsx` to
  `gains+4*index172`, `+4*index176`, `+4*index180`, `+4*index184`, each index reloaded from the
  object after the previous store; then `count` reloaded, and if >= 6 `stfs gains+4`; then `count`
  reloaded again, and if == 8 `stfs gains+20,+24`.
- Windows: path A is `write(gains, 20)`, or 28 when the entry count is 8 or `gains..+19` overlaps
  `obj+56..+59` (the reload follows the stores, so the entry value cannot predict it). Path B is
  the four 4-byte stfsx spans, plus `gains+4/+20/+24` when the entry count asks for them or when
  any store overlaps `obj+56..+59` -- a superset compares equal. **Windows() returns false** when
  a computed store address overlaps `obj+172..+187`: an index reloaded after such a store makes a
  later store address unknowable, and that cannot be supersetted. At most 7 spans, 28 bytes.
- Reads recorded: the record, the count, the four indices and the four pairs they select, `+40..+55`
  when count == 8, `+8..+15` when count != 4, and the four rodata singles.
- Gates: 1 pass (leaf, no imports, no indirect call, no lock), 2 pass except the index-aliasing
  case above, 3 pass (no timebase), 4 pass (the gain stores are observable). STATUS: pending.
- Unsure:
  - The speaker-table reading, and reading f1 as a caller-supplied weight for speaker 1, are both
    inferences from the offset arithmetic; the code is faithful either way.
  - `center` (guest f8) is the 0.0f constant on the count == 4 path, because nothing writes f8
    between the constant load and its use. That is modelled explicitly rather than dropped, since
    it is stored if the reloaded count reads >= 6 -- only possible if the field changes mid-call.
  - f1 is left holding `depth*gain172`, as the original leaves it, although the mask does not
    compare it and neither caller reads it.
  - Operand order on every commutative `fmuls`/`fadds` is kept as lifted for NaN propagation
    (`vmx128-exactness.md` rule 4); whether clang keeps it is not controllable from source.
  - The `disableFlushModeUnconditional()` calls attached to the red-zone spill and the exit
    restores are not reproduced: no float work follows them, and fpscr is not compared.
