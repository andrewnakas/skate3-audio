# sub_82B32328

- Role: `void f(record*)` — the record's flush. It raises `u8[record+477] = 1`, then walks the
  **48-byte request ring embedded at `record + u16[record+464]`** from the cursor
  `u8[record+468]`, calling `sub_82B33F98(record, u8[record+468])` for every entry whose
  `u8[entry+46]` is nonzero and advancing the cursor (wrapping to 0 on equality with
  `u8[record+470]`), and finishes by resetting ten fields of the `+432..+477` block. 125 lifted
  lines, one direct callee, no own indirect call, no imports, no timebase, no lock. **2,494 boot
  calls** on `RwAudioCore Dac` (tier D).
- Argument: r3 = the record. No other entry register is read.
- This is the callee `port_82B32870` calls first, and its note's claim that it "resets
  `+432..+477`" is confirmed here store by store. It is also the other half of `port_82B32480`:
  `+477` is the flag that function reads to suppress its release calls (set for exactly this
  call's duration), and `+475` — one of the bytes zeroed here — is *that* ring's read cursor. So
  the record carries **two** rings: 48-byte requests at `record + u16[+464]` with cursor `+468`
  and length `+470` (flushed here), and 20 × 16-byte completions at `record+100` with cursor
  `+475` (drained there). Three functions agree on the bytes.
- Stores (11 outside this call's frame):
  - `stb r8,477(r3)` — `u8[+477] = 1`, 1 byte, **first**, before the first entry address is
    even formed
  - `stb r4,468(r31)` — the new cursor, 1 byte, once per loop iteration
  - then the tail, in this exact order: `477`=0, `469`=0, `467`=0, `468`=0, `u32[432]`=0,
    `u32[436]`=0, `473`=0, `474`=0, `475`=0, `472`=**16**. Ten stores, 14 bytes, unconditional on
    every path including the no-op one.
  - the `-8(r1)` link slot, the `-16(r1)` r31 save and the `stwu` back chain are this call's own
    frame; never windowed.
  `u8[+468]` is reloaded for the call argument *and* again for the increment, and `u16[+464]` is
  reloaded at the bottom of every iteration — the callee may move any of them, so none of those
  loads may be hoisted.
- Wrap detail worth keeping: the cursor advance is the `subfic`/`subfe`/`and` carry idiom, and it
  wraps on **equality** with `u8[+470]`, not on `>=`. A cursor that ever exceeds the count would
  never come back. `subfe r5,r6,r6` reads r6 (the first iteration's entry address, then stale);
  `~r6 + r6` is all ones whatever r6 holds, so the result cannot depend on it.
- Result: **none** honestly — there is no `li r3,...` on any path, so r3 is the record on the
  no-op path and `sub_82B33F98`'s result after a flush. The macro line carries `kReturnR3`
  because a gate-labelled port with a false `Windows()` and `kReturnNone` trips lint check 5; the
  mask is never read for a gate label. A comparable version would declare `kReturnNone`.
- Gate 1 **fails** at depth 1, and this is the failure `probe/ports/notes/sub_82B32870.md`
  already records from the other side: `sub_82B33F98` frees through the core allocator's vtable,
  `u32[u32[u32[owner+36] + 0] + 12]`, at its `bctrl` **0x82B340A4**. The call here is
  `bl 0x82b33f98` at 0x82B32374, inside the loop, so it is unconditional whenever any entry is
  busy. The no-op path (no busy entry) is replayable, but it is exactly the path that proves
  nothing, so `Windows()` returns false outright rather than being split.
- The write set I WOULD have declared: `spec.write(record + 432, 8)` (the two words),
  `spec.write(record + 467, 11)` (`+467..+477`, which covers every tail byte and the cursor
  stores in one span), plus `sub_82B33F98`'s own write set per iteration — that last one is the
  blocker and is allocator-wide. Reads `{record+464, 8}` (`+464`, `+468`, `+470`) and
  `{entry+46, 1}` per iteration. Note the iteration count is only knowable after each callee
  returns, so even without the allocator this would need a bounded walk with the entry states
  read up front, and the callee is free to invalidate them.
- Unsure: what `u8[+472] = 16` means — 16 is the only nonzero constant this function writes, and
  nothing else read so far touches `+472`. `+467`, `+469`, `+473`, `+474` are only ever zeroed
  here, so the port is safe, but their meaning is unknown and they are deliberately left as plain
  offsets. `u16[+464]` is read with `lhz`, so it really is 16-bit, which is unusual for a byte
  offset field and might mean the ring lives within the first 64 KB of the record — unverified.
