# sub_82B28970 -- shut a player object down: decoder, record, block

`r3` = the object, the only argument. Three independent teardown steps, each guarded:

1. `u32[object+336]` is the live decoder. Non-null: `sub_82B3C930(decoder)` -- the decoder
   teardown `docs/command-queue.md` names, the one `EVENT_STOP` calls -- then `stw 0` over the
   pointer.
2. The byte at `+373` arms the record step: `stw 0` at `+24`, `stb 0` at `+43` (in that order),
   then `sub_82B489D0(u32[object+8], object+56)`. The owner pointer is loaded *after* both
   stores in the lifted form and is left there. `sub_82B489D0` retires the record: it compares
   its `r4` against `u32[owner+180]`, rethreads the lists at `owner+112`, and reads the
   discriminator byte at `record+20`. The byte at `+43` is the same flag `sub_82B48440` tests
   at `skate3_recomp.68.cpp:37343` before walking that record, which is what makes `+43`
   read as "the record at +56 is live".
3. `u32[object+80]` is a heap block. Non-null: `free(allocator, block, 0)` through vtable slot
   **+12** of `u32[u32[object+8]+36]` -- the same `allocator->vtable[12](allocator, ptr, 0)`
   shape `sub_82B1E3F8`, `sub_82B1E458`, `sub_82B34D60` and `sub_82B3C810` all use. The
   pointer at `+80` is **not** nulled afterwards.

`+8` is the owner in both steps 2 and 3, and `docs/command-queue.md` documents `Player+8` as
the `System*`; `+36` on it holding the allocator matches `sub_82B1E458`, which reaches the same
allocator offset off the global `System*` at `0x8307762C`.

No constant-pool addresses: every offset here is off `r3`, and the census's provenance table
agrees (three `entry`-class stores, no `derived` ones).

Stores outside the frame: `{object+336, 4}`, `{object+24, 4}`, `{object+43, 1}`.

## Unverifiable, and why

**Gate 1**, and twice over:

- Its own `bctrl` at `0x82B289E4` is a *free*. Replaying the native body on rewound memory
  would free the same block a second time; no window rewinds an allocator's own book-keeping,
  and the target is a vtable slot loaded from rewound memory anyway.
- `sub_82B3C930` at depth 1 is this project's canonical gate-1 callee
  (`probe/ports/notes/sub_82B3C930.md`): four indirect calls that release and unregister the
  voice. `docs/shadow-harness.md` already uses it to explain why `EVENT_STOP` has no comparable
  path.

The census reports the verdict at depth 0 because its own indirect call is found first; both
reasons are fatal and independent. A path with neither (no decoder, no block) exists in
principle, but the byte at `+373` still reaches `sub_82B489D0`, which the static screen passes,
so that path alone would be comparable. It is not worth engineering for: the function ran
**once** in the traced boot, and shutting a player down is exactly when the decoder and the
block exist.

## The write set it would have declared

Enumerable from entry state as far as this body goes -- the callees are what make it false:

    const uint32_t obj = ctx.r3.u32;
    if (REX_LOAD_U32(obj + 336) != 0) return false;                  // sub_82B3C930
    if (REX_LOAD_U32(obj + 80) != 0) return false;                   // the free bctrl
    if (REX_LOAD_U8(obj + 373) != 0) return false;                   // sub_82B489D0's writes
    spec.write(obj + 336, 4);
    spec.write(obj + 24, 4);
    spec.write(obj + 43, 1);
    spec.read(obj + 8, 4);  spec.read(obj + 80, 4);  spec.read(obj + 373, 1);

`sub_82B489D0`'s own writes are enumerable in principle (10 stores, gate-1 verdict `pass` in
`docs/ports-static.md`) but include a `sub_82B39690` call and a `rlwinm`-scaled base off the
record's discriminator byte, so declaring them belongs to that function's own port, not here.

Result mask `kReturnR3`: r3 is not set deliberately on any path -- it holds the decoder, or
whatever `sub_82B3C930`, `sub_82B489D0` or the free left behind. The native body leaves the
same value on every path, so the mask is accurate; the function is morally void, and the lint
forbids `kReturnNone` when no writes are declared.

## Unsure

- Whether `+24` is a pending-command count or a pointer. It is zeroed with the same register
  as every other clear here, so the store carries no type information.
- What the block at `+80` is. Its size is the allocator's business and nothing here reads it.
- Whether not nulling `+80` after the free is a bug or deliberate (the object is presumably
  about to be freed itself). No caller exists in the lifted corpus to settle it -- this
  function is reached through a function pointer.
