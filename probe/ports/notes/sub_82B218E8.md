# sub_82B218E8 -- start the Dac profiler worker and publish its run state

`r3` = the object `sub_82B217F0` hands over (`config+4`), `r4` = the mode -- in the one traced
call, the rounded rate `sub_82B217F0` computed from `config+12`, which this function only ever
compares against 0 and 1. The only direct caller is `sub_82B217F0`
(`skate3_recomp.67.cpp:9261`), and it ignores r3.

Guarded by the run-state word at `0x830845CC`, the same word `sub_82B217F0` tests before
calling and the shutdown at `skate3_recomp.67.cpp:9226` clears. Non-zero means already
running and the call does nothing -- no stores, no call.

On the zero path:

1. `stb 1` at `0x83067057`, the armed byte, unconditionally and before either mode branch.
2. mode 0: if `u32[object+76]` is non-null, call slot **+48** of that sink's vtable with
   `r3 = sink`, `f1 = 1.0f` (the pool constant at `0x8231A844`) and `r5 = 0` -- one float
   argument, which reads as a gain or rate setter. Then publish run state **1**. A null sink
   publishes 1 all the same.
3. mode 1: publish run state **2**, no call.
4. any other mode: **nothing is published**. The armed byte stays 1, the run state stays 0, so
   the next call arms it again and repeats. Reproduced as-is; it is only unreachable if
   `sub_82B217F0`'s rounded rate is always 0 or 1, which nothing here guarantees.

All three constants computed as `((imm & 0xFFFF) << 16) + offset`: `0x83080000 + 17868` =
`0x830845CC`, `0x83060000 + 28759` = `0x83067057`, `0x82320000 - 22460` = `0x8231A844`. The
first two match the addresses `probe/ports/notes/sub_82B217F0.md` recorded independently; the
third is the 1.0f that `sub_82B2F2C8`, `sub_82B2FEA8` and `sub_82B454B8` all identify.

Store order inside the mode-0 call setup is preserved: `r3`, `r5`, the vtable load, the `lfs`
(with its `disableFlushModeUnconditional`), then the slot load. The `lfs` sits between the two
loads in the lifted form and is left there.

Stores outside the frame: `{0x83067057, 1}` and `{0x830845CC, 4}`. The frame stores are the
function's own; the native body builds no frame and never touches r31.

## Unverifiable, and why

**Gate 1**, at depth 0 (`indirect: 1`, `gate1 fail, reason indirect, at sub_82B218E8`). The
`bctrl` at `0x82B21944` targets `u32[u32[object+76]+0]+48`, a vtable slot read from memory the
harness rewinds; replaying it would re-issue a call whose target is outside the rewind window
by construction. `sub_82B217F0`, the caller, is already labelled gate 3 for the `mftb` in its
own tail and its note names this `bctrl` as the second, independent reason that path cannot be
replayed.

The gate is path-dependent three ways and none of them is worth building for: the run-state
path has no stores and no call (fully comparable, and it is the path the traced boot did not
take), the null-sink and non-0/1-mode paths have stores but no call. With **one call per boot**
there is no evidence to be had regardless -- one comparison is not evidence.

## The write set it would have declared

Everything is a fixed global, so it is enumerable from entry state; only the callee makes it
false:

    if (REX_LOAD_U32(kRunState) != 0) { spec.read(kRunState, 4); return true; }  // no writes
    if (ctx.r4.s32 == 0 && REX_LOAD_U32(ctx.r3.u32 + 76) != 0) return false;     // the bctrl
    spec.write(0x83067057, 1);
    spec.write(0x830845CC, 4);   // not written when r4 is neither 0 nor 1; declared as the union
    spec.read(ctx.r3.u32 + 76, 4);
    spec.read(0x8231A844, 4);

Result mask `kReturnR3`. The function never sets r3 deliberately -- it is unchanged on the
run-state, null-sink and other-mode paths, and on the sink path it holds the sink and then
whatever the callee returned. The native body leaves exactly the same value on every path, so
the mask is accurate rather than merely inert; `kReturnNone` is what the caller actually
justifies, and the lint forbids it here because no writes are declared.

## Unsure

- What the sink's `+48` entry does. One float argument of 1.0f and `r5 = 0` is consistent with
  a volume, a rate scale, or an enable-with-weight; nothing in this body pins it.
- Whether run states 1 and 2 mean "started with a sink" versus "started without". Mode 0
  publishes 1 whether or not the sink existed, so the word records the mode, not the outcome.

## Split and armed, 2026-09-12

Converted from gate-1 to a path split. This note called the path-dependence "not worth building
for", on the grounds that one call per boot is not evidence; that judgement stands about the
*evidence*, but the split itself costs four lines and three of the four store shapes call nothing, so
the port is now armed rather than labelled.

- **Predicate:** false only when `REX_LOAD_U32(0x830845CC) == 0 && r4 == 0 && REX_LOAD_U32(r3+76) !=
  0`. Every other entry state — already running, mode 0 with a null sink, mode 1, any other mode —
  calls nothing.
- **One extra decline.** The armed byte at `0x83067057` is stored *before* the sink pointer at `+76`
  is read, so `Windows()` refuses if that byte falls inside `[r3+76, r3+80)` rather than asserting
  the global cannot be inside the object.
- **Comparable write set:** `{0x83067057, 1}` and `{0x830845CC, 4}`, declared as the union — the
  run-state word is not written when the mode is neither 0 nor 1, and an unwritten window compares
  equal, so over-declaring it costs nothing. Empty on the already-running path. Reads
  `{0x830845CC, 4}` and `{r3+76, 4}`.
- **Expected fraction:** one call a boot, and which path it takes depends on `sub_82B217F0`'s rounded
  rate and on whether `+76` holds a sink; nothing measured says. So: 1 or 0 comparable calls per
  session, and the skip counter distinguishes them.
- **Stays unchecked:** the `bctrl` into slot +48 with `f1 = 1.0f`, and the ordering of the `lfs`
  between the vtable load and the slot load that only matters on that path.
