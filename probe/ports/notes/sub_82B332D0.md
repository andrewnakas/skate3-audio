# sub_82B332D0

- Role: `int f(object*, int index, r5, r6, r7)` — refill one slot of the 80-byte array at
  `object+96`. It is the deferral target of `sub_82B33870`, which calls it as
  `(owner, index, entry r5, 1, 0)`; the two functions share both parallel arrays and the same
  index scaling, so the offsets here are cross-checked against that port. 179 lifted lines, three
  direct callees (`sub_82B33C08`, `sub_82B32550`, `sub_82B33418`), no imports of its own, no
  indirect call of its own, no timebase. 1,071 boot calls on `RwAudioCore Dac` (tier D).
- Addressing, both `rlwinm`+`add` chains reproduced in 64 bits:
  - the 48-byte **record** = `object + u16[object+464] + 48*index` (index\*3 then \*16);
  - the 80-byte **slot** = `u32[object+96] + 80*index` (index\*5 then \*16);
  - the 16-byte **ring entry** = `object + 16*claimed`, where `claimed` is the index
    `sub_82B32550` writes into the local at `r1+80` (that port documents the ring: 20 entries,
    busy byte at entry+113, so `+100` here is a field of the same 16-byte entry).
- Flow: `u8[record+46] == 1` arms a staleness check on the slot's handle at `u32[slot+44]`.
  The handle's low byte indexes a table of **328-byte** entries at
  `u32[u32[u32[slot+40] + 8] + 40]` with a signed count at `+44` of the same table object; the
  entry is live when `s32[entry+0] == handle` and `s32[entry+4] != 0`. Out of range, or a
  mismatched handle, or a null `+4`, all mean stale: the function stores `u32[record+20] = 0` and
  returns 0. A live handle, a zero handle, or a state byte that is not 1 all fall through to the
  refill.
- Refill: `sub_82B33C08(object, index, &r1+84, &r1+88, &r1+92)`. A zero first out-word means
  nothing was produced — return 0. Otherwise `sub_82B32550(object, &r1+80)` claims a ring entry;
  then `sub_82B33418(object, chunk, index, r5, r6, r7)` and return 1.
- Stores, in the order the original makes them (four to memory outside the frame, plus the frame):
  - `stw r7,80(r1)` — the local at frame+80 zeroed, inside the 160-byte frame, not a window
  - `stw r7,20(r9)` — `u32[record+20] = 0`, 4 bytes, stale path only
  - `stw r8,24(r29)` — `u32[slot+24] += u32[r1+88]`, 4 bytes, refill path. **`slot+24` is an
    outstanding-byte count, corroborated:** `sub_82B32480` subtracts the retired buffer's byte
    count (`u32[buffer+4]`) from the same field of the same 80-byte record, which it reaches as
    `u32[self+96] + class*80 + 24` with the class taken from the ring entry's `+14`. Two ports
    reading the field opposite ways is what makes the reading more than a guess.
  - `stb r6,74(r29)` — `u8[slot+74] = (u8)claimed`, 1 byte, claim-succeeded path
  - `stw r9,100(r11)` — `u32[object + 16*claimed + 100] = u32[r1+92]`, 4 bytes, same path
  - the `stwu` back chain and the `__savegprlr_25` spills are this call's own frame.
  **The running total at `slot+24` is updated BEFORE the ring claim is tested**, so a refused
  claim still advances it and then returns 0. That looks like a bug; it is reproduced, not fixed.
  The add is `add r8,r11,r10` on two zero-extended words — 64-bit — and `stw` narrows it, so a
  wrap past 2^32 is lost exactly as on the machine, which is why the port keeps 64-bit
  intermediates and casts at the store.
- Result: **r3**, a 0/1 boolean. `sub_82B33870` reads it as `clrlwi r11,r3,24`, so only the low
  byte matters to that caller, but the function itself writes all 64 bits (`li r3,0` / `li r3,1`).
  `kReturnR3` is the honest mask.
- Gate 1 **fails twice**, both at census depth 2, both unconditional on the refill path:
  1. `sub_82B33C08` reaches `RtlEnterCriticalSection` / `RtlLeaveCriticalSection` through
     `sub_82EC1290` — a lock cannot be replayed on rewound memory;
  2. `sub_82B33418` reaches `sub_82B3C870`, whose single `bctrl` is an indirect call.
  `sub_82B32550` itself is clean (`verdict: pass`, and it is a **verified** port).
- One path IS replayable and enumerable: state byte 1 plus a stale handle calls nothing and writes
  only `u32[record+20]`. All of it — the record address, the slot address, the table walk — is
  loads from entry state, so a partial `Windows()` could return true there and false elsewhere,
  exactly as the brief allows. It is not written that way because a gate-1 STATUS makes the macro
  skip the shadow branch entirely, so `Windows()` is never called; if someone wants that path
  compared, the STATUS has to change to `kPortPending` first and the write set is
  `spec.write(record + 20, 4)` with reads `{record+46,1}`, `{slot+40,8}`, `{table+40,8}`,
  `{entry, 8}`, `{object+464,2}`, `{object+96,4}`.
- Unsure: what `sub_82B33C08`'s three out-words are. Their use says the first is a chunk pointer
  or handle (passed on as `sub_82B33418`'s r4, which is where `sub_82B33870` passes the slot's
  `+48` handle), the second a size added to a running total, the third a word parked in the ring
  entry — none of that was confirmed by reading `sub_82B33C08`. The 328-byte handle table is
  named nowhere in `docs/rw_audio_structs.h`; the "generation-tagged handle" reading comes only
  from the `entry+0 == handle` test, which is the usual shape but was not verified against the
  allocator that hands the handles out.
