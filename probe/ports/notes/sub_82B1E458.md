# sub_82B1E458 -- destroy an object: queue the sub-object's teardown, destruct, free

`r3` = the object, the only argument. Three parts, the last two unconditional:

1. `u32[object+4]` is a sub-object whose teardown is deferred. Non-null: an **8-byte command
   record** is appended to the System command queue reached as `u32[sub_object+16]`, using the
   offsets `docs/command-queue.md` documents -- buffer at `System+0x30` (48), write offset at
   `System+0xCC` (204). The record is `{handler, sub_object}` with handler
   `0x82B49238`, a real function in the corpus (`docs/ports-static.md`: 29 stores, indirect).
   The 8-byte size matches `sub_82B28A00`'s `param_2 == 1` class, which uses a different
   handler (`0x82B28C18`), so `0x82B49238` is a fourth queue handler, not previously listed.

   The consumer side corroborates the layout: `sub_82B49238`, ported this session, reads its
   argument's `+4` and returns the constant **8** -- it is handed the record, takes the object
   out of the second word this function stores, and reports the record's length, which is how a
   consumer advances past a record whose size is implied by its handler
   (`docs/command-queue.md`). `sub_82B33210` returns 8 from the same shape.
2. Slot **+28** of the object's own vtable is called with `r3 = object`, `r4 = 0`.
3. The object is freed: `free(allocator, object, 0)` through slot **+12** of
   `u32[u32[0x8307762C]+36]` -- the global System's allocator, the same
   `allocator->vtable[12](self, ptr, 0)` shape `sub_82B1E3F8`, `sub_82B28970`, `sub_82B34D60`
   and `sub_828E2E08` use.

Both constants computed as `((imm & 0xFFFF) << 16) + offset`: `0x82B50000 - 28104` =
`0x82B49238`, and `0x83070000 + 30252` = `0x8307762C`, the System pointer cell `sub_82B219E8`
reads too.

Two ordering facts kept deliberately:

- **Bug 1 is in this function.** `stw r5,204(r8)` publishes the advanced write offset *before*
  the two record words are stored, exactly the race `docs/command-queue.md` describes for
  `sub_82B28A00`. Reproduced bug for bug. This is a second producer for the same queue, so a
  fix that only locks `sub_82B28A00` does not cover the queue.
- `u32[0x8307762C]` is loaded into **r30, a callee-saved register, before the first `bctrl`**,
  so the destructor cannot change which System the free goes through. The native body keeps it
  in a local read at the same point and never touches r30.

`add r11,r9,r11` is 64-bit on two zero-extended loads; the record address is truncated at the
stores, as lifted.

Stores outside the frame: `{system+204, 4}`, `{record+0, 8}`.

## Unverifiable, and why

**Gate 1**, at depth 0, twice, and neither is avoidable on any path (`indirect: 2` in the
census):

- `0x82B1E4C0` calls vtable slot +28 of the object. `sub_82B1E3F8`, the sibling destructor at
  the previous address, shows what these entries do: install a vtable, then free `this` when
  bit 0 of `r4` is set. Here `r4 = 0`, so the reading is "destruct without freeing, the caller
  frees" -- an inference from the sibling's shape, not from this body.
- `0x82B1E4DC` is the free itself. Replaying it on rewound memory frees the object twice, and
  no window rewinds the allocator's book-keeping.

Both are reached unconditionally, so unlike `sub_828E2E08` and `sub_82B1F440` there is no
comparable path at all: `Windows()` returning false everywhere is the whole truth, not a
convenience.

## The write set it would have declared

The queue append alone is enumerable from entry state, which is worth recording because it is
the part with the bug:

    const uint32_t obj = ctx.r3.u32;
    const uint32_t pending = REX_LOAD_U32(obj + 4);
    if (pending != 0) {
      const uint32_t system = REX_LOAD_U32(pending + 16);
      const uint32_t off = REX_LOAD_U32(system + 204);
      spec.write(system + 204, 4);
      spec.write(REX_LOAD_U32(system + 48) + off, 8);
      spec.read(system + 48, 4);  spec.read(pending + 16, 4);
    }
    return false;   // parts 2 and 3 are two bctrls, one of them a free

Result mask `kReturnR3`: the function ends on the free's `bctrl`, so r3 is the allocator's
return value. No direct caller exists in the lifted corpus -- this address is reached through a
function pointer -- so nothing shows whether it is read.

## Unsure

- What `0x82B49238` does with the queued sub-object *in detail*. Its own port (written this
  session) reads the object from the record's `+4` and forwards it to `sub_82B48F28`, "unlink
  and release the object's children", which is consistent with part 1 deferring a child
  teardown -- but that chain is three indirect calls deep and nothing here observes its effect.
- Whether slot +28 is the destructor with a "do not free" flag. The `r4 = 0` plus an explicit
  free afterwards fits `sub_82B1E3F8`'s flags convention, and that is the kind of coherent
  story CLAUDE.md warns about -- it is consistent with two functions, not verified.
- What the object is. `+4` is a sub-object that owns a `System*` at its `+16`; the object
  itself has a vtable at `+0` and 514 destructions a boot, the same count as `sub_82B1E3F8`.

## Re-screened for a path split, 2026-09-12: cannot be split

Checked against the lifted body. Only the queue append is conditional; both `bctrl`s — vtable slot
`+28` at `0x82B1E4C0` and the free at `0x82B1E4DC` — are after `loc_82B1E4A4`, which the `beq` at the
top falls through to and jumps to, so every path reaches both. There is no entry state that reaches
neither, and the second is a free, whose effect no window rewinds. Left as `kPortGate1`, exactly as
the section above already concluded; this records that the split was looked for rather than assumed
absent.
