# sub_82B1F440 -- deactivate an audio object: release what it owns at +8, clear one stride-12 slot

`r3` = the object. No second argument is read. Returns the literal 0 on both paths (`li r3,0`
sits after the release call), so the value carries no information.

Two independent halves:

1. `u32[object+8]` is an owned instance. When it is non-null the function calls slot **0** of
   that instance's own vtable with the instance in `r3` -- the release/destructor entry -- and
   then stores 0 over the pointer. `sub_82B1D240` does exactly this inline at
   `skate3_recomp.66.cpp:68733` and then calls this function on the same object, which is why
   the null case is the common one: the caller has usually already torn the instance down.
2. When the byte at `+15` is non-zero, the byte at `+14` selects a slot in a stride-12 array
   and the two words at `slot+32` and `slot+28` are zeroed, **+32 first**. `addi r10,r11,28`
   computes the slot base into `r10` and nothing reads it -- dead code, not reproduced.

The index arithmetic is `rotlwi r10,r11,1 ; add r11,r11,r10 ; rlwinm r11,r11,2,0,29`, i.e.
`index*3 << 2`. Written as `index * 12` because a `lbz` index caps the product at 3060, so
neither the `0xFFFFFFFC` mask nor the 64-bit `add` can change the result. The final
`add r11,r11,r31` is 64-bit on zero-extended operands and the stores truncate, as lifted.

Stores, all outside the frame: `{object+8, 4}` on the release path; `{object + 12*u8[object+14]
+ 28, 8}` on the armed path. The frame stores (`stw r12,-8(r1)`, the two `std` spills, the
`stwu`) are the function's own and are excluded by the brief; the native body does not build a
frame, so r30/r31 are never touched and need no restoring.

## Unverifiable, and why

**Gate 1**, at depth 0: the `bctrl` at `0x82B1F474` goes through `u32[u32[object+8]+0]`, a
vtable slot loaded from memory the harness rewinds. Replaying it would run an unknown release
entry a second time -- a double free if it is one -- and the census confirms the reach
(`indirect: 1`, `gate1 fail, reason indirect, at sub_82B1F440, depth 0`). The call is
conditional, so the null-`+8` path *is* replayable; a path-dependent `Windows()` could return
true when `u32[object+8] == 0` and false otherwise, which would still compare the whole tail
(the armed test and the two stores). That is worth recording, not worth building: with 451
calls a boot and no way to steer which path they take, the evidence would be whatever the
game happens to do.

## The write set it would have declared

Both halves are enumerable from entry state, so the only false-maker is the callee:

    const uint32_t obj = ctx.r3.u32;
    if (REX_LOAD_U32(obj + 8) != 0) return false;         // the release call's writes
    spec.write(obj + 8, 4);                                // not reached on this path, but
                                                           // declared as the union
    if (REX_LOAD_U8(obj + 15) != 0)
      spec.write(obj + 12u * REX_LOAD_U8(obj + 14) + 28, 8);
    spec.read(obj + 8, 4);  spec.read(obj + 14, 2);

Result mask `kReturnR3`: the value is the constant 0. `sub_82B1F4C8` overwrites r3 with its own
`li r3,0` immediately after the call (`skate3_recomp.67.cpp:3819`), so no caller reads it
either.

## Unsure

- What the object is. `+8` is an owned instance released through vtable slot 0, `+12` is a
  signed byte mode `sub_82B1D240` clamps to 0..2, `+14` an index, `+15` a flag, and an array of
  12-byte slots reaches at least `+28`/`+32` past the indexed base. Nothing in
  `docs/rw_audio_structs.h` matches, so every offset here is a plain constant.
- Whether the stride-12 array is the same one `docs/command-queue.md` describes at
  `Player+0x54` (20 entries, stride 12, discriminator at `+0x5D`). The stride matches and the
  base does not, and `+8` being an owned, releasable instance rules out the Player layout,
  where `+8` is the `System*`. Treated as a different array.
