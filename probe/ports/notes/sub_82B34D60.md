# sub_82B34D60

Ninety-two lifted lines, no frame at all: a leaf that never calls anything directly, so it
uses only volatile registers (r8-r11) and ends in a `bctr`.

What it does: `r3` is a container holding two things, a list head at `+4` and an object at
`+8`. The function drains the list -- for every node it unlinks it from its owner's chain and
zeroes `+12`, `+16`, `+8`, `+22` (byte) and `+20` (halfword), in that order -- then tail-calls
a virtual on the object at `+8`. The node layout and the clear order are identical, field for
field and store for store, to the unlink in `sub_82B34BD0` (`prev +0`, `next +4`, live `+8`,
list token `+12`, owner `+16`, short `+20`, gain count `+22`); the difference is that
`sub_82B34BD0` unlinks one node and can fold its gains into the owner, while this one unlinks
all of them and folds nothing. It reads as the teardown counterpart: release every voice a
group holds, then hand the group itself back through the manager.

Arguments: `r3` = the container (read at `+4` and `+8`); `r4` = a manager whose `+36` holds
the object whose vtable slot `+12` is the release entry. `r4` is read only on the non-empty
tail path, which is why it looks unused in the census's store table.

Stores (all inside the loop, all on nodes reached from `r3+4`): `owner+4` (4), `next+0` (4),
`prev+4` (4), `node+12` (4), `node+16` (4), `node+8` (4), `node+22` (1), `node+20` (2).
Nothing outside its own (absent) frame besides those.

Bug reproduced as found: the loop re-reads `4(r3)` at the bottom rather than following
`next`, and a node whose token at `+12` is zero is skipped *without* being unlinked. If such
a node is ever at the head, the head never advances and the original spins forever. The
native body keeps that shape (`while` on a re-read head, `if` on the token) rather than
"fixing" it into a `next`-walk.

Gate verdict: **gate 1**, at depth 0 -- the function's own `bctr`. The target is
`**(*(r4+36))+12`, a vtable slot loaded during the call; replaying the body on rewound memory
would issue that call a second time, and whatever it reaches (this is a release path, so
almost certainly the allocator) is outside any window by construction. There is no path that
avoids it except the early `beqlr` when `8(r3)` is zero, and predicting that from entry state
would leave only the trivial case comparable.

Write set that would have been declared if it were comparable: not enumerable either, so it
is gate 2 as well. Walking the list from entry state is possible in principle -- follow
`node = 4(r3)`, then `0(node)` -- but the walk is unbounded (no count field anywhere on the
container) and the loop's own stores change the pointers it walks, so the set of nodes visited
is only known during the call. For a bounded cap of N nodes it would be, per node:
`{node+8, 12}` (covering +8, +12, +16), `{node+20, 3}` (+20 and the byte at +22) and
`{owner+4, 4}` for the head advance, plus `{next+0, 4}` and `{prev+4, 4}`; reads
`{node, 24}`. That is five spans a node against a 32-span budget -- six nodes and it
overflows, before counting the callee's writes.

Result mask: r3. On the early return it is the entry argument unchanged; on the tail path it
is whatever the virtual leaves, because `bctr` does not set `lr`. Callers of this address
are all indirect (no `bl 0x82b34d60` in the corpus), so whether r3 is actually read was not
determined -- r3 is declared to compare more rather than less.

Uncertain: the assumption that a node's `+16` owner is always `r3` itself. The unlink only
touches `owner+4` when `node == *(owner+4)`, so a foreign owner is handled correctly, but if
it were foreign the head at `4(r3)` would not advance and the loop would spin -- the same
non-termination hazard as the zero token. 244 calls a boot session and no hang observed, so
in practice it is always `r3`.
