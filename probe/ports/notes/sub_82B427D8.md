# sub_82B427D8

Linear-ramp writer, 742 lifted lines, 36 vector instructions, **4 calls per boot session** on
`RwAudioCore Dac` (tier C). One callee, `sub_82F52FB8`, a forward byte/word `memcpy(r3, r4, r5)`
that writes exactly `[r3, r3 + r5)` -- no allocation, no lock, no indirect call -- so gate 1 passes
at depth 1.

**STATUS: pending, and verification here will be almost nominal.** Four calls per boot is four
comparisons. A clean session says the one entry state the game happens to use is right; it says
close to nothing about the five other paths. Treat a green on this function as a smoke test, not as
evidence, and read the path list below before trusting it.

## What it does

Fills a 256-entry block of a float array with a piecewise ramp:

    out[i - first] = start                                for i < 0
                   = fma(float(i + 1), step, start)       for 0 <= i <= last
                   = end                                  for last < i <= first + 255

with `step = (end - start) / float(length)`, `last = min(first + 255, length - 1)`. The ramp
therefore reaches `end` exactly at `i = length - 1`, and the block always spans 256 indices.

Arguments: `r3` the output array, `r6` the starting index (may be negative), `r7` the ramp length,
`f1` the start value, `f2` the end value. `r4` and `r5` are `f1`'s and `f2`'s GPR parameter slots
and are never read as integers -- except by `subfe r3,r4,r4`, where `r4` is only a self-cancelling
operand used to turn the carry bit into an all-ones mask. Nothing in `docs/rw_audio_structs.h`
names the buffer, so there are no offset constants. Returns 1 in `r3`, hence `kReturnR3`.

## Six paths, and two rounding shapes for the same ramp

1. **Sub-zero bulk** (`first < 0`): `-(first/4)` units of 16 bytes filled with `start`, four
   `stvx128` per pass then one `stvx128` plus a replicating `memcpy`.
2. **Sub-zero remainder**: fewer than four floats left, one `stfs` plus a replicating `memcpy` of
   `4*left - 4` bytes.
3. **Alignment padding** (`loc_82B42958` / `loc_82B429A4`): up to three ramp samples written one at
   a time so the vector body starts on a four-sample boundary. **This is where the two rounding
   shapes are**: if `end - start >= ` the constant at `0x82165A10` the value is
   `fma(float(i+1), step, start)`; if it is less, the same sample is computed from the other end as
   `fnmsubs(float(length) - float(i+1), step, end)`. Algebraically equal, not equal in float. Both
   are written out; nothing shares code between them.
4. **Vector ramp body**, four vectors of four samples per pass, then odd groups one vector at a
   time. The index vector is `{i+1, i+2, i+3, i+4}` built through the frame and read back with the
   lane reversal, advanced by the four-lane constant at `0x8231BA90`.
5. **Scalar ramp tail** to `last`, one `fmadds` per sample.
6. **Flat fill** to `first + 255` with `end`: `count % 4` single `stfs` first, then `count / 4`
   units through the same 16-byte fill as path 1.

## Stores

| where | address | size |
|---|---|---|
| `stvx128` x4 per pass | `(cursor + 64k + {0,16,32,48}) & ~0xF` | 16 each |
| `stvx128` + memcpy | `cursor + 16*bulk`, masked, then `[+16, +16u)` | 16 + 16(u-1) |
| `stfs`/`stfsu` | `cursor`, advancing by 4 | 4 |

Everything else the census lists is inside the `stwu r1,-240(r1)` frame: `80(r1)` (the integer
transfer slot for `fcfid`), `96(r1)`..`140(r1)` (the four-lane splat scratch and the index
vector) and the `__savegprlr_26`/`__savefpr_27` spills. Not reproduced, not windowed. `r26`-`r31`
and `f27`-`f31` are saved and restored, so no preserved register changes; every vector register
touched is `v0`-`v13` or `v32`-`v63`, all volatile.

## Window

One contiguous run, `[out & ~0xF, out + bytes)`.

The masking is not cosmetic: the output pointer is **never checked for alignment**, and every
`stvx128` masks its address down to 16 bytes, so the run can start up to 15 bytes below `out`.
Over-covering there is safe (both sides are rewound to the same snapshot); under-covering would
not be.

`bytes` is **not 1024 in general**, which is the one thing about this function worth remembering:

- `first < 0` adds a flat prefix of `-first` samples *on top of* the 256-entry block, so a very
  negative `first` makes the write set arbitrarily large. `Windows()` computes it and lets the
  hook's oversize check reject the call rather than guessing.
- If the ramp has already run out (`length - 1 < first`), `span = last - index + 1` is negative,
  `groups = span/4` is negative, both vector loops are skipped -- but `r11` is still advanced by
  `4*groups`, i.e. *backwards*. The flat fill then starts from an index below the one the cursor
  actually sits at and writes more than 256 entries. Worked example: `first = 8, length = 3` gives
  `groups = -1`, `tail_index = 4`, and a 260-float (1040-byte) write. The original does that; the
  port does it too, and `Windows()` predicts it.

So `Windows()` replays the same integer control flow the body does -- all of it decided by the
entry registers, none of it by memory -- and adds up the bytes each section writes. It returns
false only on the two address-space-wrap guards, which cannot fire for a real buffer.

## Uncertainties

- **Almost no verification is available.** Four calls per boot, one call site unknown (the census
  has not dumped this function's entry registers yet -- it is not on a manifest). Which of the six
  paths those four calls take is unknown, and the two rounding shapes of path 3 are mutually
  exclusive per call, so a single session can exercise at most one of them.
- **The `.inc` is not on any manifest**, so nothing is armed yet;
  `audio_ports/ports_68a.manifest.inc` is generated by `probe/ports/queue.py manifests`.
- The two image constants are loaded, not assumed. `0x82165A10` is almost certainly `0.0f` (it
  selects ascending versus descending) and `0x8231BA90` almost certainly four copies of `4.0f` (it
  advances the index vector by four), but neither was read out of the image -- there is no dumped
  image in this tree -- and the port does not need them to be.
- The splat vectors are `simde_mm_set1_ps(float(x))` rather than four `stfs` into the frame
  followed by `lvx128`, and the index vector is a `setr_ps` rather than four `stfs` plus a
  lane-reversed load. Both agree only if the guest `r1` is 16-byte aligned. `r1` here is
  `r1_caller - 240`, and 240 is a multiple of 16, so it is aligned whenever the caller's is;
  `sub_82B3D0A8`'s census shows `r1 = 0x707BF820` on this thread. Argued, and observed one frame
  up, not observed here.
- The index vector's lane order is the one place a silent sign error would hide: the guest writes
  `float(i+1)` at `96(r1)` through `float(i+4)` at `108(r1)`, and `lvx128`'s byte reversal puts the
  word at `108` in lane 0. `simde_mm_setr_ps`'s first argument is lane 0, so the port passes
  `i+4` first. Getting this backwards would reverse each group of four samples -- visible as a
  memory diff, not as a crash.
- If a caller ever placed the output buffer inside this callee's own 240-byte frame, the spills and
  the splat scratch would land inside the declared window and the native body (which uses none of
  it) would differ. Not plausible; recorded because it would present as a memory diff with no
  arithmetic explanation.
