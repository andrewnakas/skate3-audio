# sub_82B443F8

Non-leaf, 122 lines, 578,783 calls in the boot session, all on `RwAudioCore Dac`.

Args: r3 = owner (`+28` -> buffer plan, `+48` last cleared count), r4 = fill state
(singles at `+40`/`+44`/`+48`, byte at `+69`), r5 = channel layout (`+42` = u8 channel
count), r6 = count in frames. Returns 1 when it cleared, 0 when there was nothing to do.

Body: clamp the limit at `+48` up to the floor at `+40`; reload `+48`, and if the position
at `+44` is **not** below it, zero the byte at `+69` and return 0. Otherwise add the count
(as a single) to `+44`, then for each of `[r5+42]` channels call `sub_82EE5E80(plan_buffer +
4*stride*i, 0, 4*count)` -- memset -- and finally publish the count at `r3+48` and return 1.
Plan fields: `+4` = first channel's buffer, `+14` = u16 frame stride between channels.

Stores: `stfs [r4+48]` 4 (conditional), `stb [r4+69]` 1 (idle path only), `stfs [r4+44]` 4,
`stw [r3+48]` 4, plus the callee's `4*count` bytes per channel. The only non-frame stores.

Callee: `sub_82EE5E80` is the XDK vector memset -- stbu loop under 16 bytes, then
stvlx/stvx128/dcbzl/stvrx. It writes exactly `[r3, r3+r5)`; the dcbzl lines are 128-aligned
only after the run has been aligned past them and are then fully overwritten. No locks, no
allocation, no indirect calls (census transitive gate 1: pass), so it is called through
`GuestCall` on the live context.

Windows: the union of both paths -- `{r4+44, 8}`, `{r4+69, 1}`, `{r3+48, 4}` and one span
per channel. Everything derives from entry state: the count is r6, the channel count, plan
pointer, buffer and stride are all readable before the call. Returns false when the plan or
the buffer is null, when a channel span would wrap 2^32, when the channel count exceeds 24
(4 scalar spans + channels must fit kPortMaxSpans), when `4*count*channels` exceeds the 32 KB
cap, or when any clear overlaps the loop's own control words (`plan+4..15`, `layout+42`),
which the original re-reads every pass and which would therefore move the later targets.

Gates: 1 pass, 2 pass (with the predicates above), 3 pass (no timebase), 4 pass -- the
caller reads the 0/1 in r3, so the mask is `kReturnR3`.

Unsure: nothing about the float fields is named anywhere, so `+40/+44/+48` are read as
floor/position/limit purely from the arithmetic. If the census shows most calls skipped as
"not enumerable", the likely cause is the 32 KB total cap on wide multichannel clears; the
cheap fix is to predict the idle path from the entry floats (the clamp is reproducible
before the call) and declare only the 5 idle-path bytes then. That prediction was written
out deliberately in favour of the plain union.
