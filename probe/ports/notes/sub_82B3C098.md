# sub_82B3C098

Leaf VMX128 kernel, 356 lifted lines, 69 vector instructions, **950,911 calls per boot session**
on `RwAudioCore Dac`. No callees, no imports, no indirect calls, no timebase.

**Role: a gain-ramped copy of a fixed 256-single block.** `r3` = destination, `r4` = source,
`f1` = the gain at sample 0, `f2` = the gain increment per sample. It writes
`dst[k] = src[k] * gain(k)` for k in 0..255, where `gain(k) = f1 + k*f2` for the first 64
samples and `f1 + f2*kRampSpan` thereafter. The length is not a parameter: `r31 = src+256` and
`r30 = src+1024` are both literal, so the call always touches exactly 1024 bytes in and out.

The per-lane starting gains come from four scalar singles the original writes to its own stack
frame at `-96..-81(r1)` and reloads with one `lvx128`: `f1`, `f1+f2`, `fmadds(f2,kLane2Scale,f1)`
and `fmadds(f2,kLane3Scale,f1)`. The eight 16-byte pool vectors at `0x8231BA20..0x8231BA9F`
scale the step per 16-byte group, and the one at `0x8231BA50` is the whole-block increment.
Consistent with `kStepScale = 4.0`, `kLane2Scale = 2.0`, `kLane3Scale = 3.0`,
`kRampSpan = 64.0` and the eight vectors being splats of 1..8 (the same table and the same
plumbing appear in `sub_82B44D18`, which corroborates the mapping) — but **those values are
inferred from the register plumbing, not measured**: no image dump was taken for this port and
the body assumes none of them, loading every one through the guest map.

## Stores

- `dcbzl r0,r11`, once per 128-byte block, 8 blocks: `[(r3 + 128i) & ~127, +128)`.
- `stvx128`, eight per block, 16 per loop body, 64 in all: `[((r3 + 128i + 16g) & ~0xF), +16)`.
- `stfs`, twelve of them, all to `-112..-81(r1)`: the function's own frame below `r1` (it has no
  `stwu`; `__savegprlr_23` puts the register saves at `-80..-1`). Not windowed, per the brief.
  The native body does not write them at all — it builds the two vectors in registers, which is
  exact because `stfs` writes big-endian and `lvx128` reverses all sixteen bytes, so the two
  reversals cancel and the single at `-96` is host lane 3.

## Window

One span, `[r3 & ~127, (r3 & ~0xF) + 1024)`. Both write shapes are contiguous across the eight
blocks because `128i` and `16g` are multiples of their respective alignment masks, so the
masking factors out of the loop; `r3 & ~127` is the lower of the two starts. At most 1136 bytes,
exactly 1024 when `r3` is 128-byte aligned. Reads declared: the 1024-byte source, the four
rodata singles and the two 64-byte halves of the pool table.

## Gates

All four pass. Gate 1: leaf, nothing to replay. Gate 2: the write set is a fixed 1024 bytes at
`r3`, known from entry. Gate 3: no `mftb`. Gate 4: the result is memory.

**STATUS `verified`: zero divergence over 902,638 calls in one boot session**
(`probe/ports/queue.json`, `last_divergence: null`; promoted by the port loop, not by hand).
That result also settles three things this port had to reason out rather than measure, and
`sub_82B44D18` reuses all three: the `stfs`-then-`lvx128` lane order (the single at `-96` is
host lane 3), the decision not to write the guest stack at all, and the need to leave the
clobbered preserved VRs behind.

Result mask `kReturnNone` — the function is void and leaves `r3 = 64` as scratch. The real extra
signal is free: **the original clobbers v28..v31, which are in the ABI-preserved range the
harness compares unconditionally**, and it never saves them (`__savegprlr_23`, no
`__savevmx_*`). So four group-multiplier vectors are compared on every call whether or not the
mask names anything. The native body reproduces them explicitly at the end.

## Unsure

- Whether `r3` is always 128-byte aligned in practice. The window covers both cases, so this
  only affects the declared span length, not correctness.
- Rule 4 of `docs/vmx128-exactness.md` applies to the 16 `vmaddfp` and the 16 `vmulfp128` sites:
  if a NaN ever reaches the source buffer or the gain, which operand's payload survives is a
  clang register-allocation decision at each site and cannot be matched from source. Operand
  order is kept identical to the lifted lines, which is the best that can be done here. A
  divergence that appears only on some calls should be checked for NaN in the source run first.
