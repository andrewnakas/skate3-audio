# sub_82B34E08

**Shadow-verified clean**, 727,030 calls on the verifying session (the screening census put it at
860,783 on a longer boot).

Non-leaf, 176 lines, on `RwAudioCore Dac`. No caller appears in the
lifted sources (`grep 82B34E08` finds only its own definition and labels), so it is reached through
a function pointer; it ends `li r3,0` on one path and `li r3,1` on the other, so the mask is
`kReturnR3`. Callees: `sub_82EDF460` (memcpy), `sub_82EE5E80` (memset), `sub_82B3C668` (the verified
delta-fold port). All three go through `GuestCall` on the live context. Census gate-1 verdict: pass,
closure of 5 including `82EE7460` and `82F52FB8` inside memcpy -- no lock, allocation, release,
indirect call or timebase anywhere in it.

Arguments: r3 = the mixer-side object, r4 = a two-entry row-owner pair. Nothing in
`docs/rw_audio_structs.h` names either. Fields used, all plain offsets: `u8 +42` channel count
(reloaded at every single use), `rw_ptr +60` accumulator base, `float[] +64` the delta array handed
to sub_82B3C668, `u16 +96` a byte offset into the accumulator naming a flag word, `u8 +98` the
delta-pending flag, `u8 +165` where 0xFF forces the flush. On the pair: `+32` the owner this call
uses (read *before* the swap), `+28` the other. On the owner: `+4` row base and `u16 +14` row pitch
in singles -- sub_82B3C668's `kRowBase`/`kRowStride`, same names, same `mullw`/`rlwinm` row
arithmetic, which is what makes its 64-byte rows a subset of the 1 KB spans declared here.

Behaviour: (a) if the flag word at `u32[+60][u16[+96]]` is zero AND `u8[+98]` is zero AND
`u8[+165] < 255`, return 0 without one store; (b) otherwise swap `+28`/`+32` on the pair;
(c) re-read the flag word -- non-zero copies 1024 bytes per channel out of `accumulator + 1024*i`
into `row_base + 4*(stride*i)` then zeroes the flag word, zero instead memsets those same rows to
0; (d) if `u8[+98]`, call sub_82B3C668(owner, self+64, channels) and clear the flag;
(e) memset the whole accumulator, `channels * 1024` bytes (`rotlwi r5,r11,10` on a byte is `*1024`);
return 1.

Stores: `stw` at pair+32 and pair+28 (4 each); `stwx` 4 at `accum + u16[+96]`; `stb` 1 at self+98;
plus, through the callees, 1024 bytes per channel at each row (memcpy or memset), the first 64
bytes of each row and `4*channels` at self+64 (sub_82B3C668), and `1024*channels` at the
accumulator. Both CRT routines were read through to confirm they write exactly `[dst, dst+n)`: the
leading `stvlx128` writes only the bytes to the next 16-boundary, each `dcbzl` block is 128-aligned
*inside* the range (the preceding 16-byte loop is what aligns the cursor, and when it is capped
short the block count is zero), and the trailing `stvrx128` writes only `[end-r29, end)`.

Window: the early return is predicted exactly, because all three of its inputs are entry state --
the flag word is loaded before the swap. Everything after it is declared as the **union of all
paths** rather than predicted, since both remaining branch conditions are re-reads that a write
could alias. Spans: pair+28 (8), the flag word (4), self+98 (1), self+64 (4*channels), the rows
(one merged span when the byte pitch is 0 or <= 1024 -- the live pitch is exactly 1024, so they abut
-- otherwise one span per channel), and the accumulator (1024*channels). Returns false on: a span
that wraps 2^32, more than 32 spans, more than `kPortWatchCap` bytes, `channels > 32`, index math
that wrapped the monotone union, and -- the real gate-2 risk -- a write span covering any of the
four re-read fields `self+42`, `self+60`, `owner+4`, `owner+14`.

Gates: 1 pass (census verdict, whole closure). 2 pass **conditionally**, per the checks above; the
census flagged the `stwx` as gate2_suspect because its base is derived, but both halves of the
address (`u16 +96` and `u32 +60`) are loaded from entry state before any store. 3 pass. 4 pass
(r3 = 0 or 1).

Added after the clean session: `if (owner == 0) return false;` before `Windows()` loads the row
fields. It cannot affect the promoted path (`Native` never consults `Windows()`) and cannot hide a
divergence -- it only skips a comparison. It is there because `Windows()` runs *before* the original,
so a null owner would fault in the window builder rather than in the lifted body. Over 727,030 calls
it never fired, which is also why it is not part of what was verified.

Unsure: (a) the byte-cost per call is ~2052 * channels + 13, so at 6 channels every one of the
860,783 calls snapshots and rewinds ~12 KB; that is inherent to the function, not a window choice,
and it will slow an armed session noticeably. No `SAMPLE_SHIFT` is used, matching the other hot
ports in this directory. (b) The meaning of `u8 +165` and of the flag word inside the accumulator is
unread -- the `stwx` clears a word that the closing memset then clears again, which is consistent
with `u16 +96` being an offset into that same buffer but is not established. (c) `self+64 + 4*channels`
reaches past +96/+98 once channels >= 9, so sub_82B3C668 would overwrite the offset and the flag;
harmless here because both are read before it runs, but worth knowing if a divergence appears with a
high channel count.
