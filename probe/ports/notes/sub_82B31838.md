# sub_82B31838 — mix a source's channels into the bus blocks for one block

Arguments: r3 the mixer object, r4 the command record, r5 a flag byte (`clrlwi r11,r5,24`).
Returns 1 in r3 on both exits. Callees: `sub_82B46810` (ramped mix, itself calling the verified
`sub_82B44D18`) and `sub_82B44B20` (flat mix, already ported and verified) — both through
`GuestCall`, never `__imp__`. 755,028 calls in a boot session, on `RwAudioCore Dac`.

Shape: `+116` is a dirty mark. Forced, or already dirty, and the call snaps `+112` (the gain the
buses were last mixed at) to `+52` (the target) and clears the mark, which makes the later
`+52 != +112` test false and the mix flat. No buses (`+78 == 0`) and it re-marks dirty and returns
at once. Otherwise: `[+64 + u16 at +76] += 1`; build a channel-pointer array at frame+80 from
`[[r4+28]+4]` strided by `[[r4+28]+14] << 2`, `+41` entries; build a bus-pointer array at
frame+112 from `+64` strided 1024, `+78` entries; then dispatch on the byte at `[[r3+12]+72]` —
1 ramps from the pool zero to `+112`, 3 ramps from `+52` to the pool zero, anything else ramps
`+112 -> +52` or, when they are equal, walks the routing row inline calling `sub_82B44B20` per
entry at `route_gain * +52`. Finally `+112 = +52` and `+80+4i = [channel_i + 1020] * +52`.

Stores (all cited in the file): `+112` single (twice), `+116` byte (twice), the counter word at
`[+64] + u16(+76)`, `+80 + 4i` for i in [0, `+41`), and — through the two mixers — 1024 bytes at
each bus block the routing row names. The frame (back chain at r1-208, the two arrays) is this
call's own and is not windowed; Native still moves r1 to -208 because the callees allocate below
r1 and would otherwise land on the arrays they are handed.

Window rationale: the destination of every mix is one of eight bus pointers this call builds
itself — the entry byte's destination field is three bits — so the write set is at most eight
1024-byte blocks regardless of the bus count, ~8.4 KB total. Which blocks is a walk of rodata
(`{first,last}` pair at 0x820ED700, entry bytes at 0x820ED780, gains at 0x820ED6C0), readable
before the call and identical on every mixing path. Each block's span starts at `dst & ~0xF`
because `sub_82B44D18` masks the low four address bits off every `stvx128`; `sub_82B44B20` writes
`[dst, +1024)`; one span covers both. Addresses were computed as `((imm & 0xFFFF) << 16) + off`.

`Windows()` returns false when: `+64` or `[r3+12]` or the source list is null (the original faults
there); `8*channels + buses < 9`, so the row index is negative; a row longer than 64 entries; an
entry naming a bus or channel index past the array actually built (which would send a mixer at an
uninitialised frame word); or `channels > 8` / `buses > 24`, past what the 208-byte frame holds —
there the original overruns its own arrays and then the caller's frame, which no window can
declare. All of these are decided from entry state.

Gates: 1 passes (census: no indirect call, no lock, no import anywhere in the closure; both
mixers are ported and verified). 2 passes with the guards above. 3 passes (no `mftb`). 4: r3 is
always 1, declared `kReturnR3`.

Unsure: whether the u16 at `+76` is a byte offset that can land inside a mixed bus block (it is
windowed either way, and the increment happens before the mixing on both sides); the meaning of
the mode byte values 1 and 3; and whether the four gain constants at 0x820ED6C0 are only four
(16 bytes are declared as read, which is what a 2-bit index can reach).

Volume: 755k calls x ~8.4 KB of window copied three times per comparison. If the harness is too
slow armed here, `SKATE3_PORT_EX(82B31838, ..., 6)` compares one call in 64.
