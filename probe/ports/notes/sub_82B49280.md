# sub_82B49280

- Role: **grow-and-priority-insert** into an owner's handle array. `u32 f(object*)`, returns 1 on
  success and 0 when the allocation failed. 241 lifted lines, two direct callees
  (`sub_82EDF460` copy, `sub_82F4DC60` move), two own `bctrl`. 2,210 calls per boot on
  `RwAudioCore Dac`; reached only through `sub_82B49210` and `sub_82B48440`.
- Structures. `owner = REX_LOAD_U32(object + 16)`, reloaded before very nearly every access:
  `owner+16` list head, `owner+36` allocator (vtable at +0), `owner+108` the entry array,
  `owner+272` u32 high-water mark, `owner+276` u32 first-grow capacity, `owner+280` u16 count,
  `owner+282` u16 capacity. An entry is 8 bytes: `{u32 object, u32 payload}`. On the object:
  `+64` the payload word, `+71` the type byte (`sub_82B48F28` dispatches on it), `+73` the
  UNSIGNED priority, `+76` a flag, `+28`/`+32` an embedded list node (`next`, `prev`).
- Flow:
  1. `count < capacity` unsigned -> skip straight to the insert.
  2. Otherwise grow: `growth = capacity ? 32 : [owner+276]`; **reload** the capacity and form
     `new_capacity = capacity + growth` as a 64-bit add; `bytes = new_capacity * 8`
     (`rlwinm ...,3,0,28`, so modulo 2^32 with the low three bits cleared),
     `old_bytes = rotlwi(capacity, 3)`. Call the allocator vtable's **+4** with
     `(allocator, bytes, 0x820ED918, 0, 16, 0)`.
  3. Non-null: `sub_82EDF460(new, [owner+108], old_bytes)`, then the allocator vtable's **+12**
     with `(allocator, [owner+108], 0)` -- the **free of the old array**. Then
     `stw new -> owner+108` and `sth new_capacity -> owner+282`, each after its own reload of
     `object+16`.
  4. Null: `stb 2 -> object+71`, `stw 1 -> object+76`, then push the node at `object+28` onto
     `owner+16`: `object+32 = 0`, `object+28 = head`, and if the head (**read a second time**,
     after those two stores) is non-null, `head+4 = object+28`; finally `owner+16 = object+28`.
     Returns 0.
  5. Insert: read the count ONCE for the tail arithmetic, then walk entries from index 0 while
     `this_priority > entry_object_priority` (unsigned), the bound `owner+280` **reloaded every
     iteration** while the count used by the `subf` is the first read. `offset = index * 8`,
     `tail = used - index` (64-bit `subf`), `sub_82F4DC60(array+offset+8, array+offset, tail*8)`.
     Then `stwx object -> array[offset]`, `stw [object+64] -> array[offset]+4`,
     `sth count+1 -> owner+280` (low halfword only: 0xFFFF wraps to 0), and if the reloaded count
     exceeds `owner+272` unsigned, store it there. Returns 1.
- Stores, in order: `stw owner+108`, `sth owner+282` (grow path); or `stb object+71`,
  `stw object+76`, `stw object+32`, `stw object+28`, `stw head+4`, `stw owner+16` (failure path);
  then `stwx array+offset`, `stw array+offset+4`, `sth owner+280`, `stw owner+272` (insert path).
  Plus the callees' own writes: `sub_82EDF460` fills `bytes` of the new block, `sub_82F4DC60`
  rewrites `tail*8` bytes of the array from `offset+8`.
- Result mask: `kReturnR3`. Both returns are literals (1 and 0) and `sub_82B49210` /
  `sub_82B48440` do read them.
- Gate: **1, fail**, depth 0, indirect 2. `bctrl` 0x82B492EC is the allocator's +4 allocate and
  `bctrl` 0x82B49328 its +12 free; a replay on rewound memory allocates a second block and frees
  the same pointer twice. `docs/shadow-harness.md` names exactly these two as why transitive
  screening exists (they kill `sub_82B48440` two levels up and `sub_82B49210` one level up).
  `Windows()` returns false. Gate 2 also fails independently: seven of the thirteen stores have a
  base reloaded *after* the allocation, so the array address is not knowable from entry state, and
  `head+4` is one indirection past it. Gate 3 passes (no `mftb`).
- Unsure:
  - Which list `owner+16` is. `sub_82B48F28` unlinks the same embedded node from `owner+20` or
    `owner+28` selected by the type byte at `object+71`, and this path writes `+71 = 2` while
    linking unconditionally into `owner+16`. Either there are more than two heads on the owner or
    `2` means something other than a head index; not resolved, and nothing here reads it back.
  - `0x820ED918` is only passed through, never dereferenced; the shape of the allocate call
    (`bytes, tag, 0, 16, 0`) says the 16 is probably an alignment, but that is inference.
  - The array is a parallel `{object, payload}` list rather than an array of structs; whether
    `object+64` is a handle, a generation or a sort tiebreak is not determined here.
