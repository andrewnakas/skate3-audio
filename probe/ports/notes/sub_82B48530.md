# sub_82B48530

Lifted: `skate3_recomp.68.cpp:36568`, 394 lines. The System drain, named as such in
`docs/rw_audio_structs.h` -- every `rw_system` offset it touches is already documented there, which
made this the one port of the five where no field had to be guessed. 18,685 calls per boot session
on `RwAudioCore Dac`. `docs/shadow-harness.md` lists it among the original Phase 2 gate-1
candidates; this confirms the verdict and says where.

## Arguments

`r3` = the `rw_system`. No other argument.

## Shape: five phases in four lock brackets

| phase | lock | work | timing lands in |
|---|---|---|---|
| 1 | held | `sub_82B48A50(scheduler, 0)` -- tick bucket 0 | held in r26 to the very end |
| 2 | **released** | the `+0x14` fade pass (below) | `+0xF4`, stored |
| 3 | held | `sub_82B482F8(system)`, `sub_82B48440(system)` | `+0xF4`, accumulated onto phase 2 |
| 4 | held | drain the command ring | `+0xE8`, stored |
| 5 | held | `sub_82B48A50(scheduler, 1)` then `sub_82B39820` twice | `+0xEC` = phase 5 + phase 1 |

Four `Lock`/`Unlock` pairs, and phases 4 and 5 are separated by an unlock immediately followed by
a lock with nothing in between.

The fade pass: `record = node - 28` (the list node is embedded 28 bytes into the record), then
`if (record->+0x30 < record->+0x28) record->+0x30 = record->+0x28;` and
`if (!(record->+0x2C < record->+0x30)) sub_82B49100(record, 3);`. The `+0x30` load in the second
test is a genuine reload -- the store above may have just changed it. The next pointer is loaded
**before** the float work, so a record that unlinks itself inside `sub_82B49100` does not break the
walk.

The command drain: `cursor = system->+0x30`, `end = cursor + system->+0xCC`, and while
`cursor < end` call `(*(fn**)cursor)(cursor)` and advance by the return value -- the variable-length
ring `docs/rw_audio_structs.h` describes. The bound is computed once and **not** re-read, so a
handler that appends is not seen by this drain. Afterwards `+0xCC` is re-read for the `+0xD0`
high-water compare, then reset to zero, and `+0x100` is incremented.

## Gate verdict

**gate-1, at depth 0, nine indirect calls.** Eight of them are the lock/unlock hooks: each bracket
reads `+0x54` (or `+0x58`) and, when it is non-zero, calls it through `mtctr`/`bctrl`; only the
null case falls back to `RtlEnterCriticalSection` / `RtlLeaveCriticalSection`. Either way the
function *is* the lock, so the replay problem is `sub_82B4FAF8`'s: a second acquisition from the
same thread is kernel (or hook) state that no memory rewind undoes. The ninth is the command
handler, called through the record's own first word -- an arbitrary function, and on this path the
`EVENT_PLAY` / `EVENT_STOP` / `EVENT_SUBMIT` handlers that allocate and signal.

It **also fails gate 3**: `sub_82B1F7E8` is a bare `mftb`, called nine times here, and its
differences are stored into three fields. Even with the locks and the handlers made replayable,
the stored elapsed values could never compare equal. Either label alone is sufficient;
`kPortGate1` is used because that is the one the census reports.

Gate 2 would fail too: the fade pass writes `node-28+48` for every node on an unbounded list, and
the command drain's per-record writes are whatever the handlers do.

## Return mask

No `li r3,...` on either exit. r3 is whatever the final unlock left -- `RtlLeaveCriticalSection`'s
result or the hook's. Functionally void. `kReturnR3` is declared because a gate-labelled port with
`kReturnNone` and no `spec.write()` trips lint check 5; nothing is compared either way.

## Uncertainties

- On the hook arm r3 is **not** set before the `bctrl`. The hook is entered with whatever the
  previous call left there: the System at the first bracket, a `mftb` reading at every later one.
  So the hook takes no argument and must find the lock itself. Read off eight sites, all agreeing.
- `+0xEC` is inside the `_padec` gap in `docs/rw_audio_structs.h`. Naming it `kTimeScheduler` is
  this port's reading, from one site: it receives phase 5's elapsed plus phase 1's, and those two
  are the two `sub_82B48A50` bucket ticks.
- The three floats at `+0x28`/`+0x2C`/`+0x30` of the list record are named for the comparisons they
  take part in. Whether `+0x30` is a fade gain, a timer or a distance was not established, only
  that it is clamped up to `+0x28` and that reaching `+0x2C` fires `sub_82B49100(record, 3)`.
- `subfic r11,r30,0 ; subfe r8,r10,r10 ; and r3,r8,r9` is the null-safe downcast idiom and the
  mask is always all ones here, because both the entry test and the loop test exclude a null node.
  It is reproduced anyway: the `and` is 64-bit and `addi r9,r30,-28` goes negative for a node
  address under 28, which the mask would then not clear. `subfic`/`subfe` also write XER[CA],
  which this port does not model -- it is volatile and outside the compared set.
- What `sub_82B39820` takes is a guess only in its base: the argument is the scheduler *base*
  advanced by 32, not `buckets[0]` at `+0x10` advanced by the same documented 0x20 stride.
