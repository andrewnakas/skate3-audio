# sub_82B44D18

Leaf VMX128 kernel, 402 lifted lines, 84 vector instructions, **19,417 calls per boot session**
on `RwAudioCore Dac`. No callees, no imports, no indirect calls, no timebase.

**Role: the accumulating sibling of `sub_82B3C098`.** `r3` = destination, `r4` = source,
`f1` = the gain at sample 0, `f2` = the gain increment per sample. It computes
`dst[k] += src[k] * gain(k)` for k in 0..255, where `gain(k) = f1 + k*f2` for the first 64
samples and `f1 + f2*kRampSpan` thereafter. Same four rodata singles, same eight pool vectors
at `0x8231BA20..0x8231BA9F`, same two-loop shape, same literal 1024-byte extent — the only
differences are that every group is a `vmaddfp` into the destination rather than a `vmulfp128`
over it, and that there is no `dcbzl` (there is nothing to discard: the old contents are read).

Reading the two kernels together is what settles the constant table. The registers are allocated
differently but the roles line up exactly, and the plumbing is only consistent if
`kStepScale = 4.0`, `kLane2Scale = 2.0`, `kLane3Scale = 3.0`, `kRampSpan = 64.0` and the eight
pool vectors are splats of 1..8 (laid out 5,6,7,8 at `BA20..BA50` then 1,2,3,4 at
`BA60..BA90`). **Still inferred, not measured** — no image dump was taken, and the body assumes
none of it: every constant is loaded through the guest map.

## Stores

- `stvx128`, eight per block over eight blocks, 64 in all: `[((r3 + 128i + 16g) & ~0xF), +16)`.
  Nothing else touches guest memory outside the frame.
- `stfs`, twelve of them, all to `-112..-81(r1)`: the function's own frame below `r1` (no `stwu`;
  `__savegprlr_24` puts the register saves at `-72..-1`). Not windowed, per the brief. The native
  body does not write them at all — it builds the two vectors in registers, which is exact
  because `stfs` writes big-endian and `lvx128` reverses all sixteen bytes, so the two reversals
  cancel and the single at `-96` is host lane 3.

The ramp loop's store order is **not** ascending: `+0, +16, +32, +48, +96, +64, +80, +112`.
Reproduced literally (`kRampStoreOrder`) rather than sorted — a store order only matters when
the buffers alias, and this port is not the place to decide that they cannot.

## Window

One span, `[r3 & ~0xF, +1024)`. Contiguous because `128i` and `16g` are multiples of 16, so the
`stvx128` address masking factors out of both loops. Reads declared: the 1024-byte source, the
four rodata singles and the two 64-byte halves of the pool table. The destination is read as
well (it accumulates), but it is inside `windows`, so the harness snapshots it for replay
anyway.

## Gates

All four pass; STATUS `pending`. Gate 1: leaf, nothing to replay. Gate 2: a fixed 1024 bytes at
`r3`, known from entry. Gate 3: no `mftb`. Gate 4: the result is memory.

Result mask `kReturnNone` — the function is void and leaves `r3 = 32` as scratch. The extra
signal is free and large here: **the original clobbers the entire ABI-preserved vector range
v14..v31 and saves none of it** (`__savegprlr_24`, no `__savevmx_*`), and the harness compares
that range on every call. v14..v21 keep the eight group multipliers; v22..v31 keep the *last
ramp block's* intermediates, which survive because the hold loop only writes v0..v13. The native
body reproduces all eighteen explicitly at the end, which is why the arrays are declared outside
the ramp loop.

Mapping, for whoever reads a divergence report: v22 = the destination read at `+48` of the last
ramp block, v23 = the same at `+32`, v24 = the accumulated result for group 1, v25 = group 0,
v26 = the gain the third block would have started from, and v27..v31 = the group gains for
groups 7, 6, 5, 4, 3 in that order.

## Unsure

- The inferred constant values above. Nothing in the port depends on them; they are here so the
  next reader does not re-derive the shape from scratch. An image dump would settle them.
- Rule 4 of `docs/vmx128-exactness.md` applies to all 64 accumulate `vmaddfp` sites and the 16
  ramp ones: if a NaN ever reaches the source, the destination or the gain, which operand's
  payload survives is a clang register-allocation decision per site and cannot be matched from
  source. Operand order is kept identical to the lifted lines, which is the best available. A
  divergence on only some calls should be checked for NaN in the source or destination run
  first.
- The sibling `sub_82B3C098` came back **verified, zero divergence over 902,638 calls**
  (`probe/ports/queue.json`) with the same stack-vector idiom, the same lane-order derivation
  and the same preserved-VR reproduction. That is direct evidence for the parts of this port
  that are shared, and it leaves the accumulate FMAs and the non-ascending store order as the
  only genuinely new surface.
