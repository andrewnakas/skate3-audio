# sub_82B42C98

1006 lifted lines, 99 vector instructions, **39,553 calls per boot session**, `RwAudioCore Dac`.
One callee, `sub_82F52FB8`, a forward memcpy that touches only r0 and r3-r10 — no vector register,
no non-volatile GPR. Reached only from `sub_82B238A8`, which dispatches to it on `state[0x72]`; it
is the square-root sibling of the linear `sub_82B427D8` and takes the same five arguments.

**Role.** Writes one 256-entry block of a float envelope with a square-root curve.
`step = (end - start) / sqrt(float(length))`, and index i in `[0, last]` gets
`fma(sqrt(i + 1), step, start)` — reaching `end` exactly at `i = length-1` — or, when the ramp
descends, `end - sqrt(length - (i + 1)) * step`. `last = min(first + 255, length - 1)`. Indices
below zero are flat at `start`, indices above `last` flat at `end`. Ascending or descending is
picked by `fcmpu` of the delta against the f32 at **0x82165A10**, the same word the sibling loads.

Arguments: `r3` out, `r6` first (may be negative), `r7` length, `f1` start, `f2` end. `r4`/`r5` are
f1's and f2's GPR slots and are read only by `subfe r3,r4,r4`, which uses r4 as a self-cancelling
operand to turn a carry into a mask. Nothing in `docs/rw_audio_structs.h` names this buffer.

Shape: a 16-byte-unit fill plus a replicating memcpy for the sub-zero span, up to three scalar
padding samples to reach a four-sample boundary, a software-pipelined vector body (four groups of
four per pass) then `groups - bulk` single vectors, a scalar ramp tail, and a one-at-a-time prefix
plus a second unit fill for the flat end.

## The square root

Five sites, one shape: `e = vrsqrtefp128(x)`, `c = vnmsubfp(x*0.5, e*e, 0.5)`,
`r = vmaddfp(e, c, e)`, `mask = vcmpeqfp(c,c) XOR vcmpeqfp(e,e)`, `out = vsel(x*r, x, mask)`. The
mask is set where exactly one of `e` and `c` is a NaN, which is `x == +0` (e = +inf, c = 0.5 - NaN)
and `x == +inf` (e = +0, c = NaN) — the two arguments the estimate cannot refine and the two that
are their own square root, so selecting `x` is the fixup. Ported as the helper `SqrtVector`, with
every `vmulfp128` left a separate multiply, both FMAs single-rounding, and the operand order of
each one copied rather than rearranged (rule 4).

The descending form reuses the same five sites by rewriting three frame splats instead of the
algorithm: `x` becomes `splat(length_f) - idx`, the stride becomes `0xC0800000` (-4.0f, from
`lis r11,-16256`), the coefficient becomes `step * <f32 at 0x8216DEE0>` and the addend becomes
`end`. `fnmsubs` in the scalar tail implies that constant is -1.0f; it is loaded, not assumed.

## The padding loop is linear, and that looks like a copy-paste bug

`loc_82B42E1C` and `loc_82B42E68` — the up-to-three alignment samples — compute
`fma(float(n), step, start)` and `end - (length_f - float(n)) * step` with **no `fsqrts` at all**.
Verified directly in `generated/`: `fsqrts` appears at three lines only (the prologue's
`sqrt(length)`, 24413 in the ascending scalar tail, 24460 in the descending one), while the two
`fmadds`/`fnmsubs` of the padding loop at 23882/23928 have none. The sibling `sub_82B427D8`'s
padding loop is the same code and is correct there because that generator is linear throughout, so
this reads as the square-root variant being derived from it without adding the root. It is
reproduced exactly, and only bites when `first` is negative and not a multiple of four.

## Stores

| where | address | size |
|---|---|---|
| `stvx128` x4 per pass | `(out_cursor + {0,16,32,48}) & ~0xF`, sub-zero fill | 16 each |
| `stvx128` + `sub_82F52FB8` | `(cursor + 16*bulk) & ~0xF`, then a replicating copy | 16 + rest |
| `stfs` + `sub_82F52FB8` | `cursor`, then `4*left - 4` bytes above it | 4 + rest |
| `stfs` | `cursor + 4i`, padding samples, `i < 3` | 4 each |
| `stvx128` x4 per pass | `(cursor + {0,16,32,48}) & ~0xF`, vector body | 16 each |
| `stvx128` | `cursor & ~0xF`, residual groups | 16 each |
| `stfs` | `cursor + 4i`, scalar ramp tail | 4 each |
| `stfs` | `cursor + 4i`, flat prefix, `i < 4` | 4 each |
| `stvx128` x4 per pass + `sub_82F52FB8` | `(cursor + ...) & ~0xF`, flat unit fill | 16 each |

Plus 41 stores through `r1` — `std` at 80/96 (the integer-to-float transfer slot), five four-lane
splat areas at 80..159, and the three `lwz`/`stw` hop chains the descending setup uses to copy words
around inside the frame. Own frame: not windowed, not reproduced. The splats are built as registers,
which is exact because each one's four words are identical (so the `lvx128` lane reversal is a
no-op) except the index vector at `96(r1)`, whose reversal is spelled out with `setr_ps` — and
because every slot used is a multiple of 16 from `r1`, which the lifted `lvx128` masking relies on
too. No `dcbzl`, no `stvlx128`/`stvrx128`, no `mftb`, no lock, no indirect call.

## Window

**One span.** The caller's claim was checked independently against the census provenance rather
than taken on trust: of the 68 stores, 41 go through `r1` (above) and every one of the other 27
addresses `r31`, which is entry `r3` plus an offset built only from entry `r6` and entry `r7`. No
store address carries a loaded value, and the callee stores only through its own `r3`, which is one
of those addresses. So the write set is a single contiguous run from `out & ~0xF` (every `stvx128`
masks its address down to 16 bytes and the output pointer is never checked for alignment).

Its length is **not** 1024 bytes in general, and the two exceptions are the same two the sibling
documents. `first < -256`: the sub-zero fill is `-first` samples with no clamp to the block.
`first > length - 1`: `span` goes negative, both vector loops are unentered, but the index still
advances by `4*trunc(span/4)`, so the trailing flat fill starts *below* where the ramp left off and
runs to `first + 255`. For `-256 <= first <= length-1` the total is exactly 1024 bytes plus
`out & 0xF` — the one envelope span `sub_82B238A8` expects, and that caller's `Windows()` already
refuses cursors outside that range.

Either way the byte count is decided entirely by the entry registers, so `Windows()` computes it by
replaying the same integer control flow the body does and returns **true unconditionally**. A
pathological `first` is left to the harness's own 32 KB budget check (`PortOversize`, which runs the
original) rather than being refused here, so `skipped` should stay at zero and `overflow` is the
counter to watch.

## v29, v30 and v31 have to be left behind

Three registers in the ABI-preserved range the harness compares are clobbered by the main vector
loop and never saved — the prologue is `__savegprlr_26` + `__savefpr_26`, no `__savevmx_*`. Seven
writes, all inside `loc_82B43044`; the last of each is `vxor128 v31,v55,v58` (group 0's NaN mask),
`vmaddfp v29,v12,v30,v12` (group 1's refined reciprocal root) and `vmaddfp v30,v11,v1,v11`
(group 2's). Those three are stored back immediately after the loop, guarded on the loop having
run, and deliberately *there* rather than at the exit so the trailing fill's `sub_82F52FB8`
disturbs them exactly as it does under the original — which is not at all, since it touches only
r0 and r3-r10. No register in `v64-v127` is used; `v39`-`v61` are all outside the compared set.

## Gates

All four pass, so **STATUS `pending`** — written, not yet compared.

1. The only callee is a pure forward memcpy inside the declared window: replayable.
2. Enumerable from entry state, one span. The 32 gate-2 suspects in the census are all `stfs` to
   `r1+80..140`, this function's own splat scratch and transfer slot.
3. No `mftb`, no indirect call.
4. Memory plus `li r3,1` at the single exit, so `kReturnR3`; `v29`-`v31` are compared anyway as
   part of the preserved set.

## Unsure

- **0x8216DEE0 is read, not interpreted.** -1.0f is the only value consistent with the scalar
  tail's `fnmsubs`, but no guest image dump was consulted.
- **The linear padding loop.** Read as a bug in the original rather than intent. If a divergence
  ever lands on a negative, non-multiple-of-four `first`, that is the first line to re-read.
- Neither this port nor the note has been built into the game or run. `clang++-20 -std=gnu++23
  -march=x86-64 -mssse3 -msse4.1 -fsyntax-only -Wall -Wextra` against the real headers and the
  pushed `skate3_audio_port.h`: clean, with a deliberate-error control to prove the check was live.
- Wiring: `probe/ports/queue.py manifests` has to add this file to a manifest, and the
  `sub_82B42C98` slot in `skate3_audio_census_all.cpp` has to go at the same time or the link
  fails on a duplicate strong symbol.
