# sub_82B1F360

Leaf, 137 lines, 2,884 calls per boot. No arguments: it advances a six-word counter at the fixed
global 0x830775F0 (`lis -31993` + 30192). Each word accumulates the word below it with an upward
carry, the lowest word at +20 is then incremented by one, and if it wraps a single increment
ripples upward through +16, +12, +8, +4 and +0, stopping at the first word that does not wrap.

Write set `{0x830775F0, 24}` -- a constant, so the window does not depend on any register. That
makes this one of the few functions whose gate-2 answer is unconditional. `kReturnR3`, since r3
is left holding the new +0 word.

Two details worth keeping:

- The carry out of each addition is computed by a `subfc`/`subfe` pair that reduces to "the sum
  came out below its addend". That misses the case where the lower sum plus its incoming carry
  wraps to exactly the addend, so a carry is dropped there. The port reproduces the flaw rather
  than fixing it, because the harness compares against the original.
- The first carry uses a different, explicit two-compare form, and the ripple stores each word
  again after incrementing it. Both are kept as written.

**It diverged on its 120th shadow run, in r3 rather than in memory.** Every `add` in the cascade
is 64-bit on zero-extended words, so a sum can carry into bit 32. The stores keep only the low
word, which is why a 32-bit chain still produced byte-identical memory and a wrong return value:
`lifted 94BF290A01000000, native 94BF290A00000000`. The chain is now 64-bit throughout, with
`uint32_t` casts at the stores and at each `addic.` comparison. Two lessons: a register-only
difference hides behind correct memory, and a carry that appears once in 120 calls is exactly
what a per-call harness catches and a unit test would not.

Nothing in the lifted tree calls this directly, so it arrives through a function pointer; the
neighbouring 0x830775D8 is a runtime float global that other ports in this set read.
