# sub_82B470D0 — parse a stream header and dispatch to a record parser

Arguments: r3 = the object being filled, r4 = the byte stream. **r5 is a third argument** —
this function never writes it, and both record parsers read it (`sub_82B472C0`: `subf r11,r30,r5`;
`sub_82B474B8`: `and r22,r5,r6`), so it flows through untouched. Neither is set by GuestCall, which
is given two arguments only. Result: a status byte in r3 (`kReturnR3`).

Dispatch: `version = (int8_t)stream[0]`, sign-extended then compared **unsigned** against 1 — so
0x80..0xFF join 0x02..0x7F on the `r3 = 1` failure path; only 0 and 1 have their own path.
- version 1 → `sub_82B471D8(self, stream)`
- version 0 → inline header, then on the high nibble of `stream[1]`: 0 → `sub_82B472C0`,
  1 → `sub_82B474B8`, ≥2 → `r3 = 0` and no parser at all
- else → `r3 = 1`

Version-0 header stores, in the original's order (load/store interleaving preserved, because
self+0 and self+24 are written *before* stream[2..7] are read):
- `stw r30,0(r31)` self+0 = 0
- `stw r8,24(r31)` self+24 = `stream[1] & 0xF`
- `stw r29,28(r31)` self+28 = the big-endian u16 at stream[2..3]
- `stw r11,4(r31)` / `stw r30,4(r31)` self+4 = `stream + u32be(stream[4..7])`, or 0 when that u32
  is zero (64-bit add, low word stored)

The original assembles both multi-byte fields through four scratch bytes at sp+80 (two `stb` then
`lhz`, then four `stb` over the same bytes then `lwz`). That scratch is its own frame, no callee
sees it, so the port reads the bytes directly — the `lhz` precedes the second `stb` group, which is
what makes the u16 `stream[2..3]` and not `stream[4..5]`.

Tail: if `status & 0xFF` is non-zero, self+0, +4, +8, +12, +20, +24 are zeroed. **+16, +28 and +32
are deliberately left alone** — reproduced as found, not tidied.

The `stwu r1,-128(r1)` frame move is REPRODUCED: `sub_82B472C0` has no frame of its own and spills
into the red zone at `r1-129..r1-144`, and the other two build frames below this one, so skipping
the move puts every one of their stack writes 128 bytes off.

Windows: one span, `[self, self+33)`. The whole subtree's guest-visible stores are fixed offsets off
this function's r3, with no loop to bound:
- here: +0, +4, +24, +28 and the six-field wipe
- `sub_82B471D8`: +0, +4, +24, +28, then one of the two parsers
- `sub_82B472C0`: +4, +8, +12, +16, +20 and the byte at +32 (leaf; everything else is its red zone)
- `sub_82B474B8`: the same six, plus a 272-byte frame it passes to `sub_82B47658` and four
  `sub_82B47010` calls — every destination those touch (the four sub-objects at sp+100/116/132/148
  and the shared cursor word at sp+96) is inside that frame, exactly as
  `recomp/src/audio_ports/sub_82B47658.inc` and `recomp/src/audio_ports/sub_82B47010.inc` enumerate.
  MIRRORS those two ports; a change to either one's write set requires a change here.

Gates: 1 pass (three callees plus a four-deep decoder subtree, all pure byte parsing — no
allocation, free, lock, indirect call or timebase; the census agrees, `gate1: pass`); 2 pass (a
single fixed-size span off r3); 3 pass; 4 pass. STATUS pending.

Known limitation, replay only: the declared **read** set is the first 16 stream bytes plus the
object. Both record parsers then walk 16-byte records from `stream+8` until an accumulated count
passes r5, which is not bounded from entry state. Reads are not compared, so this cannot cause a
false verdict — but a recorded vector for this function is not self-contained.

Unsure: what r5 means. It reads like a total sample or frame position that the parsers clamp
against, but nothing here shows it, and the two callees are unported so nothing else documents it.
