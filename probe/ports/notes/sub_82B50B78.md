# sub_82B50B78

Six lifted lines and one instruction of substance: `b 0x82b4fe40`. A tail-branch alias for the
XMA input-buffer feeder `sub_82B4FE40` -- it takes no decision, touches no register, sets no
`lr`, and adds no frame of its own. Arguments pass through untouched and the result is whatever
the feeder leaves in r3.

Small correction to `docs/xma-transcode.md`, which calls it "the near-duplicate of
sub_82B4FE40": it is not a duplicate, it is a thunk to the same code. Anything documented about
the feeder applies verbatim, because it *is* the feeder.

Arguments: unknown and irrelevant here -- the feeder's, passed through.

Stores: none of its own (only the caller-frame `stw r12,-8(r1)` the brief excludes; in fact
this one does not even build a frame).

Gate verdict: **gate 1**, at depth 1, `sub_82B4FE40`. That function drives the hardware decoder
through `XMASetInputBuffer0Valid` / `XMASetInputBuffer1Valid`,
`XMAEnableContext` / `XMADisableContext` and `XMASetInputBufferReadOffset`, and it advances the
stream's source pointer and buffer-select flag as it pushes 0x800 bytes per packet. Running the
body a second time against rewound memory would re-arm an input buffer and re-enable a context
that the first (real) run already advanced -- an effect on the decode hardware that no memory
rewind can undo. There is no path through this function that avoids it: the branch is
unconditional.

Write set that would have been declared if it were comparable: `sub_82B4FE40`'s own, which is
not enumerable from entry state either (it copies 0x800 bytes into an input buffer whose address
comes from the stream record and whose select flag it then flips) -- so this would be gate 2 as
well, one level down. Result mask: r3, passed straight out of the callee.

Reached only indirectly: no `bl` to this address exists anywhere in the generated corpus, so the
2,993 boot calls all arrive through a function pointer. That is consistent with it being a thunk
the linker kept for a second reference to the feeder.
