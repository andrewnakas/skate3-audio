# sub_82B1C910

Leaf, 274 lines, 41,268 calls per boot, `RwAudioCore Dac`. One argument: r3 = a multi-segment
envelope. Returns the current value in r3 as a rounded int.

Layout read from this function alone (nothing in `docs/rw_audio_structs.h` names it): `+0` u16 is
the byte offset, inside this same object, of the **mode word** (`lhz r8,0(r3)` then
`lwzx r9,r8,r3`); `+2` u8 caches that word's low byte from the previous call; `+3` u8 segment
index; `+4` f32 time left; `+8` f32 per-tick increment; `+12` f32 value; `+16` u8 segment count;
`+18` u16 whose low byte is a jump target index and whose signed halfword gates the jump; `+20`
f32 initial value; `+24` the segment array, stride 8, `{f32 duration, f32 target}`. Segment k's
duration is at `+24+8k` and its target at `+28+8k`, confirmed three times: the start path uses
`24(r3)`/`28(r3)`, and both index paths compute `(k+3)*8` for the duration and `k*8` + `28` for
the target.

Four dispatch paths, in the original's order:

1. mode 1 with `+2 == 0` (a fresh start): index 0, value = initial, timer = duration[0],
   step = ((target[0] - initial) / duration[0]) * kUpdateDelta.
2. mode 3 with `+2 != 3` and `(s32)index < (s16)+18` (a jump): index = `+18 & 0xFF`, timer and
   step re-armed from that segment against the *current* value.
3. mode 1 or 3 with `index < count` (running): `timer -= kUpdateDelta`. If the timer is still
   `> 0`, `value += step`. Otherwise the value snaps to target[index], the index advances, and
   if the next index is still below the count the timer and step re-arm from it -- with the
   slope measured from the target just reached, not from the stored value.
4. anything else (including 1 or 3 with `index >= count`, and the segment-done path that ran off
   the end) forces the value to zero, except mode 2, which leaves it alone.

Every path then re-reads the mode word, caches its low byte at `+2`, and returns the value
rounded half away from zero and truncated.

Write set: `{env+2, 2}` and `{env+4, 12}` -- 14 bytes, two contiguous spans, the union of all
paths, every address a fixed offset from r3. The `fctiwz` spill at `r1-16` is the function's own
red zone, so it is not windowed. `kReturnR3`. Reads: the 24-byte header, the mode word at
`env + u16[env]`, the segment array bounded by `max(count, +18 & 0xFF) + 2` entries (both are
single bytes, so 258 entries is the ceiling), and the three pool constants.

Gates: 1 pass (leaf, no imports, no indirect calls, no lock), 2 pass (all stores at fixed
offsets), 3 pass (no timebase), 4 pass (r3, plus five observable bytes). STATUS pending.

Exactness points:

- The mode word is **re-read after the stores** at `loc_82B1CA90`. If the offset at `+0` points
  inside `+2..+15` that reload sees this call's own writes, so it is reloaded, not reused.
- `fcmpu cr6,f0,f13` in the tail runs before the `stb` at `+2` and before f13 is overwritten with
  the round-half constant; the sign is captured first, in that order.
- `fadds f11,f12,f0` is `step + value`, not `value + step`, and every `fmuls`/`fsubs` keeps the
  lifted operand order -- commutative float ops are not NaN-commutative (cookbook rule 4).
- `cmpw` on `+3` against the sign-extended halfword at `+18` is signed, while `cmplw` on `+3`
  against the count at `+16` is unsigned. Both are reproduced with those widths.
- The index arithmetic masks to a byte in three places (`clrlwi ...,24`), so index 255 wraps to 0
  rather than reaching 256.
- The three pool addresses were computed as `((imm & 0xFFFF) << 16) + offset` and all three are
  addresses the already-verified ports use, which is independent confirmation.

Unsure: mode values are read as 1 = start/run, 2 = hold, 3 = jump/run purely from the dispatch;
nothing names them. `kUpdateDelta` at `0x830775D8` is called a per-tick delta because this
function multiplies a per-second slope by it while `sub_82B1D3D0` divides it by a period -- its
actual float value was not read (no image dump on this box). The name is the only thing that
depends on that reading.
