# sub_82B1C598

Non-leaf, 164 lines, 829,106 calls per boot session on `RwAudioCore Dac`. One callee,
`sub_82B1F360`, taking no arguments -- already a verified port, a six-word cascading counter at the
fixed global `0x830775F0` (`lis r11,-31993 ; addi r11,r11,30192`, computed, not read off). It is the
only state the draw depends on: no timebase, no lock, no allocation, no indirect call. Census gate-1
verdict: pass, closure size 1. No caller appears in the lifted sources (`grep 82B1C598` finds only
its own definition), so it is reached through a function pointer; both exits leave a value in r3, so
the mask is `kReturnR3`.

Argument: r3 = the bag. Nothing in `docs/rw_audio_structs.h` names it. Fields: `u16 +0` a
SELF-relative byte offset naming a gate word; `u8 +2` element width selector (1 = bytes, anything
else halfwords); `s8 +3` set to 1 by the draw that wrapped and 0 otherwise, and *also* subtracted
from the count to form the range; `u32 +4` a base added to the drawn element; `u16 +8` cursor;
`u16 +10` element count; `u32 +12` the cached result, which the swap below also uses as its
temporary; the element array at `+16`.

Behaviour: if `u32[self + u16[+0]] == 0` the bag is inert -- return the cached `u32[+12]` with no
store. Otherwise draw the counter, compute `range = count - (s8)flag - cursor`, take
`index = cursor + draw % range`, and swap element[index] with element[cursor] using `+12` as the
temporary (store the picked value there as a word, reload it, store its low byte/halfword into the
cursor slot). Then `+12 = u32[+4] + drawn`, `+8 = cursor + 1`, and either `+3 = 0` or -- when the
new cursor reaches the count -- `+8 = 0` and `+3 = 1`. r3 is that sum.

The flag doing double duty reads as the no-immediate-repeat trick: after a wrap the range is one
short, so the first pick of the new cycle cannot land on the last slot, which is where the previous
cycle's final draw was swapped to. That is a reading of the arithmetic, not established, and the
port does not depend on it.

Stores, in order: `stw` 4 at +12 (the temporary); 1 or 2 bytes at the picked slot; `stw`/`lwz`
round-trip of +12; 1 or 2 bytes at the cursor slot; `sth` 2 at +8; `stw` 4 at +12; then either
`stb` 1 at +3, or `sth` 2 at +8 and `stb` 1 at +3. Plus `sub_82B1F360`'s whole 24-byte counter.

Two 64-bit traps, both live here. `add r3,r11,r10` sums two zero-extended words, so a carry lands
in bit 32: r3 keeps all 64 bits and only the `stw` to +12 truncates. And `subf r11,r4,r3` subtracts
the `mullw` product from the counter word in 64 bits, so the remainder carries the counter's high
half with it; only the low word ever reaches an address, which is why the picked slot is still
inside the declared span.

Window: the inert path is predicted exactly (its one input is entry state). Otherwise the picked
slot is *not* predicted -- that would mean reimplementing the counter inside `Windows()` -- but it is
bounded: `index` lies in `[cursor, cursor + range)` and the cursor slot is the lowest member of that
interval, so one span `{self + 16 + width*cursor, width*range}` covers both halves of the swap.
Five spans: that, +3, +8, +12 and the counter. `+8`, `+4`, `+10` and `+12` are all reloaded after the
swap's stores, and need no alias check because the array starts at +16 and the span only grows
upward -- the wrap guard is what makes that argument sound.

Returns false on: `range == 0`; an array span that wraps 2^32; a span over the byte budget; and an
object whose 16-byte header overlaps the counter global, since `+2`, `+3` and `+10` are read *after*
the counter has advanced and would then not derive from entry state.

Gates: 1 pass. 2 pass conditionally, per those four exits; the census flagged four stores
gate2_suspect because their bases are derived, but every base derives from header fields readable
before the call plus a remainder the span above bounds. 3 pass -- the draw is a deterministic
counter, not `mftb`. 4 pass.

Unsure: (a) a zero range makes `twllei r6,0` trap and then indexes with the raw counter word, so the
original's store lands wherever that points -- a wild write no window can cover. `ppc_trap(type 0)`
only warns and returns, so the original would carry on and corrupt memory. `Windows()` declines the
call rather than comparing it; if `PortSkip "not enumerable"` ever shows up in the census for this
function, that is the case to look at, and it is a bug worth a docs entry. (b) The meaning of `u32 +4`
is unread: "a base added to the drawn element" is what the arithmetic says, and whether the elements
are indices, offsets or IDs is not established. (c) `addi r10,r11,16` in the byte path is dead --
computed and never used -- so it is not reproduced.
