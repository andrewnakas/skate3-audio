# sub_82B31680

- Role: `int f(link*)` — re-point a mix link. Detaches the target's embedded mix node from
  whatever list it is on (`sub_82B31480`), then, when the link names a source, copies four of the
  source's fields into the node and pushes the node on the front of the source's list. Returns 16
  in r3 on every path. 89 lifted lines, one direct callee, closure of 7, no imports, no indirect
  call, no lock, no timebase. 3,001 boot calls.
- Arguments: r3 = the link record. `u32[r3+4]` = the target, `u32[r3+12]` = the source. The node
  lives at `target+56`: `+0` next, `+4` prev, `+8` a mirror of the owner's `+8`, `+12` the owner's
  item (non-zero means "linked"), `+16` the owner, `+20` u16, `+22` u8 channel count. The list
  owner is `source+52` (`addi r9,r10,52`, the value that lands in the node's `+16`): `+0` the
  mixer item, `+4` the list head, `+8` a value, `+44` u16 — exactly the offsets `sub_82B34BD0`
  reads off `u32[node+16]`. `u8[u32[owner+0] + 42]` is the same channel count `sub_82B27E20`
  reads at `+42`.
- Stores, all when `u32[link+12] != 0`: `node+12 = u32[owner+0]`; `node+8 = u32[owner+8]`;
  `node+20 = u16[owner+44]` (2 B); `node+22 = u8[item+42]` (1 B); `node+16 = owner`;
  `node+0 = u32[owner+4]`; `node+4 = 0`; `u32[head+4] = node` when the re-read head is non-null;
  `u32[owner+4] = node`. One span `node+0 .. +22` covers the node half. Plus `sub_82B31480`'s.
  The `stwu r1,-112(r1)` **is** reproduced (unlike most ports' frames): `sub_82B31480` spills
  r12/r30/r31 at -8/-16/-24 off the *caller's* r1 before its own `stwu`, so without the move its
  frame lands where this function's spills went.
- `sub_82B31480` through `GuestCall`. It has two arms, selected on `u8[node+22]`:
  - `== 0`: an inline unlink of the node — `u32[old_owner+4] = u32[node+0]` when the node is that
    head, `u32[prev+0] = u32[node+0]`, `u32[next+4] = u32[node+4]`, then it clears `node+8`,
    `node+12`, `node+16`, `node+20` (u16) and `node+22` (u8). No calls. This is the arm the port
    compares.
  - `!= 0`: the node still holds per-channel deltas, and they are flushed through
    `sub_82B468C0` → `sub_82B3BED8` (25 vector stores) / `sub_82B426D0` (two byte-write loops,
    one addressed `stbx r6,r8`) and `sub_82EE5E80`, then `sub_82B34BD0` folds them into
    `u32[node+16]+12+4i` and `u8[owner+46] = 1`, and `target+80..111` is zeroed. `sub_82B468C0`'s
    own census says `stores_present: false` — every byte it writes comes from a callee three
    levels down, and two of those write through pointers built inside their own loops.
    **`Windows()` returns false on this arm**: gate 2, on that path only. The body still runs it
    correctly (it is the same single `GuestCall`), it is simply never compared.
- Window rationale. The arm is predicted from `u8[node+22]`, which is entry state (nothing is
  written before the call). On the compared arm the declared set is: the unlink's up to three
  4-byte link fixups; `node+8 .. +22` (its clears); `node+0 .. +22` (this function's rewrite);
  `owner+4`; and the back-link `head+4`. Returns false when the link or the target is null, when
  the node names an item but its owner is null, when either of the unlink's first two stores lands
  on the node's two link words (the unlink re-reads them after those stores, so the third store's
  address would not be entry state), and when the source's read fields overlap the node block —
  that last one is the honest form of "the source and the target are different objects", and it is
  what keeps the four source reads entry-exact. Budget: at most 9 spans, ~60 bytes.
- The one place a superset is declared rather than a case analysed: `stw r11,4(r10)` stores
  through the head read a **second** time, after `node+0` and `node+4` are written. When the node
  is being moved inside the list it already sits on, `sub_82B31480`'s unlink has already written
  `owner+4`, so that address is one of three entry values — the head as it stands, `u32[node+0]`
  (what both of the unlink's head-side stores leave there) or `u32[node+4]` (what its prev-side
  store leaves). All three are declared when the unlink runs. The other source fields read after
  stores (`owner+0`, `owner+8`, `owner+44`) only supply stored *values*, never addresses, so a
  write that landed on them cannot move a byte outside the declared set.
- Unsure: nothing names this structure, so `link`, `owner` and `item` are descriptive only; the
  identification of `owner = source+52` rests on `sub_82B34BD0` reading `+0/+4/+12/+46` off
  `u32[node+16]` and on `u8[item+42]` matching `sub_82B27E20`'s channel count. A null item is
  reproduced, not guarded: the original reads `u8[42]` out of the image and stores the byte.
- Gate verdict: **gate 2 on the delta-flush arm only**, none on the compared arm. STATUS pending:
  written, never compared.
