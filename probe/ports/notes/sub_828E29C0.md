# sub_828E29C0

One hundred and two lifted lines, twelve of them frame. A leaf by the census's reckoning --
no direct callees, no imports -- with one `bctrl` inside a list walk. It lives in
`skate3_recomp.47.cpp`, well outside the audio translation units; it is in the corpus because
`sub_82B1C210` (25,894 calls a boot session) calls it, and it is the generic listener-notify
primitive, not audio code.

Arguments: `r3` = a handle record, `r4` = an opaque payload pointer that is forwarded to every
listener untouched.

Structure. Handle: `+0` holder pointer, `+4` generation token. Holder: `+0` list head, `+8`
the generation the handle must match. Node: `+0` next, `+8` function pointer, `+12` the
listener's own registration data.

Control flow and every result value:

| condition | result | writes |
|---|---|---|
| token at `+4` is already negative | that word, **zero-extended** | none |
| holder at `+0` is null | -6, sign-extended | none |
| token != holder's generation | -3, sign-extended | `+4` = -3 then `+0` = 0 |
| list head is null | -4 | none |
| otherwise | 0, after calling every node | none |

The first row is the detail that would sink a careless port: `mr r3,r9` copies the register a
`lwz` left, so `r3` is `0x00000000FFFFFFFD`-shaped, while the `li r9,-3` path leaves
`0xFFFFFFFFFFFFFFFD`. Both return "-3" to a 32-bit caller and differ in all 64 bits, which is
what the harness compares. The native body spells both out.

Two more preserved details: on the stale-handle path the token is stored *before* the holder
is cleared, and in the loop `next` is read from `0(r31)` **after** the callback has run -- a
listener that frees its own node reads freed memory here. Neither is corrected.

Stores: two, both on the entry `r3`, both on one path: `{r3 + 4, 4}` and `{r3 + 0, 4}`.
Everything else the call changes belongs to the listeners.

Gate verdict: **gate 1**, at depth 0. The `bctrl` target is the word at `node+8`, a stored
function pointer, and the walk is over a list of unknown length, so the call count is not
bounded from entry state either. A replay would fire every listener a second time -- and since
`sub_82B1C210` reaches this from the Dac thread 25,894 times a session, those listeners are
live audio state, not pure functions. There is no path predicate worth splitting on: the three
error returns are exactly the cases where nothing interesting happens.

Write set that would have been declared if it were comparable, on the paths that never reach
the loop: `{r3 + 0, 8}` (the two words, contiguous) on the stale-handle path, nothing on the
other three. Reads: `{r3, 8}`, plus `{holder + 0, 12}` when the holder is non-null. Two spans,
trivially inside budget -- so this is only gate 1, not gate 2, for the non-dispatch paths.

Result mask: r3 on every path.

Uncertain: `+8` on the holder is read as an int32 and compared signed against the handle's
token, which is the shape of a generation counter, but nothing here proves it is monotonic --
it could equally be a type tag. The behaviour is the same either way. Also unverified whether
the node's `+4` is used by anyone; this function never touches it.
