# sub_82B474B8

Non-leaf, 233 lifted lines, 729 calls on the boot session, `RwAudioCore Dac`. Census gate-1
verdict: pass, closure of 4 (`82B47658`, `82B47010`, and under those `82B46FB0`/`82B46EA0`),
no imports, no indirect calls, no timebase. Mask `kReturnR3`: 1 or 0 on the three exits.

Arguments: r3 = the object the found record is published into, r4 = the byte pointer at the start
of the four interleaved variable-length streams, r5 = the target position.

It builds the decoder state in its own 272-byte frame -- the shared cursor object at r1+96 (its +0
is the live byte pointer, set from r4), four zeroed 16-byte sub-objects at r1+100/116/132/148 whose
`cursor*` all point at r1+96, and sub_82B47658's four-word result at r1+80 -- then walks the four
streams in lockstep with `sub_82B47010`, one call per stream per record, in the order 0,1,2,3.
Stream 2 is the step (how far this record advances the position), stream 3 the mode, streams 0 and 1
feed running sums. The walk ends when the position passes the target (return 0) or when a step comes
back negative (return 1, and also the pre-loop exit when the very first step is negative).

`limit` (r22) = `target - [r3+28]` kept only when its low word is a positive int32, else zero: the
lifted form is `subfic`/`rlwinm`/`addme`/`and`, whose mask is sign + carry - 1. A record publishes
when `position <= limit && limit < position + step` (signed, short-circuiting) **or** when the mode
word is exactly 1.

Stores, all on r3 and in this order: `+4` (4) = 0 when stream 1's current value is zero, else
stream 1's running sum plus the entry value of `+4`; `+8` (4) = the position; `+16` (4) =
`min(target - position, [r3+28])` signed, with `[r3+28]` **reloaded** here; `+20` (4) = stream 0's
running sum; `+12` (4) = `(target - length) - position`; `+32` (1) = 1 when the mode word is exactly
1, computed as bit 5 of `cntlzw(mode - 1)`.

Window: `{r3+4, 20}` and `{r3+32, 1}`, the same two spans on every path -- the loop cannot move a
store address. Everything the decoder writes (the cursor's byte pointer, each sub-object's
accumulator/remaining/flag) is inside this call's own frame, which is not windowed;
`probe/ports/notes/sub_82B47658.md` and `port_82B47010.inc`/`port_82B46FB0.inc` are where that write
set is enumerated, so a change to either of those ports' write sets needs a re-read here. Returns
false on a null object, on an object whose span would wrap 2^32, and on an object that overlaps
[r1-272, r1) -- a frame store landing on a windowed byte would be neither rewound nor compared.

The frame move **is** reproduced (like sub_82B47010/sub_82B46FB0): the callees are handed frame
addresses and build their own frames below r1. 272 leaves exactly 8 bytes between the last
sub-object byte (r1+160 = entry_sp-112) and `__savegprlr_20`'s spill area ([entry_sp-104,
entry_sp-8)), which is the cross-check that the frame size is read right. r20-r31 are spilled by the
prologue only because of the calls; this body keeps all twelve in locals and writes none of them.

Unsure of: the field names are descriptions of the arithmetic, not recovered names -- nothing in
`docs/rw_audio_structs.h` covers this object. The read span for the stream is a fixed 1 KB summary:
the walk length is not bounded from entry state, so a replayed vector of a long walk may run past
the recorded bytes. Reads are not compared, so this cannot cause a divergence in the game.
