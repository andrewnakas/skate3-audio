# sub_82B482F8

Non-leaf, 196 lines, 18,685 calls in the boot session, all on `RwAudioCore Dac`.
**Gate 2, and the canonical one:** `docs/shadow-harness.md` (the "address set data-dependent" row
and the `sub_82B7F8A8` comparison) and `docs/PLAN.md` phase 2 gate 2 both name this function as
the measured failure. The body is written and exact; it is the reference for the Rust port. No
attempt was made to rescue it.

Arg: r3 = the System object. Void: no `li r3` before the return, so the caller can read nothing
(the `kReturnR3` on the macro line is the repo's convention for gate ports, which never compare).
`docs/decompilation-status.md` places this call in the queue drain, under the System lock, walking
the list at `System+0x1C` = `+28`.

What it does, per element on that list (the node is at `element+28`, so `element = node - 28`):

1. For each of `element[+68]` children at `element[+80 + 4*i]`, for each of `child[+43]` sends at
   `child[+24 + 4*j]`: `sub_82B48B28(System+112, send)`. Both counts are **reloaded every
   iteration**.
2. Unlink `element+28` from the owner `element[+16]`: if it is the head at `owner[+28]`, publish
   `node[+0]`; then `node[+4] -> +0 = node[+0]` and `node[+0] -> +4 = node[+4]`, each guarded on
   non-null, and `node[+0]` re-read between the two stores. So `+0` is next, `+4` is prev.
3. `element[+71] = 0`, then `sub_82B49438(element)`. On a non-zero low byte: push the node onto
   the owner's other head `owner[+24]` (`node[+4] = 0`, `node[+0] = old head`, old head's `+4` =
   node if non-null, `owner[+24] = node`), then `element[+0] = +4 = +8 = 0.0f`, `element[+71] = 4`,
   `element[+60] = 0`. `element[+16]` and `owner[+24]` are both re-read on this path.

Stores: `{owner+28, 4}`, `{prev+0, 4}`, `{next+4, 4}`, `{node+0, 4}`, `{node+4, 4}`,
`{owner+24, 4}`, `{element+0, 4}`, `{element+4, 4}`, `{element+8, 4}`, `{element+60, 4}`,
`{element+71, 1}` twice -- per element, times an unknown element count, plus everything
`sub_82B48B28` writes.

Constant: `lis r11,-32234 ; lfs f31,23056(r11)` = `((-32234 & 0xFFFF) << 16) + 23056` =
`0x82160000 + 0x5A10` = **0x82165A10**, computed not eyeballed. `port_82B269C0` already names that
word `kZeroFloat`.

**Why gate 2.** Two independent reasons, either fatal. The list length is whatever the drain left
at `System+28` and nothing readable before the call bounds it. And per node the write set reaches
three objects only addressable *through* that node -- the owner, the previous node and the next
node -- both of the latter being nodes of the same list, so iteration two's addresses depend on
the surgery iteration one performed. `sub_82B48B28`'s subtree adds a third unbounded set keyed on
each child's reloaded `+43`. `Windows()` returns false unconditionally and the original runs.

Not rescuable by mirroring a callee: neither `sub_82B48B28` nor `sub_82B49438` has a port in
`recomp/src/audio_ports/`, and the unenumerable part is this function's own walk, not a callee's.
Gate 1 passes (census verdict pass, closure `82B48B28`/`82F4DC60`/`82F52B30`), gate 3 passes (no
timebase).

Fidelity notes. `r3`, `r5` and the `r6` counter of the send loop are **live across** `bl
0x82b48b28` -- the original sets `r3`/`r5` once outside the loop, which is a whole-program
register-allocation fact and not the ABI. The body therefore reads all three back out of `ctx`
after each `GuestCall` instead of caching them, so a callee that does clobber them diverges the
same way the original would. `stwu r1,-160(r1)` is reproduced so the two callees' frames land
where the original put them; the `__savegprlr_24` and `stfd f31` spills are not, because r24-r31
and f31 are never written here.

Unsure: `element[+68]`/`child[+43]` are read as counts because they index pointer arrays with a
signed `cmpw`; `element[+71]` taking 0 then 4 reads like a state enum, and 4 is only written on
the recycle path. The `r30 = 0` fallback for a null node is unreachable from either entry to the
loop but is reproduced anyway.
