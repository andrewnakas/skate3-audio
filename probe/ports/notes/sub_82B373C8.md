# sub_82B373C8

Leaf, 451 lines, 29 vector instructions, **23 calls per boot session**, `RwAudioCore Dac`. Called
from `sub_82B376B8`, which passes `r3` = the meter object and `r4 = *(u32*)(other+0x1C)`, ignores
the return and calls `sub_82B370E8` next — so `kReturnNone`.

Per-channel RMS and peak metering of one block into two ring histories. `r4` is the same
channel-buffer descriptor shape `sub_82B238A8` reads at its own descriptor `+0x1C`:
`+4` float* of channel 0, `+14` u16 floats between channels.

**Phase 1, vector** (skipped when `object[0x2A] == 0`): per channel, sixteen passes accumulate
`mag = |sample|` (`vandc128` against a `vslw128`-built 0x80000000) into four sum-of-squares
accumulators by `vmaddfp` and four running maxima by `vmaxfp128`, then reduce pairwise to one
16-byte sum vector and one peak vector, stored 16 bytes per channel into two **red-zone** arrays
at `r1-304` and `r1-176`.

Two things there are reproduced rather than corrected:

- each pass steps 64 bytes but loads only 16, so **three quarters of every row is never read**;
- all four accumulator pairs are fed the *same* vector, so the reduction yields **four times**
  the sum of squares, and the peak reduction is just that one maximum.

**Phase 2, scalar**: per channel, the scratch vector's four lanes are read back by `lfsx` at
`+0/+4/+8/+12` — the reason phase 1 keeps real guest stores instead of host locals is that the
`stvx128` lane reversal is part of that read-back, not incidental to it. Then
`mean = (sum * k) / (float)frames` with `k` = the f32 at **0x822F8A44**, and
`level += mean - history[slot]`, clamped at the floor; the running sum at `0xF0` accumulates
`mean`; the block peak lands at `0x130` and the held peak at `0x150`; `mean` and the peak are
written into the two rings at `slot = ((frames * channel) + cursor) * 4`.

**Tail**: on the last block of the ring (`cursor == frames - 1`) each channel's running sum is
published to its level and cleared. Then the cursor advances as `(cursor + 1) mod frames` via a
real `divw`, guarded by the `twllei`/`twlgei` pair the compiler emits for a signed divide — both
are reproduced (their second clauses, `u32 < 0` and `u32 > UINT32_MAX`, are vacuous and are not).

## Stores

All sixteen from the census: `0xF0 + 4c` (sum), `0x110 + 4c` (level, twice), `0x130 + 4c` (peak,
three sites), `0x150 + 4c` (peak hold), `slot + object[0x182]` (peak ring, three sites),
`slot + object[0x180]` (level ring), `0x184` (cursor, u16), plus the two `stvx128` and the one
`std` in the red zone. The tail loop's `+36`/`+4` from `0xEC` are the level and sum arrays again.

## Window rationale

Four per-channel arrays of `4 * count` bytes at `0xF0/0x110/0x130/0x150`, the 2-byte cursor, and
two 4-byte ring slots per channel: `5 + 2*count` spans, 194 bytes at eight channels. The four
arrays end at `0x170` even at eight channels, so they cannot reach the header fields at `0x178`
and above.

`Windows()` returns **false** above **eight channels**. That is not a budget limit but the
original's own: the two red-zone arrays are 128 bytes each, so at nine channels the sums array
runs into the peaks array, and at twelve the peaks array reaches `r1` and starts overwriting the
caller's frame. Replaying that is not something the harness should be asked to do.

Five header fields — `0x2A`, `0x178`, `0x180`, `0x182`, `0x184` — are **reloaded after** stores
inside the channel loop, so a declared ring slot covering one of them would shift the remaining
addresses mid-call. Every slot is checked against all five and a hit returns false.

The red-zone scratch (272 bytes below `r1`; the function has no `stwu` at all) is the function's
own frame and is not windowed, per the brief. It is dead to the caller and the original writes
the same bytes immediately before the native body does.

## Gates

All four pass: leaf, no imports, no indirect calls, no lock (1); every address derived from entry
state, subject to the checks above (2); no `mftb` (3); 16 stores, all observable (4).
STATUS pending.

**Expect a thin verification.** 23 boot calls is the whole budget, against `sub_824531C8`'s
seven million — and if `object[0x2A]` is 0 on some of them, fewer still. A clean session here is
much weaker evidence than the same result on a hot function, and the phase-1 vector path in
particular gets 23 chances at most. Worth re-running under a play session rather than boot alone.

## Unsure

- The f32 at **0x82165A10** is read as the floor for every comparison. `sub_82B1D5D0.inc` already
  names that exact address `kZeroSingle`, i.e. `0.0f`. If that is right, the `peak < floor` branch
  (`loc_82B375D8`, the peak-ring scan) is **dead**, since every peak there is a magnitude and NaN
  fails `lt` as well. The port writes the branch anyway and declares its spans; nothing in it
  writes outside what the always-taken path writes, so a dead branch costs the window nothing.
- The scan loop inside that branch strides the ring by `4 * count` per channel while the ring
  index strides by `4 * frames`. Those disagree unless `count == frames`. Reproduced as-is; it
  looks like a bug but it is in dead code if the point above holds.
- `0x180`/`0x182` are read as u16 byte offsets *within* the object to the two rings. That follows
  from `add r4,r11,r3` alone, so it is a reading, not a confirmed field.
- Wiring: `SKATE3_CENSUS(11, sub_82B373C8)` in `skate3_audio_kernel_census.cpp` and the
  `sub_82B373C8` slot in `skate3_audio_census_all.cpp` define the same strong symbol; both must
  go when this lands in a manifest.

Both this port and `sub_82B238A8.inc` / `sub_82B373C8.inc` were checked with
`clang++-20 -std=c++23 -march=native -fsyntax-only -Wall -Wextra` against the real headers:
clean, with a deliberate-error control to prove the check was live. Neither has been built into
the game or run.
