# sub_82B1C150

One hundred and eight lifted lines, four of them frame. One direct callee (`sub_82B1BF98`),
no imports, no vector work. **64,666 calls a boot session** -- the busiest function in this
batch, and on the Dac thread.

What it does. `r3` is a registration record: `+0` the owner, `+4` the node, `+12` a flag that
is zero when there is nothing to unlink (the whole body is skipped and the function returns 0
immediately -- that is the common case at 64k calls a session). The node carries **two** link
pairs: `node+0/+4` threads the owner's chain, whose head is at `owner+56`; `node+8/+12`
threads a process-global chain whose head is the cell at `0x83036F4C`
(`((-31997 & 0xFFFF) << 16) + 28492`, computed, not read by eye). The function performs the
same four-store unlink on both pairs -- patch the neighbour on each side if it exists, and
advance the head if this node *is* the head -- then calls `sub_82B1BF98` with `r3` untouched
and returns a literal 0.

The unlink is byte for byte the one in `port_82B34BD0`: `+0` and `+4` in the same roles, the
head advance reading `head+0`, both neighbour pointers reloaded inside their own branch
instead of cached across a store that could alias them. Factored here into `UnlinkPair()`
because it appears twice identically; it takes `base` because `REX_LOAD_*` expands to code
naming it.

One preserved re-read: the node pointer at `4(r3)` is loaded **again** before the second
chain's work (`lwz r11,4(r3)` at `0x82B1C1AC`), not carried over from the first block. The
first block stores through two pointers that could in principle alias `4(r3)`, so caching it
would be a different program.

Stores, six outside the frame: `{owner+56, 4}`; `{next+0, 4}` and `{prev+4, 4}` for the first
pair; `{0x83036F4C, 4}`; `{next+0, 4}` and `{prev+4, 4}` for the second pair -- where each
`next`/`prev` is read off `node` or `node+8` respectively. All six are conditional.

Gate verdict: **gate 1**, at depth 1, `sub_82B1BF98`. That callee has two `bctrl`s of its own
and its closure (11 functions) leaves the audio corpus entirely into `82EDFEC0`, `82EDFF50`,
`82EE6260`, `82EE7880`, `82EEEA98` -- the CRT/allocator side -- so this is a "release the
record" path and a replay would release it twice. The call is *unconditional* once the flag at
`+12` is non-zero, and the only path that avoids it is the flag-zero path where the function
writes nothing at all. Comparing exclusively the no-op path is the vacuous green the brief
warns about, so the whole function is labelled rather than split.

Write set that would have been declared if it were comparable: the unlink itself is fully
enumerable from entry state -- `owner = *(r3+0)`, `node = *(r3+4)`, then five spans of 4 bytes
plus the global cell, six spans total, six of the census's "gate2_suspect" stores accounted
for and none of them loop-derived. Reads: `{r3, 16}`, `{node, 16}`, `{owner+56, 4}`,
`{0x83036F4C, 4}`. It is `sub_82B1BF98`'s writes that are not enumerable, not these.

Result mask: r3, the literal 0 on every path.

Uncertain: the "registration record" reading. What is verified is the shape -- a node in two
chains, one per-owner and one global, unlinked from both and then handed to a function that
reaches the allocator. Whether `+12` is a liveness flag, a refcount or a handle was not
determined; it is only ever compared against zero here. Nothing was checked about what
`owner+56` belongs to structurally, and `docs/rw_audio_structs.h` documents no `+56` on any
recovered layout, so the offset is left as a plain constant.
