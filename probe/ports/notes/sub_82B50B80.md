# sub_82B50B80

Lifted: `skate3_recomp.68.cpp:57220`, 757 lines. 131,630 calls during boot on `RwAudioCore Dac` --
the second busiest gate-1 function after the feeder it calls. The XMA **output** drain, the twin of
`sub_82B4FE40` (input): `r3` = the System object, `r4` = the planar float output descriptor
(`+4` data, `+14` u16 floats per channel), `r5` = sample frames wanted. Returns frames produced.

## Shape

Outer loop (`loc_82B50BC0`) until `r5` frames are satisfied:

1. `+0x48` zero: bind the next segment. The segment is `object + [object+0x24] + 24*[object+0x31]`,
   and the null check on its `+12` is **branchless** (`subfic`/`subfe`/`and`), so an empty segment
   leaves the pointer at 0 and the loads that follow address low memory. Every stream's
   `sample_credit` gains `((first + offset) mod 512) + [object+0x4C]`, where `offset` is 384 when the
   segment's `+20` is clear -- the sub-frame remainder the previous segment left. Then
   `+0x48 = last - first`, `+0x38 = segment`, `+0x54 = 0`.
2. `chunk = min(wanted, [+0x48])`, signed.
3. Unless `+0x54` is set, per stream (`loc_82B50CB8`): read the hardware write offset (scaled by
   256 into a byte position in the 6144-byte ring), subtract `out_cursor` for the bytes available,
   and add a whole ring when that is negative -- or zero with the output buffer reported invalid --
   provided `+0x55` is clear. Retire `min(avail, credit*channels*2)` bytes: advance `out_cursor`
   (wrapping at 6144) and drop `taken/(channels*2)` frames off the credit. Then if
   `avail >= chunk*channels*2`: build one output pointer per channel on the frame at `+80`, split
   the chunk at the ring's end, and call `sub_82B50380(dst0, dst1, ring, cursor, channels, first,
   wrap)`. Otherwise `sub_82B4FE40(object)` and set the stall flag.
4. Recompute the read offset the context should hold -- `(out_cursor / (channels*1024)) *
   channels*4`, i.e. 128-sample subframes -- and when it differs from what the hardware reported,
   `XMADisableContext` / `XMASetOutputBufferReadOffset` / `XMASetOutputBufferValid` /
   `XMAEnableContext`.
5. Stall tail (`loc_82B50F00`): read the counter `sub_82EE02B0` returns, re-enable the context, and
   look at the two bytes at `[context+0]+8` and `+12`. Busy (bit 7 in either, or a null pointer):
   latch `r17 = 2` and reinit. Idle and the counter has moved less than 4: retry **the same stream**
   once (the latch stops a second retry). Otherwise `r17 = 1` and reinit.
6. Reinit (`loc_82B50F78`): `+0x54 = 1`, `sub_82B4FC00(object, [+0x50])`, clear five fields of every
   stream record, set the fill slot to the play slot then to that plus one wrapped at `[+0x32]`,
   `+0x3C = 0`, `sub_82B4FE40(object)`.
7. With `+0x54` set, memset `chunk*4` bytes of each of `[+0x2E]` output channels at the running
   position and count the chunk as produced.
8. `+0x48 -= chunk`; when it hits exactly zero on a non-zero chunk, carry `512 - ((last + offset)
   mod 512)` into `+0x4C` (cleared again if this block was silence). `sub_82B4FE40(object)`, loop.

## Gate verdict

**gate-1 at depth 0**, seven XMA imports. Two of them are pure reads
(`XMAGetOutputBufferWriteOffset`, `XMAGetOutputBufferReadOffset`) but they report hardware state, so
a replay would see a decoder that has moved on; the other five *change* it -- moving a context's
read offset, marking its output buffer valid and cycling disable/enable. No memory rewind undoes
any of that. `sub_82B4FE40`, `sub_82B4FC00` and `sub_82B50B78` are gate-1 for the same reason, and
`sub_82B50380` is gate-2. `Windows()` returns false.

Gate 2 would fail too: how many streams are written, and how many times each, depends on the write
offset the hardware reports and on `XMAIsOutputBufferValid`, neither readable from guest memory.
The census marks 25 stores `gate2_suspect`.

## Return mask

`r3` is `produced` (`mr r3,r20`) on the normal return and 0 on the `r5 == 0` early one, so
`kReturnR3` is the honest mask -- the caller uses it as the frame count actually delivered.

## Uncertainties

- **The decode destination omits the running output position.** `loc_82B50DE0` builds the channel
  pointers as `out_data + 8*stride*index + 4*stride*lane` with no `r20` term, while the silence fill
  at `loc_82B51028` does add `r20`. So a second outer-loop pass would overwrite the first pass's
  output. Either the outer loop is single-pass in practice (one segment always covers the request)
  or this is a real bug; nothing here settles it, and it is reproduced as written.
- The write offset is scaled by 256 regardless of channel count while the read offset formula
  divides by `channels*1024`. For a mono context both agree on 128-sample subframes; for a stereo
  one the write side would undercount by two. Only mono has ever been observed on the
  `sub_82B50380` side (see that note), so this is untested rather than known wrong.
- `r17` is written 1 or 2 and only ever tested against 0, so the two values are indistinguishable
  here. Whatever distinguishes them is not in this function.
- The `loc_82B50CB8` bound test is skipped whenever the stall flag is set, which would let the body
  run on an index past the stream count. Unreachable as written -- the retry never advances the
  index -- but nothing in the function enforces that.
- `sub_82EE02B0` reads `[[0x8200063C]+16]` (`lis r11,-32256` + 1596, computed not eyeballed) and the
  result is compared against 4 after subtracting 1. A counter of some kind; not a timebase, so this
  function is not gate-3.
- `sub_82F52040` is a byte-fill memset and `sub_82EE02B0` a one-word getter, both confirmed from
  their lifted bodies rather than assumed.
