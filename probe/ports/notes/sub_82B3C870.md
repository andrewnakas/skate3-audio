# sub_82B3C870

- Role: `uint8_t f(obj*, r4, r5, r6, r7, r8, r9, r10)` — the producer for a ring of **24-byte
  request slots embedded in the object itself**. It reads the write index `u8[obj+47]`, forms the
  slot address `obj + u32[obj+36] + index*24`, and if `u32[slot+12]` is **zero** (the consumer has
  taken the previous request) it fills the slot from the argument registers, notifies the owner
  through the object's own table (`u32[u32[obj+0] + 0](obj, index)`), latches `u32[slot+8]` into
  `u32[obj+28]` when the write index still equals `u8[obj+49]`, then advances `u8[obj+47]` and
  wraps it to 0 at `u8[obj+50]`. 109 lifted lines, no direct callees, one own indirect call, no
  imports, no timebase, no lock. **4,788 boot calls** on `RwAudioCore Dac` (tier D).
- Arguments: r3 = the object; r4 → `slot+0`, r8 → `slot+4`, r7 → `slot+8`, r5 → `slot+12`,
  r10 → `slot+16`, r6 → `u8[slot+20]`, r9 → `u8[slot+21]`. r4..r10 are all consumed; nothing
  else is read from entry registers.
- The array is **embedded, not pointed to**: `add r11,r11,r3` adds `u32[obj+36]` to the index
  scale and then `add r30,r11,r31` adds the object, so `u32[obj+36]` is a byte offset inside the
  object, not a base pointer. Read once, from this function alone; no second reading corroborates
  it, and I did not confirm that the resulting range lies within the allocation.
- Stores (7 to the slot, 2 to the object, 1 to this call's own frame):
  - `stw r4,0(r30)` / `stw r7,8(r30)` / `stw r8,4(r30)` / `stw r5,12(r30)` / `stw r10,16(r30)` —
    4 bytes each, in exactly that order (+0, +8, +4, +12, +16)
  - `stb r9,21(r30)` / `stb r6,20(r30)` — 1 byte each, +21 **before** +20
  - `stw r11,28(r31)` — `u32[obj+28]`, 4 bytes, only when `u8[obj+47] == u8[obj+49]` **after**
    the notify
  - `stb r10,47(r31)` then, when the incremented value is `>= u8[obj+50]`, `stb r11,47(r31)` — the
    same byte written twice on the wrap path; reproduced as two stores
  - the `stwu` back chain is this call's own frame; never windowed.
  `u8[obj+47]` is reloaded **three times** (once for the latch test, once for the increment) and
  `u32[slot+8]` is reloaded for the latch rather than reusing r7 — the notify runs in between, so
  none of those reloads may be hoisted.
- Result: **r3**, and honestly so — `mr r3,r29` returns the index the call filled, and `li r3,0`
  the busy path. Note the two are indistinguishable when the ring's write index is 0; that is the
  original's ambiguity and is reproduced, not fixed. The macro line carries `kReturnR3`, which is
  also the honest mask here.
- Gate 1 **fails** at depth 0: this function's own `bctrl` at **0x82B3C8E4**, through
  `u32[u32[obj+0] + 0]`. The target is a data word, so the callee cannot be enumerated before the
  call, and it demonstrably mutates the same ring (the reload of `+47` afterwards only makes sense
  if it can). Unconditional on the fill path, so the only replayable path is the busy one — too
  little to be worth a partial `Windows()`.
- The write set I WOULD have declared if it were comparable: `spec.write(slot, 22)` (the whole
  `+0..+21` span; `+22`/`+23` are never touched), `spec.write(obj + 28, 4)` when
  `u8[obj+47] == u8[obj+49]` — but the notify can change `+47`, so that predicate is **not**
  decidable from entry state, which would make it gate 2 as well — plus `spec.write(obj + 47, 1)`;
  reads `{obj+0, 4}`, `{obj+36, 4}`, `{obj+47, 1}`, `{obj+49, 2}` (+49 and +50), `{slot+8, 8}`.
  The notify's own writes are unbounded and unknowable, which is the whole of gate 1.
- Unsure: what the object is. The `+0`-slot notify, the embedded 24-byte ring and the
  `+47`/`+49`/`+50` index triple do not match any structure in `docs/rw_audio_structs.h`, and the
  field names in the port are positional (`kSlotWord0` and friends) for that reason. `u8[obj+49]`
  behaves like a *consumer* cursor — the latch at `+28` fires only when the producer has caught up
  to it — but that is inference from one function, not evidence.
