# sub_828E2E08 -- unlink a node from the container's `+12` list, free the container at zero

`r3` = the container, `r4` = the node. Returns the literal 0 (`li r3,0` on every path), and
`sub_82B1BF98` ignores it (`skate3_recomp.66.cpp:65859`). The node's links are `next` at `+0`
and `prev` at `+4`.

Four steps:

1. If the node *is* the cursor at `container+12`, the cursor advances to `u32[node+0]` first.
2. `prev != 0`: `u32[prev+0] = u32[node+0]`.
3. `next != 0`: `u32[next+4] = u32[node+4]`. Both links are re-read from the node rather than
   cached across step 2's store -- kept, since step 2 can alias the node when a list has been
   corrupted into a self-link.
4. `addic. r11,r11,-1` on `u32[container+4]`, stored back, and when the low word reaches zero
   the container is freed: `free(allocator, container, 0)` through vtable slot **+12** of the
   allocator held at `0x83083CCC`, the same `allocator->vtable[12](self, ptr, 0)` shape
   `sub_82B1E3F8`, `sub_82B1E458`, `sub_82B28970` and `sub_82B34D60` use. A null allocator
   pointer skips the free and the container leaks.

The node's own `next`/`prev` are **not** cleared, so an unlinked node keeps stale pointers.

`0x83083CCC` computed as `((-31992 & 0xFFFF) << 16) + 15564` = `0x83080000 + 0x3CCC`. It is on
the same page as the profiler run-state word at `0x830845CC` (`+17868`).

## The pair with sub_828E2EA0

`sub_828E2EA0` is this function with one offset changed: the cursor it fixes is at
`container+8`, not `+12`. Everything else -- the link offsets, the count at `+4`, the allocator
global, the free slot, the returned 0 -- is identical, instruction for instruction, and both
run 154 times a boot.

`sub_82B1BF98` calls both, on the same container (`u32[owner+8]`) and on two nodes embedded
20 bytes apart in the same element (`u32[owner+4] + 24`, then `+20` for the second). So the
element is registered in two lists of one container, each list keeping its own cursor, and the
count at `+4` counts registrations across both -- which is why two removals decrement it twice
and the container is freed when the last one goes.

## The decrement is not saturating

`addic.` runs 64-bit on a zero-extended `lwz`, so a count already at 0 becomes
`0xFFFFFFFFFFFFFFFF`: the store writes `0xFFFFFFFF` and `cr0` does not see zero, so the free is
skipped and the next call wraps down again. Reproduced, not fixed -- the native body keeps the
64-bit intermediate and tests the low word, as the lifted `cr0.compare<int32_t>(r11.s32, 0)`
does.

## Unverifiable, and why

**Gate 1**, at depth 0: the `bctrl` at `0x828E2E88` is an allocator *free*, reached through a
vtable slot loaded from `u32[0x83083CCC]`. Replaying the native body on rewound memory would
free the container a second time; no window rewinds an allocator's own book-keeping.

The gate is path-dependent and here that is actually usable: the call only happens when the
count hits zero AND an allocator is installed, both predictable from entry state before the
call (`REX_LOAD_U32(container+4) == 1` and `REX_LOAD_U32(0x83083CCC) != 0`). Of the 154 boot
calls, at most one per container can be the last, so the overwhelming majority take the
comparable path. If this function is ever worth comparing, `Windows()` should return true on
the non-final path rather than false everywhere -- that is a genuine comparison of the whole
unlink, which is the part with the aliasing subtleties. Not done here: the brief labels the
gate and moves on, and a partial-path window set is a design decision for the harness owner.

## The write set it would have declared

    const uint32_t c = ctx.r3.u32, n = ctx.r4.u32;
    if (REX_LOAD_U32(c + 4) == 1 && REX_LOAD_U32(0x83083CCC) != 0) return false;  // the free
    spec.write(c + 12, 4);                       // the cursor, only when it names this node
    spec.write(c + 4, 4);                        // the count
    const uint32_t prev = REX_LOAD_U32(n + 4);
    if (prev != 0) spec.write(prev + 0, 4);
    const uint32_t next = REX_LOAD_U32(n + 0);
    if (next != 0) spec.write(next + 4, 4);
    spec.read(c + 4, 12);  spec.read(n + 0, 8);  spec.read(0x83083CCC, 4);

Five spans at most, well inside the budget. Result mask `kReturnR3`, the constant 0.

## Unsure

- Whether `+4` is a registration count or a refcount. Freeing the container at zero fits both;
  two call sites decrementing the same word for two different lists fits the first better.
- What the container is. `docs/rw_audio_structs.h` documents nothing with a count at `+4` and
  cursors at `+8`/`+12`, so every offset here is a plain constant.
- Whether `0x83083CCC` is the same allocator `sub_828AAF88` returns (`sub_82B1E3F8` fetches it
  through that call instead of a global). Both are freed through slot +12, which is suggestive
  and not evidence.

## Split and armed, 2026-09-12

Converted from gate-1 to the path split this note proposed. STATUS is `pending (partial: ...)`.

- **Predicate:** false when `REX_LOAD_U32(container+4) == 1 && REX_LOAD_U32(0x83083CCC) != 0` — the
  only combination that frees — true otherwise. Both words are readable at entry.
- **Soundness of reading those words early.** The count and the allocator cell are read by the body
  *after* three stores (the cursor, `prev->next`, `next->prev`), and the node's links are re-read
  between them. So `Windows()` also declines when any store address overlaps a word read after it:
  the cursor store against `node+0`, `node+4`, the count and the allocator cell; the `prev` store
  against `node+0` (unless it is the same address, where it rewrites the value already there), the
  count and the allocator cell; the `next` store against the count and the allocator cell. A list
  corrupted into one of those shapes is skipped rather than windowed on a guess — a skip costs
  coverage, a missed window costs correctness. `Overlaps()` is a byte-range test, not an equality
  test, because `stw`/`lwz` need no alignment here.
- **Comparable write set:** at most four spans of 4 bytes — the cursor (only when it names this
  node), `prev+0`, `next+4` and the count. Reads `{container+4, 12}`, `{node+0, 8}` and the
  allocator cell.
- **Expected fraction:** the overwhelming majority of the 154 boot calls. At most one call per
  container can be its last, and the count is shared with `sub_828E2EA0` across two lists, so the
  final call is rarer still.
- **Stays unchecked:** the free, and with it whatever the container's last unlink leaves behind. The
  non-saturating decrement's wrap case (`0 -> 0xFFFFFFFF`) is compared if the game ever produces it,
  since that path does not free.
