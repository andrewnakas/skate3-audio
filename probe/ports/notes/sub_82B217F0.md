# sub_82B217F0 -- start the Dac profiler: round the config rate, start the worker, zero the block

`r3` = a config object. `+4` is the object handed to `sub_82B218E8`; `+12` is a float rate.
Returns 16 on both paths (`li r3,16`), so the value carries no information about which path
ran. No direct caller exists in the lifted sources -- it is reached through a function
pointer, and the dynamic census saw it once, at boot.

Guarded by the run-state word at `0x830845CC` (`lis r10,-31992 ; lwz r10,17868(r10)`). That
word is not a plain "initialised" flag: `sub_82B218E8` sets it to 1 or 2 and the shutdown at
`skate3_recomp.67.cpp:9226` clears it to 0. Non-zero means already running, and this call
then does nothing at all -- no stores, no timebase read.

The zero path:

1. `+12` is rounded half-away-from-zero (`fadds`/`fsubs` of the 0.5f at `0x8209975C`, chosen
   by `blt` against the 0.0f at `0x82165A10`) and truncated with `fctiwz`. Only the low word
   of the spilled doubleword reaches `r4`, so a NaN rate arrives as `0x80000000` and anything
   past `INT_MAX` saturates -- the same idiom `sub_82B2DAC8` uses.
2. `sub_82B218E8(config+4, rate)` starts the worker. It re-tests the same run-state word,
   sets the byte at `0x83067057` to 1, branches on `r4 == 0` versus non-zero, makes one
   indirect call, and finally writes the run-state itself.
3. The profiler block at `0x830BDEBC` is zeroed in the original's order: `+16` (the smoothed
   frame time), `+4` (the tick accumulator, stored as an integer zero), `+20` and `+24` (the
   two-slot frame-time history). Note `+28`, the slot index, is **not** reset.
4. `mftb` stamps `+8`, giving `sub_82B3C2D0` its first "previous stamp" to subtract from.

The `r3` config pointer is dead after the `lfs` at step 1 -- the original reuses `r11` for a
constant-pool base immediately after, which is what proves it.

## Unverifiable, and why

Gate 3. The zero path ends in `mftb` through `sub_82B1F7E8` and stores the raw tick count to
`0x830BDEC4`. Two runs of the same call store two different words there, so the original's
result and the rewrite's differ by construction and a shadow comparison can never pass. No
care in the port changes that. `Windows()` returns false, which is moot: the macro never arms
the shadow branch for a gate-labelled port. The body is still the deliverable -- it is the
readable form and the reference for the Rust port.

Worth recording for a future harness: the gate is **path-dependent** here, and this is the
one of the three functions where that is true. When the run-state word is non-zero the call
is a pure `li r3,16` with no stores and no timebase read, so it is fully comparable on that
path -- a real `Windows()` could read `0x830845CC` and return true with an empty write set
when it is non-zero, false when it is zero. That would be a genuine (if thin) comparison of
the guard. It is also the path the traced session never took: the one boot call found the
word at zero.

Gate 1 would still fail on the zero path with a stubbed clock: `sub_82B218E8` reaches a
`bctrl` (`queue.json`: `gate1 fail, reason indirect`), so it is not replayable on rewound
memory.

## The write set it would have declared

Nothing here depends on a mid-call value, so the block itself is enumerable from entry state:

    if (REX_LOAD_U32(0x830845CC) != 0) { spec.read(0x830845CC, 4); return true; }  // no writes
    spec.write(0x830BDEC0, 8);   // +4 the accumulator, +8 the timebase stamp
    spec.write(0x830BDECC, 12);  // +16 smoothed, +20/+24 the history slots
    spec.write(0x830845CC, 4);   // sub_82B218E8's run-state word
    spec.write(0x83067057, 1);   // sub_82B218E8's armed byte
    spec.read(ctx.r3.u32 + 4, 4);  spec.read(ctx.r3.u32 + 12, 4);
    spec.read(0x82165A10, 4);  spec.read(0x8209975C, 4);
    spec.read(0x8231A844, 4);  // the single sub_82B218E8 loads for its indirect call

plus whatever the `bctrl` inside `sub_82B218E8` writes, which is why the real answer on the
zero path is false regardless of the clock.

## Unsure

- What `config+12` measures. It is a float rounded to an integer and passed as
  `sub_82B218E8`'s `r4`, which that function only tests against zero, so nothing here pins
  down its units; a sample rate and a voice count are both consistent with the evidence.
- Why 16 is the status. Both paths return it, and with no direct call site there is nothing
  to read it against.
