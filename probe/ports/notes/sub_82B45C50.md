# sub_82B45C50

Non-leaf, 711 lifted lines, 76,462 calls per boot on `RwAudioCore Dac`. Census gate-1 pass, closure of
5: `82B269C0` and `82B453D8` (both already ported and verified), `82F4DED0`/`82F4DFB0` (sine and
cosine) and `82F52318` (a leaf that turns a direction into an angle -- it stores its two arguments
into the **caller's** parameter save area at r1+16/r1+24, reads them back as integers, and otherwise
only reads its own table). No import, indirect call, lock or allocation anywhere in the closure. Only
caller is sub_82B29BE0, twice, which sets r3 before its next call: mask `kReturnNone`.

Arguments: r3 = the panner entries (16 bytes each: x, y, lengthsq, angle), r4 = the channel count,
f1 = the centre's angle, f2 = the centre's distance, f3 = every entry's radius, f4 = an angle added to
the centre's before each spread, f5/f6/f7 = three spreads.

Shape. Both input angles are scaled by the single at `0x822F8E48`; the centre is `(cos a, sin a) * f2`.
Then one placement per entry: `(cos, sin)` of the centre angle plus one spread offset, times f3, added
to the centre, handed to sub_82B453D8 (which clamps the point into the unit disc and writes x, y,
lengthsq), then the clamped x and y go to sub_82F52318 and its `frsp`'d result is stored at `+12`.

The count is a branch table (`mtctr count-2` and six `bdzf 4*cr6+eq`), which decodes to:

| count | entries written |
|---|---|
| 1 | entry 0, by tail-calling sub_82B269C0 with every argument untouched |
| 2 | 0 and 1 |
| 4 | 0, 1, 2, 3 (loc_82B45F48) |
| 6 | 1 (loc_82B45EF4), then 0, 2, 3, 4 |
| 8 | 5 and 6 (loc_82B45E5C), then 1, then 0, 2, 3, 4 |
| 3, 5, 7 | nothing at all |
| 0, negative, > 8 | nothing: `count - 2 >u 6` is an UNSIGNED test |

That matches what sub_82B29BE0's note already records about this callee, from the other direction.
loc_82B45E5C falls through into loc_82B45EF4 and that into loc_82B45F48; loc_82B45EF4 also shifts the
three indices loc_82B45F48 uses from {1,2,3} to {2,3,4}, which is how entry 1 keeps its own placement.

The two-entry case has a special path: when f5 equals the single at `0x82256FD8`, the angle gets the
bias at `0x822538BC` and entry 1 is the **mirror** of entry 0 -- `centre - (dx, dy)` reusing the same
two products, with no second pair of trigonometric calls (which is why the original can destroy f31,
the radius, in the first placement). Otherwise it is an ordinary spread pair.

`stwu r1,-224(r1)` **is** reproduced: sub_82F52318 writes r1+16/r1+24, which is this function's own
frame, and the sine and cosine helpers spill below the live r1.

Window: one span, `[entries, entries + 16*n)` with n from the table above -- exact, since the count is
an entry register and every written entry is a prefix of the array. Per entry it is sub_82B453D8's
three singles plus this function's angle, so all 16 bytes. Returns false only on a null r3, where
sub_82B453D8 would store through null. Reads recorded: the four rodata singles this function loads,
the two sub_82B453D8 loads, the three sub_82B269C0 loads on the count-1 path, and sub_82F52318's
table at `0x82FB5068`.

Gates: 1 pass, 2 pass, 3 pass (no timebase), 4 pass. STATUS: **verified** -- the .inc header carries the status and the call count the harness session recorded; this note was written before that session ran.

Unsure of:
- No rodata value was read (`probe/harness/out/image` is empty on this tree); all four addresses are
  computed as `((imm & 0xFFFF) << 16) + offset` and loaded through the guest map.
- `82F52318` read as an angle-from-direction (atan2-shaped) is inferred from its arguments being the
  clamped y and x and its result being stored where sub_82B269C0's port already calls `+12` the
  "angle this call settled on". Its table span is recorded as 192 bytes covering the offsets its
  lifted body names; one indexed read there was not chased, and reads are not compared.
- `82F4DED0` = sine and `82F4DFB0` = cosine is consistent here (`DFB0`'s result becomes the x
  component and `DED0`'s the y) and in sub_82B45788, and with the note for sub_82B29BE0.
- The three "spreads" f5/f6/f7 and the name "centre" come from the geometry of the placements, not
  from any symbol.
- Operand order on commutative `fmuls`/`fadds` is kept as lifted for NaN propagation
  (docs/vmx128-exactness.md rule 4).
