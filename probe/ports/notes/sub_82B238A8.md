# sub_82B238A8

420 lines, 16 vector instructions, **62,273 calls per boot session**, `RwAudioCore Dac`. Not a
leaf: three callees. No caller in `generated/` — it is reached through a function pointer, so
where its `r5` comes from is not visible in this tree.

Per-voice gain staging for one 256-sample block. `r3` = voice state, `r4` = mix descriptor,
`r5` = forwarded to the generator untouched. Returns 1 in r3 on every path.

1. **Latch** (`state[0x70] == 1`): the pending request — span `0x40`, extra `0x44`, curve `0x48`,
   start time `0x38` — is copied into `0x58/0x68/0x72/0x50`; `fmuls` + `fctiwz` turn the span
   into a sample count at `0x5C`, clamped up to 1; the ramp arms (`0x71 = 1`, `0x70 = 0`).
2. **Place** (`state[0x71] == 1`): `cursor = -(int)(rate * (rampTime - desc[0x10]))` into `0x60`.
   A `rampTime` equal to the f64 at **0x822F8700** skips the subtraction and keeps the
   *sentinel's own* bits — the port preserves that rather than reusing `rampTime`, because
   `fcmpu` calls `-0.0` and `+0.0` equal. Ends at state 2 (running), 0 (already past the end), or
   stays 1 (offset >= 256).
3. **Envelope**: a running ramp has `sub_82B427D8` / `sub_82B42C98` / `sub_82B43340` (chosen by
   `state[0x72]`) fill the 256-float envelope at `desc[0x20]->+4`; the cursor then advances 256
   and the ramp ends at the sample count. Otherwise the 256 floats are filled with the held gain
   `state[0x6C]`, eight per pass — and a gain equal to the f32 at **0x8231A844** returns
   immediately with no stores at all.
4. **Apply** (the vector part): per channel, 16 passes of four `lvx128`/`lvx128`/`vmulfp128`/
   `stvx128` groups scale 1024 bytes of channel buffer by the envelope in place. Channel j lives
   at `chan[0x04] + ((chan[0x0E] * j) << 2)`, `chan = desc[0x1C]` — the same descriptor shape
   `sub_82B373C8` takes as its own `r4`, confirmed from `sub_82B376B8` passing `+0x1C` of the
   same object. The envelope is the **first** `vmulfp128` operand at all four sites; rule 4 of
   `docs/vmx128-exactness.md` makes that slot semantic, so it is not free to swap.
5. **Publish**: the block's last envelope sample becomes `state[0x6C]` and `state[0x34]`, and
   `state[0x30]` is stamped `0x7FF7FFF1`.

Stores: state `0x64/0x50/0x72/0x58/0x68/0x5C/0x71/0x70` (latch), `0x60`+`0x71` (place, and again
after the generator), `0x6C/0x34/0x30` (exit) — all inside `[0x30, 0x73)`, one 67-byte span; the
envelope block, 1024 bytes; one 1024-byte block per channel, `count = state[0x29]`. The two
`fctiwz` spills at `r1+80` are the function's own frame and are not windowed.

## Window rationale

The four `stvx128` of a pass are 16 bytes apart and each pass steps 64, so sixteen passes cover
exactly 1024 bytes from the channel's **16-byte-aligned** start. That alignment comes from the
`& ~0xF` in every effective address, not from the base pointer, which is what makes one span per
channel right whatever `chan[0x04]`'s alignment is.

### A running ramp is now windowed; an arming one still is not (changed 2026-09-12)

It used to return **false** whenever `state[0x70] == 1` or `state[0x71] != 0` — every call that
could reach a generator — on the grounds that the three generators "store through bases they
derive internally". Session `probe/harness/out/s20.log` priced that: **36,864 of 55,452 calls
skipped, 66%**, all logged `not enumerable`, so the green covered a third of the traffic and none
of the ramping.

That session also pins the cause exactly. At the last report, `sub_82B238A8 skipped=34,366` while
`sub_82B42C98 calls=34,361` and `sub_82B427D8 calls=5` — **34,361 + 5 = 34,366**. So every skip
was a generator dispatch and every dispatch was a skip: the channel-count guard and the
control-field check never fired once, and the whole 66% is the ramp predicate.

Half of that predicate was only conservative:

- **The bases derive from this call's own arguments, not from memory.** Every store in the lifted
  `sub_82B427D8`, `sub_82B42C98` and `sub_82B43340` was put through a flow-sensitive provenance
  pass (labels and `goto`s of the lifted C as the CFG, per-register atom sets to a fixed point).
  Outside the callee's own frame, **every** store address carries only entry `r3` (the envelope),
  entry `r6` (the cursor) and entry `r7` (the sample count). Not one carries a loaded value. The
  `stw` stores that made `sub_82B42C98` look like it touched six objects are `r1+116`, `r1+132`
  and `r1+144` — moving float scratch through GPRs inside its own frame. `r4` is "used" only by
  `subfe r3,r4,r4`, which is `-1 + CA` whatever `r4` holds, so even the one apparent dependence on
  an unrelated register is not one.
- **Their three callees cannot widen it.** `sub_824531C8` has no stores at all; `sub_82F4DED0`
  writes only below its own `r1`; `sub_82F52FB8` (the 16-byte forward replicate the fills use)
  stores only through its own `r3`, which is one of those envelope addresses.
- **The bound is the block — for a cursor in range.** All three open with `cursor + 255` and
  `min(cursor + 255, samples - 1)`, then write the pre-ramp fill, the ramp clamped at the second,
  and the post-ramp fill clamped at the first. Every vector run is `trunc(n/4)` quads with a
  scalar remainder, so no quad steps past its clamp. Sample *i* lands at
  `envelope + 4*(i - cursor)`. That is `[envelope, envelope + 1024)` — the same 256 floats the
  steady-gain fill writes, which is why the window **set** did not have to change at all, only the
  guard.
- **One adjustment.** The generators write those floats with `stvx128`, whose effective address is
  masked down to 16 bytes, so the span now starts at `envelope & ~0xF` and runs
  `1024 + (envelope & 0xF)` bytes: the floor for the generators, the unmasked top for the steady
  path's `stfs`. Moot if the envelope is 16-byte aligned (the ramp's own alignment prologue only
  makes sense if it is), but true either way.

### The cursor is what bounds it, and two entry states break that

"The generators write the block" is only true for `-256 <= cursor <= samples - 1`. Outside it they
write **without bound**, which is why the new guard is about the cursor and not about the callees:

- `cursor < -256`: the pre-ramp fill is `-cursor` samples and is **not clamped to the block** —
  `r29 = -trunc(cursor/4)` units of 16 bytes, straight off the argument. A cursor of −10⁶ fills
  4 MB from the envelope.
- `cursor > samples - 1`: the ramp span goes negative, both vector loops are unentered, but the
  index still moves by `4 * trunc(span/4)`, so the post-ramp fill starts *below* the ramp's start
  and runs to `cursor + 255` — longer than the block, unboundedly so as the gap grows.
  `sub_82B427D8`'s own port documents the same quirk from the other side, where it has to count
  those bytes ("which is how the trailing fill can end up longer than the block").

Which of the two dispatch routes can present such a cursor decides the split:

- **A running ramp** (`state[0x71]` neither 0 nor 1, nothing pending) — **now compared.** The
  latch needs `state[0x70] == 1` and the placement needs `state[0x71] == 1`, so both are skipped
  and the generator sees `state[0x5C]` and `state[0x60]` exactly as they are at entry. Both bounds
  are then plain integer comparisons on two words, no float work at all. In practice they always
  hold: the post-generator advance stores `cursor += 256` and drops the ramp when that reaches
  `samples`, so a surviving state 2 means `0 < cursor < samples`.
- **A pending or armed ramp** — **still refused, and genuinely so.** The placement step computes
  the cursor as `-fctiwz(rate * (rampTime - timeBase))` guarded only by `< 256`, and that guard
  admits exactly one dangerous value: `0x80000000`, which `fctiwz` yields for a NaN or for
  anything at or below `INT_MIN`, which `neg` leaves unchanged, and which the `> 0` clamp does not
  catch. The fill is then `2^31` samples. So the pre-ramp fill's **length is computed by the
  call**, and ruling out that one value means evaluating the guest's own float arithmetic inside a
  hook — host float work in a hook is the SIGFPE trap in CLAUDE.md, and these products (a
  multiply that can overflow, operands that can be NaN) are exactly the ones that raise. Not
  awkward: unwindowable without either reproducing that arithmetic or bounding it.

**What the refusal costs.** One call per ramp *start*, not per ramp: the arming call latches,
places and (usually) dispatches in the same call, and every later block of the same ramp is the
running case. s20 cannot separate the two — one skip counter covers both — but it bounds the
ratio: 34,366 dispatches against at most ~6,700 queue events in a boot session (the producer
`sub_82B28A00`'s count) is **at least ~5 dispatches per ramp**, so the refused class is at most
about a fifth of the dispatches, i.e. **≤ ~13% of calls, down from 66%**. The next session
measures it exactly, because `skipped` now counts nothing else: the channel-count guard and the
control-field check fired zero times in s20, and the running case's two bounds cannot fail while
the state machine is intact. **If `skipped` comes back near 30,000, ramps are one block long and
the estimate above was wrong** — in that case the integer-only route is the next move: refuse only
when `rate * position` could reach `-2^31`, decided from the IEEE exponent fields (no host FP),
which is sound for any `rampTime >= timeBase` with no magnitude bound at all and needs one for the
past-start case.

`Windows()` also still refuses **more than 30 channels** (32 spans and 32 KB both run out; the
stack scratch in `sub_82B373C8` implies the real bound is 8; worst case with the new span is
67 + 1039 + 30 × 1024 = 31,826 bytes over 32 spans, inside both budgets) and **a span covering
one of the three control fields** `state[0x29]`, `chan[0x04]`, `chan[0x0E]`, which the call
**reloads after** earlier stores (the count at the bottom of every channel pass, the descriptor
pair at the top). A span covering one would shift the remaining addresses mid-call and make the
list wrong, so every span is checked against all three and a hit returns false rather than being
assumed away. Neither fired in s20.

What the change costs elsewhere: a recorded vector for a ramping call is **not replayable
offline**, because replaying it means executing the guest generator. The read set therefore does
not bother declaring the generators' own rodata reads (`0x82165A10` and neighbours). Tier-1 replay
material still comes from the steady-gain calls; the ramping ones are compared in-process only.

## Gates

1 passes: the generators are pure functions of (envelope, cursor, samples, `f1`, `f2`) — no lock,
no allocation, no import, no indirect call, no timebase — and they write only a window, so
running them twice is safe. 2 passes on the steady and running paths and fails on the arming one,
handled by the split above rather than a whole-function `kPortGate2`. 3 passes: no `mftb`, no
indirect calls. 4: the stores plus `r3 = 1` on every path (`li r3,1` at the single exit), so
`kReturnR3`.

**STATUS is `verified`, and that label predates this change.** It was earned on a session where
the ramp predicate skipped 66% of calls, so the ramping path — the generators, the cursor advance,
the `state[0x71]` transitions — has never been compared once. Promotion to
`--skate3_audio_native=true` on the strength of that green would run a never-compared path.
Re-earn it: one session with this window set, `skipped` at or below the estimate above and
`diverged` still zero.

## Unsure

- The two sentinels (`0x822F8700` f64, `0x8231A844` f32) are compared, not interpreted; no guest
  image dump was on hand to read them. But `0x8231A844` is the **same word** `sub_82B3D0A8`'s port
  loads as its scalar paths' `1.0` (`lis r11,-32206 ; lfs f0,-22460(r11)`), and `1.0f` also reads
  right here: gain == 1.0 means unity, and the branch it takes skips the fill and the channel
  scaling entirely. Two independent uses consistent with 1.0f is not a reading of the image.
- Wiring: `SKATE3_CENSUS(14, sub_82B238A8)` in `skate3_audio_kernel_census.cpp` and the
  `sub_82B238A8` slot in `skate3_audio_census_all.cpp` define the same strong symbol; both must
  go when this lands in a manifest, or the link fails.

Both this port and `sub_82B238A8.inc` / `sub_82B373C8.inc` were checked with
`clang++-20 -std=c++23 -march=native -fsyntax-only -Wall -Wextra` against the real headers:
clean, with a deliberate-error control to prove the check was live. Neither has been built into
the game or run.
