# sub_82B46810

The channel router. Args: r3 = eight destination channel pointers, r4 = eight source channel
pointers, r7 = destination channel count, r8 = source channel count, f1 = the target gain,
f2 = the current gain. Void. Stores nothing itself -- its only store is its own `stwu`.

It looks up one (source count, destination count) cell of an 8x8 table and runs the byte program
that cell names, calling **sub_82B44D18** (the verified gain-ramp mix-add) once per byte.

Three rodata tables, addresses computed as ((lis_imm & 0xFFFF) << 16) + offset and then **read
out of the dumped image** (probe/harness/out/image), which decoded the whole format:

    0x820ED6C0  gain table, singles: 1.0, 0.707, 0.5
    0x820ED700  bound table, 128 bytes: 64 (first,last) program-index pairs
    0x820ED780  the program, 92 bytes, exactly 0x820ED780..0x820ED7DB
    0x822F8A00  the ramp rate, 1/65

The cell offset is `2 * (8*r8 + r7 - 9)`, i.e. row by source count, column by destination count,
both 1-based. A routing byte is `dst | src<<3 | gain<<6`: bits 0-2 index the destination pointer
array, bits 3-5 the source pointer array, bits 6-7 the gain table (only 0..2 ever occur; the
fourth slot at kGainTable+12 is the start of the bound table, so a 3 would read junk). Spot
checks that confirm the arithmetic: cell (1,1) = (0x54,0x54) -> one byte 0x00, dst0 <- src0 at
1.0; cell (1,2) = (0x00,0x01) -> 0x40,0x41, mono fanned to two channels at 0.707; cell (2,1) =
(0x06,0x07) -> 0x00,0x08, both sources summed into channel 0; cell (8,8) = (0x54,0x5B) -> 00 09
12 1b 24 2d 36 3f, the eight-channel identity. The last index in the table is 0x5B, which lands
on the last byte before the "rw::audio::core::mixer::mpMixBuffer" string -- the table ends
exactly where the arithmetic says it should.

Gains per entry: start = scale * f2, increment = scale * (f1 - f2) / 65. sub_82B44D18 ramps for
64 samples then holds f1 + 64*f2, so a ramp reaches 64/65 of the way to the target, not onto it.
Reproduced, not corrected.

Loop shape, reproduced literally: `lbzu r11,1(r29)` walks the program from `kProgram + first`,
and the LAST index is re-read from the bound table on every iteration (`lbz r7,1(r30)`), so the
trip count is re-derived each time rather than cached.

Callee, through GuestCall: **sub_82B44D18** only. Census gate1 pass, depth 0, closure size 1. It
is itself a verified port, so it is exercised by its own hook. It clobbers v14-v31 without saving
them; both runs call it with identical arguments in identical order, so the compared vector file
agrees at exit and nothing needs saving here.

Window rationale: this function's write set is entirely the callee's -- one 1024-byte block per
destination channel, at `(ptr & ~0xF)`, the span shape mirrored from sub_82B44D18's own Windows()
rather than re-derived. It is still enumerable from entry state because both inputs are: the
tables are rodata, and the two pointer arrays live in the caller's frame (sub_82B31838 builds
them at r1+112 and r1+80 with a 1024-byte channel stride). The walk is bounded -- first and last
are u8, so at most 256 bytes -- and only three bits pick a destination, so the spans dedupe to at
most eight, 8 KB of the 32 KB budget. Returns false when either array pointer is null, when a
selected destination channel is null, when a span would wrap 2^32, or when any write span
overlaps the tables or the pointer arrays, all of which are re-read inside the loop.

`stwu r1,-144(r1)` IS reproduced. sub_82B44D18 materialises two vectors through its own frame at
r1-112..r1-81, so without the move those stores land on this function's spill slots and the
native run's out-of-window footprint stops matching the original's. r26-r31 are saved and
restored in host locals, matching __savegprlr_26/__restgprlr_26.

Gate verdict: none fire. Callees replayable, write set enumerable from entry, no timebase, and
the output is entirely in the windows (kReturnNone -- all three call sites, skate3_recomp.67.cpp
48251/48276/48301 in sub_82B31838, treat it as void).

Unsure: nothing about the decode. Two soft spots. (1) If a bound cell holds (0xFF,0xFF) -- and 40
of the 64 cells do -- the range is not empty (255 > 255 is false), so one garbage byte would be
executed from inside a string constant. No caller should reach those cells, but Windows() does
not special-case them: it enumerates whatever the byte names, which is still a pointer out of the
entry array. (2) The re-read overlap guard assumes the reachable program range is
kProgram..kProgram+255; that is the u8 index bound, not a table length read from anywhere.
