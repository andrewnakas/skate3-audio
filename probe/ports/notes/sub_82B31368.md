# sub_82B31368

Six lifted lines, all of them `b 0x82b31480`: a pure alias, no frame, no register use of its own.
No static call site exists in the lifted corpus (`grep 'sub_82B31368(ctx, base)'` over
`generated/` is empty), so the 2966 boot calls arrive through a function pointer -- most likely a
vtable slot that 0x82B31480 also fills directly. That is why the alias exists.

Native: `GuestCall(ctx, base, sub_82B31480)` with no arguments. A tail branch passes r3..r10
through untouched and leaves LR holding this function's own return address; GuestCall writes no
argument register and does not touch LR, so the two are the same machine state. No `stwu` to
reproduce -- 82B31368 allocates nothing, and the callee spills below the live r1 exactly as it
would under the original caller.

## Why the gathering path is still enumerable

sub_82B468C0's whole subtree writes only into 82B31480's frame, and that is checkable rather than
assumed:

- `sub_82B3BED8` and `sub_82B44B20` (both ported, both verified) write exactly
  `[r3, r3 + 4*r6)`. 82B31480 passes `li r7,1`, which sub_82B468C0 forwards as the count, so
  every such call writes four bytes. The count also forces the scalar path (`count & 0x3F != 0`),
  so the non-terminating vector case their Windows() refuses cannot arise here.
- `sub_82EE5E80` is memset (`skate3_recomp.103.cpp:14877`: `r5 < 16` is a byte loop of `r5` bytes
  from `r3`); it is called with the same length of 4. No lock, no allocation, no indirect call.
- `sub_82B426D0`'s only stores of its own are its frame (`stwu`) and an eight-byte "already
  touched" flag array at its `sp+80` (`stbu`, `stbx`); every buffer it touches it reaches through
  the two pointer arrays it was handed, decoding a destination index as `byte & 7` and a source
  index as `(byte >> 1) & 0x1C`.
- In every one of those calls the destination is an entry of the `sp+112` array, i.e. a word of
  82B31480's own frame scratch, and `voice+80..108` is the SOURCE side. Direction confirmed at
  `sub_82B468C0:loc_82B46954` (`lwz r3,0(r31)` walks the A array, `lwzx r4,r26,r31` picks the
  matching B entry) and at `sub_82B426D0:loc_82B42728` (`lwzx r3,r9,r29` dst, `lwzx r4,r10,r28`
  src).

What does have to be predicted from entry state is that the array indices stay within eight
entries: the gather loop trips `voice[+41]` or `voice[+78]` times and the memset loop runs from
`voice[+41]` to `voice[+78]-1`, so past eight the original walks off the array into the scratch
area, reads whatever words are there as pointers and stores through them. `Windows()` refuses when
either byte exceeds 8 rather than trying to describe that.
