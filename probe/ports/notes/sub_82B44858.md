# sub_82B44858

Lifted: `skate3_recomp.68.cpp:27274`, 401 lines. One profiled pass over a node graph. 18,684 calls
per boot session on `RwAudioCore Dac` -- one fewer than `sub_82B48530`, so this is almost certainly
reached once per drain.

## Arguments

- `r3` the object ("self"). Nothing in `docs/rw_audio_structs.h` covers it; every name in the port
  is read off this function. `+0`/`+4`/`+8` are three sources, `+0x10` receives eight bytes copied
  from the params, `+0x18` is a device object (only its byte at `+0xFC` is read), `+0x1C`/`+0x20`/
  `+0x24` receive the three record addresses, `+0x28` parks the params pointer, `+0x2C` the total
  elapsed, `+0x38` a float reset every pass.
- `r4` the params: a doubleword at `+0` copied as bits, an array of 8-byte entries at `+8` whose
  first word is a node pointer, and a u16 count at `+0x14`.

## Three descriptor records at 0x83077650

`((-31993 & 0xFFFF) << 16) + 30288`. Three of them, stride 276, and each gets exactly five fields:
`+0` = self's device object, `+4` = self+0/+4/+8 respectively, `+12` = u16 0, `+14` = u16 256,
`+16` = u8 device->+0xFC. Their addresses are published at self+0x1C/+0x20/+0x24.

The three groups write the same five fields in **three different orders**, and each one reloads
self+0x18 and re-reads the device byte, so the port writes them out rather than looping.

## The node pass

Per params entry: `node = *(u32*)(params->+8 + 8*i)` -- the other four bytes of each entry are
never read. Then

- if `node->+70 < 255`: copy `params->+0` (8 bytes) to `self+0x10`, call
  `sub_82B444C0(self, node->+0x18, node)`, and resume the child walk at `node->+70 + 1` -- the byte
  is **reloaded** after the call. Otherwise resume at 0 with status 1.
- copy `params->+0` again, on both paths.
- when status == 1 (a SIGNED compare against 1, not "non-zero"), walk children
  `i .. node->+68`, each `child = *(u32*)(node + 80 + 4*i)`:
  - `child->+40` non-zero: skip the work, but still time it and still advance.
  - else call `(*(fn**)(node->+0x18 + 8*i + 8))(child, self, i > node->+69)` through `bctrl`.
    Non-zero result and `i == 0`: zero `node+44`. Zero result: `sub_82B443F8(self, node, child, 256)`,
    and if that is zero too, leave the walk **without** timing this child and without advancing.
  - `child->+36 = elapsed`.
  - The bound `node->+68` is re-read at the bottom of every pass.
- if status is still 1 afterwards, `node->+69 = node->+68` (the count reloaded).
- the timing tail: `node->+60 = elapsed`, `node->+0 = (node->+4 + node->+8 + (float)elapsed) *
  0x822F87B8`, `node->[4*(flag+1)] = (float)elapsed`, and `node->+12 = (node->+12 == 0)`. The two
  floats at `+4`/`+8` are a two-slot ring the flag alternates between, so `+0` is a three-tap
  average -- which makes the constant at `0x822F87B8` very likely 1/3, though its value was not
  read.

## Gate verdict

**gate-1, at depth 0, one indirect call.** Each child's process function is fetched from guest
memory (`node->+0x18`, entry `8*i`, field `+8`) and entered through `mtctr`/`bctrl` at 0x82B44A20.
It is an arbitrary callee -- on this path the per-node audio work -- so it allocates, signals or
submits, and cannot be replayed on rewound memory.

It **also fails gate 3**: `sub_82B1F7E8` is a bare `mftb`, called 4 + 2N times here, and six of the
stores are differences of two of its readings. Even with the indirect call made replayable, none of
the timing fields could ever compare equal.

Gate 2 would fail as well: the write set covers every node of an array whose count is a u16 and
every child of each node, and the census marks 25 stores `gate2_suspect`.

## Return mask

`mr r3,r27` at the exit: r27 starts at 0, becomes 1 on the state==255 path, and otherwise holds the
last of `sub_82B444C0`'s result, the child function's result or `sub_82B443F8`'s result. So r3 is a
real return value here, not the incidental leftover the other four ports have -- `kReturnR3` is the
honest mask, not just lint check 5's requirement. A zero params count returns 0.

## Uncertainties

- The values of the three float pool constants were not read: no decrypted guest image is in the
  tree, and reading one needs a running build. `0x82165A10` is the exception -- `sub_82B2DAC8.inc`
  already identified it as the zero constant, which is why "zero" here is a cross-check rather than
  an assumption. `0x822F87B8` is presumed 1/3 from the three-tap shape and `0x8231A844` is
  unknown.
- `subfc` / `eqv` / `rlwinm` / `addze` / `clrlwi` is the branchless SIGNED `node->+69 < i`
  reduction. Verified by case analysis on the sign-equality bit: when the signs agree the result is
  the inverted borrow, and when they differ it is the borrow itself, which is the signed answer
  either way. Both operands are an `lbz` or a counter bounded by one, so it never matters in
  practice. The port writes the comparison and notes the idiom rather than reproducing the five
  instructions.
- `rlwinm r4,r5,27,31,31` after a `cntlzw` is written as `== 0`: bit 5 of a count-leading-zeros
  result is set only for the value 32, and 32 only happens for a zero input.
- What the three records at `0x83077650` are for is not established. Each is 276 bytes and only
  five fields are written, so the rest is set up elsewhere; the u16 256 at `+14` and the 256 passed
  to `sub_82B443F8` are probably the same buffer length.
- `node->+70` is both the state byte (255 selects the restart path) and the resume point (its value
  plus one is where the child walk starts). That dual use is read off this one site.
