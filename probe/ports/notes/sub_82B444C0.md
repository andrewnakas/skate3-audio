# sub_82B444C0

- Role: `int render_block(mixer* r3, source_table* r4, stream* r5)` — fill one 256-frame block.
  Outer loop, once per "round", until 256 frames are produced or a source stops:
  1. stamp `f32[mixer+56]` with a pool constant;
  2. **descending** walk of sources `u8[stream+70] .. 0`, each through `u32[desc+4]`, threading the
     remaining length through r6 and replacing it with the signed-clamped-to-256 return: the last
     call's *input* is kept in r23 for the fallback below;
  3. **ascending** walk of the same sources through `u32[desc+8]`; a source returning 0 is retried
     through `sub_82B443F8(mixer, stream, sink, r23)`, and if that also returns 0 the walk stops;
  4. when the walk's last status is 1: copy `u32[mixer+48]` frames per channel from the buffers at
     `u32[mixer+28]` into those at `u32[mixer+36]`, offset by what earlier rounds produced, and add
     `float(frames)/f32[u32[mixer+40]+12]` to the double at `mixer+16`.
  Then, once: copy all 1024 bytes per channel from `+36`'s buffers into `+32`'s and swap `+28` with
  `+32`, so the caller always reads the finished block from `+28`. Returns r21, the last status,
  forced to 1 on the "ran short" path. 524 lifted lines, four direct callees, **two** indirect
  calls, no imports, no lock. 205,116 boot calls on `RwAudioCore Dac` (tier D) — the busiest
  function in this batch by two orders of magnitude.
- Arguments: r3 mixer, r4 the source table (8-byte slots; only `[+0]`, the descriptor pointer, is
  read here), r5 the stream. Per-source sink objects come from `u32[stream + 4*(index+20)]`, i.e. an
  array at `stream+80`.
- Stores: `stfs [mixer+56]` 4 per round; `stw [sink+36]` 4 twice per source per walk (the cost
  counter, zeroed on round 0 only); `stfs [stream+44]` 4 (source 0 only, on a nonzero render);
  `stfd [mixer+16]` 8 per mixing round; `stfs [mixer+52]` 4 and `stb [mixer+60]` 1 on the short
  path; `stw [mixer+28]` and `stw [mixer+32]` 4 each (the swap); `stw [mixer+48]` 4 = 256 at exit.
  Plus the `stwu` back chain and the `std r11,80(r1)` int-to-double spill, both this call's own
  frame and neither a window.
- Two dead guards, kept as comments rather than code: `lbz r31,70(r24)` then `cmpwi ; blt`, and
  `lbz r11,70(r24)` then `cmplwi ; blt` — a zero-extended byte is never negative and an unsigned
  compare is never below zero, so **both walks always run**, and they run `u8[stream+70] + 1` times.
  That reads `+70` as the LAST source index, not a count.
- The r5 argument to both indirect calls is clang's branchless signed `(int32_t)u8[stream+69] <
  index` (`subfc`/`eqv`/`rlwinm 1,31,31`/`addze`/`clrlwi`), reproduced as the plain compare in
  `ExtraFlag()`; the derivation is in the comment there, and it holds for all inputs, not just the
  byte-sized ones this site passes.
- Every compare against the running total r22 is `cmplwi`, on the LOW WORD of a 64-bit sum
  (`add r22,r25,r22` on a zero-extended `u32[mixer+48]`), so the port truncates at each compare and
  keeps 64 bits in the sum and in the address arithmetic. `fadd` at `mixer+16` is a **double** add;
  the divide feeding it is `fdivs`, single.
- Constants, each `((imm & 0xFFFF) << 16) + offset`: `lis -32234` + `23056` = **0x82165A10**, the
  same pool zero `sub_82B2DAC8` reads; `lis -32206` + `-22460` = **0x8231A844**, the value stamped
  into `mixer+56`.
- Result: **r3 = r21**, the status.
- Gate 1 **fails** at depth 0, twice: the `bctrl` at **0x82B4457C** (`u32[desc+4]`) and at
  **0x82B44618** (`u32[desc+8]`), both function pointers out of a table the caller supplies. Every
  path takes both. `Windows()` returns false.
- Gate 3 **also fails**, and that is worth recording separately: `sub_82B1F7E8` is a seven-line
  `mftb` read (census `timebase: 1`), called twice per source per walk, and its difference is stored
  into `u32[sink+36]`. Even with the two indirect calls removed this function could never compare
  byte for byte — the cost counter is wall-clock. A future comparable version would have to exclude
  `sink+36` from the window set or stub the timebase.
- The write set I WOULD have declared: `{mixer+16,8}`, `{mixer+28,8}`, `{mixer+48,16}` (48, 52, 56
  and the byte at 60), `{stream+44,4}`, `{sink+36,4}` for each of `u8[stream+70]+1` sinks (all
  readable from entry state), plus the destination ranges of the memcpy/memset loops — those depend
  on `u32[mixer+48]` and `u8[mixer+60]`, which the source callbacks themselves write DURING the
  call, so the copy targets are not knowable from entry state. Gate 2 would fail on that alone.
- Unsure: the `+28`/`+32`/`+36` triple. The reading in the port — `+28` is what the caller reads,
  `+32` the spare half, `+36` the assembly area — comes from the exit sequence (copy `+36` to `+32`,
  then swap `+28` and `+32`) plus the `r16` fast path, where a first round that delivers all 256
  frames skips **both** the staging copy and the exit copy, which only makes sense if the sources
  wrote straight into what the caller reads. That is an inference from one site. Also unsure what
  `+52` means: it is loaded from and stored back to the same word, so this function only forwards it.
