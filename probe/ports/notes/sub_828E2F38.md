# sub_828E2F38

One hundred and nine lifted lines, twelve of them frame. Leaf, no imports, one `bctrl` inside
a list walk. Like `sub_828E29C0` it sits in `skate3_recomp.47.cpp`, outside the audio
translation units -- it is the generic "publish a value and notify" primitive of the same
family (`828E29C0`, `828E2D78`, `828E2E08`, `828E2EA0`, `828E30B8`, `828E2F38`), pulled into
the corpus by audio callers.

Arguments: `r3` = a handle record (`+0` holder, `+4` generation token), `r4` = the address of
the incoming word (read once, never written).

Holder layout: `+0` listener list head, `+4` the stored word, `+12` the generation the handle
must match. Node: `+0` next, `+8` function pointer, `+12` registration data.

Behaviour: validate, then compare-and-publish. If the incoming word equals the stored one,
nothing happens at all and the result is 0. Otherwise the list head is snapshotted, the new
word is stored, and every listener is called with **the address of the cell** in `r3`
(`holder+4`) and its own data in `r4`.

Results, all four: the token word zero-extended when it was already negative; -6
sign-extended when the holder is null; -3 sign-extended when the generation moved on, after
writing `+4` = -3 then `+0` = 0 into the handle; 0 otherwise. The zero- versus sign-extension
split is the same trap as in `sub_828E29C0` -- `mr r3,r9` after an `lwz` leaves
`0x00000000FFFFFFFD`, `li r9,-3` leaves `0xFFFFFFFFFFFFFFFD`, and the harness compares all 64
bits. Spelled out in the body.

Two preserved orderings: the list head is loaded *before* the value is published, so the walk
uses the pre-store snapshot; and `next` is read from `0(r31)` *after* the callback has run, so
a listener that frees its own node reads freed memory. Neither is corrected.

Stores, three outside the frame: `{handle + 4, 4}` and `{handle + 0, 4}` on the stale path,
and `{holder + 4, 4}` on the publish path. Mutually exclusive.

Gate verdict: **gate 1**, at depth 0. The `bctrl` target is the stored pointer at `node+8`,
and the list length is not bounded from entry state, so neither the targets nor the number of
calls is knowable. A replay would re-notify every listener with a value that, from their point
of view, did not change the second time -- worse than merely irreproducible, because the
notify is the whole observable effect of the function.

**One path is worth flagging for a later re-screen**: when the incoming word already equals
the stored one, the function writes nothing and calls nothing, and that is decidable from
entry state (`*(r4) == *(*(r3)+4)`, both readable before the call). The same is true of the
three error paths. A split port could compare those and skip the publish path. It would be a
thin verification -- the no-change path has no stores at all, so it proves only the four
result values -- but the stale-handle path does write two words and is genuinely comparable.
Labelled gate 1 as a whole because nothing measured says how the 3,442 calls a session divide
between the paths.

Write set that would have been declared if it were comparable: on the stale path
`{handle, 8}` (the two words are contiguous, one span); on the no-change and error paths,
nothing. Reads: `{handle, 8}`, `{holder + 0, 16}` when the holder is non-null, `{r4, 4}`.
Result mask: r3 on every path.

Uncertain, and it matters: this holder checks the token against `+12`, while
`sub_828E29C0`'s checks it against `+8`. Either the two functions serve different holder
types, or one of the fields is not the generation. Both read `+0` as the list head and both
use the same node layout (`+0`/`+8`/`+12`), which argues the *node* type is shared and the
holder type is not. Nothing here settles it, and no struct in `docs/rw_audio_structs.h`
covers either, so the offsets stay plain constants. Also unknown whether the value at
`holder+4` is an integer or a float -- the compare is a raw `cmplw`, which does not say.
