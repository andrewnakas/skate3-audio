# sub_82B389A0

Leaf kernel, 280 lines, 42 vector instructions, **30,395 calls per boot session**, first called on
`RwAudioCore Dac`. No callees, no imports, no indirect calls, no timebase, no locks.

Four-lane one-multiply allpass stage. Per lane, over `n = r3` samples:

    d = c - a*t          -> stored to r8
    y = a*d + t
    acc = y*g + acc      -> stored to r9

Arguments: r3 = n, r6 = c (aligned, `lvx128`), r7 = t (read UNALIGNED, each group as
`lvlx(p) | lvrx(p+16)`), r8 = d, r9 = acc, r10 = a flag, f1 = a, f2 = g. r4 and r5 are not
inputs. Calling the shape an allpass is an inference from the arithmetic — no symbol or plug-in
metadata covers this function — but the port reproduces the arithmetic, not the name.

Three regions in the lifted body:

- `r10 == 0`: a `dcbzl` loop clearing acc, `(acc + 128k) & ~127`, 128 bytes, for
  `ceil(4n/128)` lines. `r10 != 0` is the same loop with only the `dcbt` prefetches, so it has
  no memory effect and its exit value of r11 is overwritten immediately — nothing to reproduce.
- eight `stfs` into the own frame (-128(r1) for a, -112(r1) for g), read back as two vectors.
  Own frame, so not windowed; reproduced so the `lvx128` reading them back sees the same bytes.
- the main loop, `ceil((n/4)/4)` iterations, 64 bytes per iteration into each of d and acc, four
  `vnmsubfp` and eight `vmaddfp` per iteration.

**Stores.** `(d + 64k + {0,16,32,48}) & ~0xF` and `(acc + 64k + {0,16,32,48}) & ~0xF`, 16 bytes
each, in the lifted order d[2],d[0],d[1],d[3] then acc[2],acc[0],acc[1],acc[3]. Plus the dcbzl
lines. Every acc load in an iteration precedes every store in that iteration, so the read-modify
-write is safe to keep in source order.

**Two deliberate overruns, both reproduced and both windowed.** The loop count is a *ceiling*:
when `n/4` is not a multiple of four it runs past n, up to the next multiple of 16 samples (n=20
writes 32). And `dcbzl` clears from acc's 128-byte floor for `ceil(4n/128)` lines, so it can
clear below acc and up to 127 bytes past the pass. Both are in the declared windows.

**Windows: enumerable, true except on a negative count.** Every effective address reduces to one
of the four bases plus a multiple of 16, so `(A + 16m) & ~0xF == (A & ~0xF) + 16m` and each
buffer collapses to one contiguous run; both trip counts are closed forms of r3. Three write
spans. `return false` on `n < 0`, where `rlwinm r10,r3,2,0,29` becomes an unsigned length near
2^32 and the dcbzl loop would sweep gigabytes — a real write set, but not one worth enumerating;
the other `return false` is an overflow guard at 2^24 samples, above the harness's 32 KB budget
(12 bytes written per sample).

**v29, v30 and v31 are clobbered and the harness compares them.** They sit in the ABI-preserved
range and `__savegprlr_21` saves only GPRs, so the native body carries their live-out values: v29
the last c[3] load, v30 the last y[2], v31 the last acc[2] load — taken *before* the store to
that same address, so the pre-store bytes. The loop always runs at least once when reached.
Everything else the body leaves behind (v0, v1, v3-v13, v56-v63) is volatile scratch.

**Mask `Gpr(3) | Vr(2)`, because the one call site is a tail call.** The only caller
(`skate3_recomp.67.cpp:67099`) reaches this with `b 0x82b389a0`, so whatever the kernel leaves in
the ABI result registers becomes its caller's result. The lifted body writes two of them:
`subf r3,r6,r9` (only on the path where `n/4 > 0`) and `vor128 v2,v57,v56` (the last tap group).
Both are reproduced, and naming them makes the harness check the reproduction rather than trust
it. r3 is assigned as a 64-bit subtract, as lifted, since it is compared as all 64 bits. f1 is
the third result register and is only read here, never written.

**Gates.** 1 pass (leaf), 2 pass, 3 pass, 4 pass. r21-r31 return through `__restgprlr_21` and the
native body does not touch them. STATUS `pending`.

**Unsure of:** which of c and t is the input and which the delay tap. t is read unaligned, which
fits a ring-buffer read pointer, and d is stored with `stvx128`'s forced alignment, which says
d must be aligned; that is consistent with t being the delay line and c the block input, but it
is not proven. Nothing in the port depends on the answer. Also unverified: whether `r10 != 0`
ever happens during play — if it does not, the dcbzl clear is the only path the session
exercises, and the comparison says nothing about the other.
