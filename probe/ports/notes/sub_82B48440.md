# sub_82B48440

- Role: `void f(rw_system*)` — drain the system's list at `+0x20`. For each object on it (the list
  node sits at `object+28`, so the walk does `container_of` by hand with `addi r29,r28,-28`):
  for each of the `u8[object+68]` record pointers at `object+80`, replay that record's
  `u8[record+43]` ids through `sub_82B48BB8(system+112, id)` — the ids are walked with
  `lwzu r4,4(r6)` from `record+20`, so the first one read is `record+24`; then unlink the node
  from the list headed at `u32[u32[object+16] + 32]`, clear `u8[object+71]`, and call
  `sub_82B49280(object)`. 142 lifted lines, two direct callees, no own indirect call, no imports,
  no timebase, no lock. **18,685 boot calls** on `RwAudioCore Dac` (tier D).
- Argument: r3 = the system. `docs/rw_audio_structs.h` labels `+0x20` `list_20` with the comment
  "walked by `sub_82B48440`" — this is that walk, and it confirms the field. `system+112` is
  `+0x70`, which the same header says is the `rw_scheduler`, so `sub_82B48BB8` is being handed the
  scheduler and an id per call. The object's own `+16` is re-read as the list owner rather than
  assuming it is the system.
- Stores (4, all outside this call's frame):
  - `stw r10,32(r9)` — `u32[owner+32] = u32[head+0]`, 4 bytes, only when this object's node **is**
    the head
  - `stw r9,0(r10)` — `u32[prev+0] = u32[node+0]`, 4 bytes, only when `s32[node+4] != 0`
  - `stw r11,4(r10)` — `u32[next+4] = u32[node+4]`, 4 bytes, only when `s32[node+0] != 0`
  - `stb r27,71(r29)` — `u8[object+71] = 0`, 1 byte, unconditional per object
  - the `stwu` back chain is this call's own frame; never windowed.
  `u32[node+0]` is **reloaded** at `loc_82B48500` after the store that could alias it, and both
  loop counts (`u8[object+68]` and `u8[record+43]`) are reloaded every iteration, so
  `sub_82B48BB8` can shorten either walk. All three are reproduced as reloads. Both loop tests
  are `cmpw` — **signed** — against a zero-extended byte.
- One thing worth flagging for anyone porting the callee: `r3`, `r5`, `r6` and `r7` are **volatile
  and live across `bl 0x82b48bb8`**. The original leaves the record pointer in r5, the id cursor
  in r6, the counter in r7 and the scheduler in r3, and reads all four again after the call. That
  implies `sub_82B48BB8` preserves them — a custom calling convention, which the XDK compiler does
  emit under LTCG — but the port does not rely on the implication: it keeps those four in the
  guest registers across the `GuestCall`, so the body sees exactly what the original would see
  whatever the callee does to them.
- Result: **none** honestly — no `li r3,...` on any path, so r3 is the system when the list is
  empty and `sub_82B49280`'s result otherwise. The macro line carries `kReturnR3` because a
  gate-labelled port with a false `Windows()` and `kReturnNone` trips lint check 5; the mask is
  never read for a gate label. A comparable version would declare `kReturnNone`.
- Gate 1 **fails at depth 1**, and this is the failure `docs/shadow-harness.md` already records:
  "`sub_82B48440`, in the same PLAN bullet, dies two levels down at `sub_82B49280`'s two indirect
  calls. A one-level screen would have passed both." Read from the callee, those two are the core
  allocator's vtable — `u32[u32[owner+36] + 0]` slot **+4** (allocate) at **0x82B492EC** and slot
  **+12** (free) at **0x82B49328**, the same chain `port_82B3C930`, `port_82B32870` and
  `sub_82B3D668` all reach. The call here is `bl 0x82b49280` at 0x82B4851C, unconditional for
  every object on the list. `docs/shadow-harness.md`'s screening table also lists this function in
  the gate-1 row with `sub_82B48A50` and `sub_82B48530`; this port is the first time its body has
  been written out.
- The write set I WOULD have declared: per object `spec.write(object + 71, 1)`, plus at most
  `spec.write(owner + 32, 4)`, `spec.write(prev + 0, 4)` and `spec.write(next + 4, 4)` — four
  spans and 13 bytes per object, all derivable from entry state because the pointers are read
  before they are overwritten (the pattern `port_82B34BD0` was verified on) — plus
  `sub_82B48BB8`'s write set per id and `sub_82B49280`'s per object. The last is the blocker. With
  a list of more than eight objects it would also hit the 32-span cap, so gate 2 is a second,
  independent problem here. Reads `{system+32, 4}`, `{object+16, 4}`, `{object+68, 1}`,
  `{object+80, 4*count}`, `{node, 8}`, `{owner+32, 4}`, `{record+20, 4 + 4*ids}` and
  `{record+43, 1}` per record.
- Unsure: what the objects are, and what `u8[object+71]` means — it is only ever cleared here.
  `u8[object+68]` doubling as "how many of the `+80` slots are live" is inferred from the loop
  bound alone. `sub_82B48BB8` was not read; "replay the ids" is a reading of the call shape
  (scheduler, id) repeated once per id, not of its body.
