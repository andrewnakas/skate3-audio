Every deep callee is bounded by its own already-verified port, which is what makes this
enumerable at all: sub_82B3BED8 and sub_82B44B20 write exactly `[r3, r3 + 4*r6)` and r6 is the
literal 256 sub_82B21D98 passes, so 1024 bytes; 256 also forces those two past the
non-terminating vector case their Windows() refuses (`len & 127 == 0` holds). sub_82EE5E80 is
memset (read by hand at `skate3_recomp.103.cpp:14877`; not in the census because it is outside
the audio corpus) and gets the same 1024. sub_82B46B30 writes 24*256 bytes from r3, or nothing on
its early-out. sub_82B20E18 writes `512 * outputs`, which at eight outputs or fewer is inside the
6144-byte block.

Two refusals, both predicted from entry state:

- `outputs > 8`: the `sp+112` array holds eight pointers, and past that the fill loop and the
  memset loop walk into the frame scratch behind it.
- a routing byte naming `b & 7 >= outputs`: that destination pointer was never written, so the
  original mixes 1024 bytes through an uninitialised frame word. The table is ROM indexed by the
  output count, so this should never fire; it is checked rather than assumed because the address
  is unnameable if it does. A run longer than 64 bytes is refused as well rather than walked.

`block` is computed in 32-bit arithmetic on purpose: the lifted `add r31,r11,r10` is 64-bit, but
the value reaches memory only as a store base (`r10.u32`), and r31 is restored by
`__restgprlr_29` before return, so no carry into bit 32 is observable. The same applies to the
destination pointers: `stwu r11,4(r10)` truncates a 64-bit running sum at each store, which is
`(base + i*stride) mod 2^32`.
