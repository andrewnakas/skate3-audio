# sub_82B49100 — retire an object: unlink, reset, deregister, relink

Arguments: r3 = the object, r4 = a word parked at self+76. Void — r3 at return is the object on the
early-exit path and `sub_82B49438`'s status on the others, which no caller can use consistently, so
the result mask is `kReturnNone`.

Structure (r3). Only +16 is named anywhere: it is the same owner pointer
`recomp/src/audio_ports/sub_82B49438.inc` calls `kOwner`, on the same object.
+0/+4/+8 three floats, +16 owner, +28/+32 an intrusive node (next/prev), +60 unknown, +68 a u8
handle count, +71 a u8 state, +76 the r4 slot, +80.. the handle pointers. The owner has **two** list
heads: +20, which the node is taken off, and +16, which it is pushed onto.

Body:
1. `state == 2` → return immediately, not one store.
2. `state == 1` → unlink `self+28` from the owner's +20 list: if the head is this node, the head
   becomes `node->next`; then `prev->next = node->next` if prev, `next->prev = node->prev` if next.
   Both node words are **reloaded** between those steps.
3. Always: read the count, then `self+76 = r4`, `self+60 = 0`, `self+71 = 2`, and the three floats
   at +0/+4/+8 set from the constant at **0x82165A10** (`lis -32234 ; lfs 23056`, computed — the
   same constant `port_82B269C0` calls `kZeroFloat`). Kept as an `lfs`/`stfs` round trip, not a bit
   copy.
4. For each of `self[68]` handles at self+80, +84, …: `handle[+36] = 0`. The count is **reloaded**
   every iteration; the walk is `lwzu 4(r10)` from self+76, so it starts at self+80.
5. `sub_82B49438(self)` — drop the object from the owner's handle array.
6. Relink: reload `self[16]`, read `owner[16]`, set `node->prev = 0`, `node->next = owner[16]`, read
   `owner[16]` **again**, and if non-zero set `old_first->prev = node`; finally `owner[16] = node`.

Windows is built in three phases, because each re-read only has to survive the stores that precede
it:
- **A** — owner+20 (declared unconditionally, so the "is the head this node" branch need not be
  predicted), prev+0, next+4, self+76, self+60, self+71, self+0..11, handle+36 per handle.
- **B** — `sub_82B49438`'s set, MIRRORED from `recomp/src/audio_ports/sub_82B49438.inc`: owner+280
  (u16) and the memmove over `[array + 8*index, + 8*((count-1) - index))`, with the same `rlwinm 3`
  arithmetic, the same 1024-entry bound, and the same "did the search find it" prediction. A change
  to that port's write set requires a change here.
- **C** — self+28..35, the old first node's +4, and owner+16.

Windows returns false when: r3 or the owner is null; a handle pointer is null; the handle count
exceeds 16 (span budget); the array count exceeds 1024; the memmove span would wrap 2^32; or any of
these re-read fields is inside an earlier write span — `self+68` and the handle array versus phase A,
`self+16`, `owner+280`, `owner+108` and the entry array versus phase A, `self+16` versus A∪B, the
node versus the two unlink stores, and `owner+16` versus A∪B∪C1. Each of those is a genuine gate-2
exit: the address or trip count would be produced during the call.

Gates: 1 pass (one callee, itself verified, whose only deep call is the memmove `sub_82F4DC60`; no
allocation, free, lock, indirect call or timebase — census `gate1: pass`); 2 pass under the guards
above; 3 pass; 4 pass (the writes are the observable). STATUS pending.

The `stwu r1,-112(r1)` frame move is REPRODUCED, because `sub_82B49438`'s own port reproduces its
frame for the same reason — the memcpy leaf under `sub_82F4DC60` spills at -8 off its caller's r1.

Unsure: what +60 and the handles' +36 mean, and whether the +16 and +20 lists are "free" and "live"
or the other way round. The port takes no position; the names are the offsets.
